I like the overall direction. The main thing I'd change before writing code is the fixed four-panel grid, because several other problems come from it. Here's the review, most important first.

## 1. Don't build around one window size

At 160x50, each panel gets about 78x23 inside its border. That causes problems:

- **Logs at 78 columns** wrap badly. Log lines are often 120–200+ characters (JSON logs, stack traces). Logs are probably the panel you'll read most, and they get the least width.
- **The pod list at 78 columns** is tight for NAME, READY, STATUS, RESTARTS, AGE and NODE. Generated pod names like `api-gateway-7d9f8c6b4-x2k9p` take ~30 columns alone.
- **It won't fit smaller windows:** a split pane, a laptop screen, or SSH from a phone.

Make the layout responsive from the start. Use Ratatui `Constraint`s based on `frame.area()`, set a minimum size (80x24 is the usual target), and show a "terminal too small" message below it. Hide panels or columns as width shrinks: drop NODE first, then AGE.

## 2. Replace the namespace panel with a picker

A permanent namespace panel takes a quarter of the screen for something you change maybe once a session. It's also often broken in practice: many users have RBAC access to a few namespaces but **can't `list namespaces`**, so the panel would just show "Forbidden."

Instead:
- Show the current namespace in the header, which you already plan to do.
- Open a fuzzy picker overlay with `:ns` or a key like `n`.
- If listing namespaces is forbidden, let users type a namespace by hand and remember recent ones.
- Add an "all namespaces" option, which adds a NAMESPACE column to the pod list.

## 3. Don't show every field in the details panel

The field list won't fit in about 21 rows, and annotations are the main problem. `kubectl.kubernetes.io/last-applied-configuration` alone can be several KB of JSON on one line. Istio, Prometheus and ArgoCD annotations add more.

Instead:
- **Summary first:** status with reason (e.g. `CrashLoopBackOff`, `OOMKilled`), ready count, restarts, age, node, pod IP, QoS, owner.
- **Collapse labels and annotations** to a count, like `Labels (7) ▸`, and expand them on demand.
- **Hide or truncate `last-applied-configuration`** by default.
- **Make the panel scrollable**, and add a full-screen describe/YAML view on Enter or `d`/`y`.
- **Show container states** (waiting/terminated reason, last exit code). Restart count alone doesn't tell you why a pod is failing.

## 4. Logs need more design work

- **Which container?** Multi-container pods (sidecars, init containers) are common, so you need a container selector. Default to the first non-sidecar container, or show all with a prefix.
- **Selection churn:** if logs follow the selected pod, scrolling with `j`/`j`/`j` starts and cancels a log stream for every pod you pass. Debounce by ~300ms, or only start streaming on Enter or once the logs panel has focus.
- **Basic controls:** a full-screen zoom toggle (most important), pause/follow, wrap toggle, `/` search, timestamps toggle, and `--previous` for crashlooping pods. For a CrashLoopBackOff pod, previous logs are usually what you actually need.
- **Memory:** keep a ring buffer with a cap rather than growing forever.

## 5. Footer: show a few keys, put the rest in `?`

Fourteen keybindings won't fit below about 140 columns, and a wall of hints is hard to scan anyway. Show 4–6 keys that depend on the focused panel, plus `? help`, and put the full list in a help overlay.

## 6. Color coding

- **Colorblind users:** red/green is the most common color deficiency (about 8% of men). Always pair color with text or a symbol, which the STATUS column mostly does already. Don't let color be the only signal, especially in the namespace and log panels.
- **Missing states:** you'll also see `Completed`/`Succeeded` (dim or gray, not green), `Terminating` (often stuck), `Unknown`, `ImagePullBackOff`, `ContainerCreating` and `Evicted`.
- **Readiness:** a pod that is `Running` but `0/1` ready is a problem. Color it yellow, not green, based on the READY column.
- **Terminal themes:** yellow on a light background is unreadable. Use the terminal's ANSI palette rather than hardcoded RGB, and respect `NO_COLOR`.

## 7. Things the design doesn't cover yet

- **Focus indicator:** with four identical bordered panels, users need to see which one is active. Highlight the focused border and title, and dim the others.
- **Stable selection:** when pods are added or removed during live updates, keep the selection on the same pod (track it by UID, not row index) so the cursor doesn't jump.
- **Filtering:** `/` to filter pods by name or label is probably the most-used feature in k9s-style tools.
- **Empty, loading and error states:** for each panel, plan what it shows when there are no pods, while it's connecting, when a request is forbidden, and when the API server is unreachable.
- **Header safety:** color the context red/orange when it matches a pattern like `prod`. Show connection status and last-sync time. If you add delete or exec later, require confirmation.

## Suggested layout

```
┌ ctx: prod-east ▲ │ ns: payments │ ● connected ─────────────────────────┐
├─ Pods (23) [/filter] ───────────────────┬─ Details ────────────────────┤
│ NAME                 READY STATUS   RST │ api-7d9f…  CrashLoopBackOff  │
│▶api-7d9f8c6b4-x2k9p  0/1   CrashLoop 14 │ Last exit: 137 (OOMKilled)   │
│ worker-5c8d…         1/1   Running    0 │ Node: ip-10-0-3-12 …         │
│                                         │ Labels (7) ▸  Annot. (4) ▸   │
├─ Logs: api / container: app [follow] ───┴──────────────────────────────┤
│ full-width log lines here …                                            │
└ ↑↓ select  ⏎ describe  l logs  z zoom  / filter  ? help ───────────────┘
```

- **Top:** the pod list is the main panel at about 60% width. Details sit beside it at 160+ columns and become a toggle when the window is narrower.
- **Logs:** full width along the bottom, with `z` to zoom to full screen.
- **Namespaces:** an overlay picker instead of a panel.

On the Rust side, keep all Kubernetes I/O (kube-rs watchers and log streams) in tokio tasks that send messages to the UI loop over a channel. Don't let the render path await anything. Starting that way makes debouncing, cancelling log streams and showing connection status much easier later.
