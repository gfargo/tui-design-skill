The busy feeling comes from three things. Your data sits inside three borders, every status is said three or four times, and half the rows carry no data at all. Cut the extra borders, use one cue per status, and give the logs the space the Details box is taking up now.

## Clutter audit

**1. Border nesting is 3 deep.** From the terminal edge to `build-api` you cross the outer `CI MONITOR` frame, the `Pipelines` panel and an unlabeled inner box. Details is the same. Logs is 2 deep.
- 8 of your 17 rows are nothing but border lines, so 47% of the height carries no data.
- Each pipeline row spends about 18 cells on `│ │ │` and padding, which is more than the job name.
- **Delete:** the outer frame (the terminal edge already frames the app) and both unlabeled inner boxes. That leaves one border per pane.

**2. Status is said 3–4 times.**
- In the list, `[PASS]` is the word, the brackets and presumably the color.
- In Details, `✅ PASSED ✅` is two emoji, an uppercase word and the color.
- Keep at most one color cue plus one non-color cue. Use the word plus color, and let `pass` stay quiet (dim or plain) so `FAIL` is the only thing that stands out.
- `[....]` for running looks like a placeholder or truncated text. Use the word `running`.

**3. A marker on every row marks nothing.**
- `▶` is on 5 of 5 rows. And nothing shows which row is selected: Details says `build-api`, but the list never does. That's a real usability bug, not just a style issue.
- **Fix:** drop the `▶`s and use reverse video on the selected row only.
- `▶` also has ambiguous width, so it can take 2 cells under CJK locales.

**4. About half of each log line is boilerplate.** In `[INFO] 2026-05-31 14:22:01 :: Starting build-api ::`, only the time and the message are information.
- The date is the same on every line, so show it once.
- `[INFO]` on every line is another always-on marker. Leave the level blank for info and show only `WARN` and `ERR`.
- The `::` wrappers add nothing.
- Result: `14:22:01  Starting build-api`, which is 27 cells instead of 51.

**5. The space goes to the wrong pane.**
- Details gets a double-boxed panel for five fields that fit on one line.
- Logs gets 3 rows, but logs are what you actually read when something breaks.
- The logs show `build-api` (passing) while `test-unit` is failing. Logs should follow the selected job, and a failure should be easy to land on.

**6. Width bugs are already showing in your sketch.** The `✅ PASSED ✅` row and the log rows break the right border. `✅` is 2 cells wide, so any byte- or rune-based padding misaligns.
- Use narrow symbols (`✓ ✗`) or words.
- Measure with `lipgloss.Width()`, never `len()`.

**7. The footer and header use space poorly.**
- The brackets in `[q] Quit` are noise.
- `[↑/↓] Navigate` describes keys everyone already knows, and there's no `?` for help.
- The header shows a version number. Repo, branch, failing count and last update time would be more useful.

Also, your sketch is about 79 columns wide, not 120. At 120, these fixed-looking boxes would just stretch with empty space.

## Proposed layout (120 cols)

```

┌ Pipelines ─────────────────────────┐┏ Logs: test-unit ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
│ pipeline        status      time   │┃ test-unit  FAIL  1m12s  main @ a3f9c2b  "fix token refresh race"               ┃
│ build-api       pass       3m42s   │┃                                                                                ┃
│ build-web       pass       2m10s   │┃ 14:22:01        Starting test-unit                                             ┃
│ test-unit       FAIL       1m12s   │┃ 14:22:03        go test ./...                                                  ┃
│ test-e2e        running    0m48s   │┃ 14:23:11        --- FAIL: TestAuthRefresh (0.42s)                              ┃
│ deploy-stg      queued         -   │┃ 14:23:11            auth_test.go:88: want 200, got 401                         ┃
│                                    │┃ 14:23:13  ERR   exit status 1                                                  ┃
└────────────────────────────────────┘┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ following ━┛
 ↑↓ select ⋅ tab pane ⋅ / filter ⋅ f follow ⋅ r refresh ⋅ ? help ⋅ q quit
```

- **Borders:** one per pane. The header and footer have none.
- **Focus:** shown by a heavy border (`┏━┓`), plus the accent color. The test-unit row is in reverse video in the real UI; that's the only selection cue. When the list doesn't have focus, its selection is shown muted.
- **Status:** a word plus one color. `FAIL` is red and bold, `running` is yellow, and `pass` is dim green or plain. That's 2 cues per status instead of 4.
- **Details:** collapsed into the first line of the log pane.
- **Logs:** follow mode is on by default. Scrolling up pauses it and shows `▾ N new` in place of `following`. `G` or `f` turns following back on.

## At smaller sizes

- **80×24:** stack the panes instead of placing them side by side. The pipeline list goes on top, sized to its row count and capped at about 8 rows. Logs get the full width below. A 34/46 split would leave log lines too narrow to read.
- **60 columns (tmux split):** one pane with no borders. `Enter` opens the selected job's logs full-screen, and `Esc` returns.
  ```
   ci-monitor  acme/api ⋅ main            1 failing ⋅ 14:23:13
   pipeline        status      time
   build-api       pass       3m42s
   build-web       pass       2m10s
   test-unit       FAIL       1m12s
   test-e2e        running    0m48s
   deploy-stg      queued         -

   ↑↓ select ⋅ enter logs ⋅ / filter ⋅ ? help ⋅ q quit
  ```
  The footer drops hints from the right but always keeps `? help`.
- **Below about 60×12:** show a centered message that names that minimum (e.g. "Terminal too small — needs 60×12, have 52×10"). Don't render a broken layout.

## Bubble Tea / Lipgloss notes

- **Borders:** use `lipgloss.ThickBorder()` for the focused pane and `NormalBorder()` for the other, chosen at render time from `m.focus`. In Lipgloss v2, `Width()` includes the border, so drop any carried-over `Width(w-2)` math.
- **Breakpoints:** read the size from `tea.WindowSizeMsg` and choose the layout (side by side / stacked / single pane / too small) in `View()`, not in `Update`.
- **Components:** `bubbles/table` (or `list`) for pipelines, `bubbles/viewport` for logs (with a capped buffer), and `bubbles/help` built from your `key.KeyMap` so the footer never drifts from the real bindings.
- **Colors:** define style tokens by meaning (`statusFail`, `statusRunning`, `textMuted`, `borderFocus`) rather than hard-coding colors in each style. That way `NO_COLOR` and light/dark (`tea.RequestBackgroundColor` → `lipgloss.LightDark`) are each one switch. Everything above still reads in monochrome, because status is a word and focus is the border weight.
- **Tests:** add golden-frame tests at 120×40, 80×24 and 60×20 so a regression at any of these sizes gets caught.
