## Fix: decide the layout from the terminal width on every frame

Splitting everything 33/33/33 is the root problem. Each column gets narrower at the same rate, so all three become unusable at about the same width. Choose a layout for each width range, and when there isn't room for a pane, hide it completely instead of squeezing it. Keep cwd, selection and scroll position in your app state, separate from the layout. That way resizing never moves the cursor.

| Width | Layout | What changes |
|---|---|---|
| **110+ cols** | parent │ current │ preview, widths `Fill(1) : Fill(4) : Fill(3)` | The middle column is widest because that's where users work (yazi uses `[1, 4, 3]`) |
| **80–109** (80×24, laptops) | current │ preview | The parent column goes away. A one-row path header at the top shows where you are |
| **40–79** (tmux splits, 60 cols) | current only, full width | `Tab` opens the preview full-screen; `Esc` comes back |
| **Under 40×8** | "Too small" message | Names the size it needs. `q` and `Ctrl+C` still work |

I'd hide the **parent** column first, not the preview. In practice the parent column tells you "where am I," and a one-row path header shows that more cheaply. The preview's content can't be shown any other way without an extra keypress. If your users rely more on looking at sibling folders than on previews, swap the order. Either way, hide a pane completely. Never shrink it below about 30 columns.

## Ratatui sketch

Put the layout math in a pure function so you can test it without a terminal:

```rust
use ratatui::layout::{Constraint, Layout, Rect};

const MIN_W: u16 = 40;
const MIN_H: u16 = 8;

pub enum Panes {
    TooSmall,
    Single { header: Rect, body: Rect, footer: Rect },               // shows current OR preview
    Two    { header: Rect, current: Rect, preview: Rect, footer: Rect },
    Three  { header: Rect, parent: Rect, current: Rect, preview: Rect, footer: Rect },
}

pub fn compute_layout(area: Rect, preview_hidden: bool) -> Panes {
    if area.width < MIN_W || area.height < MIN_H {
        return Panes::TooSmall;
    }
    let [header, body, footer] = Layout::vertical([
        Constraint::Length(1),
        Constraint::Fill(1),
        Constraint::Length(1),
    ]).areas(area);

    match area.width {
        w if w < 80 || preview_hidden => Panes::Single { header, body, footer },
        w if w < 110 => {
            let [current, preview] = Layout::horizontal([Constraint::Fill(4), Constraint::Fill(3)])
                .spacing(1)
                .areas(body);
            Panes::Two { header, current, preview, footer }
        }
        _ => {
            let [parent, current, preview] =
                Layout::horizontal([Constraint::Fill(1), Constraint::Fill(4), Constraint::Fill(3)])
                    .spacing(1)
                    .areas(body);
            Panes::Three { header, parent, current, preview, footer }
        }
    }
}
```

Call it with `frame.area()` on every draw. Don't save the rectangles between frames. When tmux or SSH resizes the window, crossterm sends `Event::Resize` and the next draw lays everything out again. In `Single`, a `single_view: Current | Preview` field in your view state decides what fills `body`. The 110 / 80 / 40 cutoffs are starting points; adjust them based on how your real file listings look.

## Why filenames turn to mush, and the fix

- **Cut filenames in the middle, keeping the extension:** `quarterly-report-fi…v3.pdf`, not `quarterly-report-fin…`. Long names often differ only near the end (`-v2`, `-v3`, `.tar.gz`).
- **Cut paths from the start:** `…/app/src/components`, so the current folder stays visible.
- **Measure in terminal cells, not bytes.** Use `Line::width()` / `cell_width()`, not `String::len()`, and leave one cell for the `…`. Test with CJK names, accented characters and emoji. Mis-measured width is one common cause of "mush" output.
- **Hide less important columns in the current pane, in order:** modified time first, then permissions, then size. The filename always keeps at least 20 cells.
- **Truncate preview text instead of wrapping it.** Over SSH and inside tmux, image previews often don't get through, so fall back to file info (type, size, dimensions) instead of showing a blank pane.

## Borders: count them before adding any

If each column is drawn with `Block::bordered()`, three boxes cost 6 of your 80 columns and 2 of your 24 rows. Each pane also ends up with two lines between it and the terminal edge. The `.spacing(1)` above uses a single blank column as the divider, or you can draw one `│` there. Put the folder path in the header row, not in three box titles. Show the selected row with reverse video only; don't also add a marker and a color.

## Height matters too

At 24 rows, a one-row header plus a one-row footer leaves 22 rows of files. Below about 12 rows, shrink the footer to just `? help`. Load directory listings and previews in the background, and wait briefly before loading a preview so scrolling stays smooth. Over SSH or a network mount, a slow `read_dir` would otherwise freeze the screen, which feels like a layout bug.

## Tests

1. Unit-test `compute_layout` at widths 220, 110, 109, 80, 79, 60, 40 and 39. Check which variant comes back and that no pane is narrower than 30 columns.
2. Render frames with `TestBackend` at **220×50, 80×24, 60×24 and 39×10**. Save each as an `insta` snapshot named by size (`browser_60x24`). These snapshots capture text only, so compare `Buffer`s where the selection highlight matters.
3. Run one or two tests in a real terminal session for a live resize and for leaving cleanly. To check by hand for free, run `tmux split-window -h` and drag the divider.

This works because the narrow layout is a drill-down. When only one thing is on screen, narrowing the terminal just makes it smaller. A fixed three-way split has nothing it can give up.
