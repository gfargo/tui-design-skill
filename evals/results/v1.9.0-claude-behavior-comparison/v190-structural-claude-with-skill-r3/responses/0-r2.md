No, don't ship the defer. It looks like a safety net, but it does the opposite of what you intended.

## Why `defer p.RestoreTerminal()` is wrong

- **`RestoreTerminal` doesn't restore the shell.** It's the other half of `ReleaseTerminal()`, a temporary handoff API. It puts Bubble Tea's terminal modes back on so the TUI can continue. If you call it after `Run()` returns, it can turn on raw mode, the alternate screen, cursor hiding or mouse modes again, right after Bubble Tea switched them off. That leaves the terminal in the broken state you were trying to prevent.
- **`Run()` already does the cleanup.** `Program.Run()` restores the terminal when the program quits normally, when it returns an error, and when it recovers a panic. Panic recovery is on by default. Wrapping `Run()` in your own cleanup just competes with the framework's.
- **The defer can't catch the panics that would actually hurt you.** If one of your own goroutines panics, the process crashes and `main`'s defers don't run. A defer around `Run()` only helps on paths that `Run()` already handles.

## What to use instead

```go
p := tea.NewProgram(model)
_, err := p.Run()
return err
```

That's the whole pattern. Make sure the rest of the shutdown goes through Bubble Tea too:

- **Exiting:** return `tea.Quit` from `Update` for a normal exit. If the caller should see an interruption, return `tea.Interrupt` instead; `Run()` then returns `tea.ErrInterrupted`. Don't call `os.Exit` or `log.Fatal` inside `Update`, `View` or a `Cmd`, because that skips the restore.
- **Signals:** Bubble Tea's default handler already turns an external SIGINT or SIGTERM into a clean shutdown, so don't add your own `signal.Notify` for this.
- **Panic recovery:** don't use `tea.WithoutCatchPanics()` in production. If you turn recovery off, you take over restoring the terminal yourself.
- **Background work:** run it as a `tea.Cmd` rather than starting your own goroutine, so it stays inside the program's lifecycle.
- **Opening an editor or shell:** use `tea.ExecProcess(cmd, callback)`. It releases the terminal, waits for the child process, restores the terminal and repaints. Reload any data the child might have changed in the callback. This handoff is the only situation where `ReleaseTerminal`/`RestoreTerminal` make sense, and `ExecProcess` already wraps them.

Only build your own outer cleanup if you deliberately bypass Bubble Tea's managed path. In that case you'd restore the terminal using the original state you saved before the program started, not with `RestoreTerminal`.

(This is based on the Bubble Tea v2 lifecycle notes in the tui-design skill's Go reference, `references/ecosystem-go.md:88-101`.)
