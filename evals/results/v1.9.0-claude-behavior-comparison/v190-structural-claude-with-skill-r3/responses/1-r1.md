Before release, I'd make three changes. First, add a narrow layout, because a three-pane layout with no fallback breaks the first time someone opens it in a tmux split or on a laptop. Second, remove the outer frame and the per-row decoration. Third, cut the footer from 18 shortcuts to about 7 that change with the focused pane. Details below, most harmful first.

## 1. Add responsive behavior

"Most of us use wide monitors" describes your desk, not every place the tool will run. It will also run in a 60-column tmux split, an 80×24 SSH session to a bastion host, and on a laptop during an on-call page. Three panes at fixed widths have nowhere to go when the terminal shrinks, so you get clipped YAML, mangled rows, or a crash on resize. The order in which panes give way:

| Width | Layout |
|---|---|
| **120+** | Three panes, as now. Namespaces 20–24 columns, resources the widest, YAML gets the rest (30 columns minimum). |
| **80–119** | The namespace pane goes away. The current namespace moves to the header, and `n` (or `:ns`) opens a picker. Resources and YAML split the width. |
| **60–79** | Resources only. `Enter` opens the YAML full-screen and `Esc` returns. This is the k9s drill-down model, which shrinks well because only one main view is ever on screen. |
| **Below ~50×12** | Show `terminal too small: need 50x12`, keep `q` and `Ctrl+C` working, and draw no broken frame. Pick the real minimum from the 60-column layout; don't claim to need 80. |


Lay out with ratios or min/fill constraints, not fixed column positions. Recompute the layout from the current size on every resize event. In tables, truncate instead of wrapping. For pod names, cut from the middle (`api-7d…x2k`) so the unique suffix stays visible.

## 2. Clutter audit

**Borders.** There are two borders between the terminal edge and your content: the double frame, then each pane's border. Delete the outer frame, since the terminal edge already frames the app. That gives back 2 columns and 2 rows. Double-line borders also look dated, and they're East Asian Ambiguous width, so on some locale and terminal settings every border cell renders two cells wide and the layout breaks. Use single-line pane borders and show focus with a heavier border on the focused pane. Once the double frame is gone, that cue becomes readable.

**Signals per status.** "Ready" is currently encoded three times: the word `[READY]`, the green color, and the checkmark. The budget is one color cue plus one non-color cue. On top of that, it appears on nearly every row, so it works as an always-on marker that tells the reader nothing.
- Show real data instead: a `READY` column (`1/1`, `0/1`) and a `STATUS` column (`Running`, `CrashLoopBackOff`).
- Mark only the exceptions, as `! CrashLoop` in yellow or red. Healthy rows get no color and no symbol, so a broken pod stands out at a glance.
- If the resources pane also lists ConfigMaps, Secrets or Services, `[READY]` on those rows is inaccurate, because those kinds don't have a ready state. Pick columns per resource kind.

**Bullets.** A `•` on every row marks nothing, and `•` is also ambiguous-width. Remove it. The selected row gets reverse video, and nothing else.

**Chrome share.** Each row spends about 12 cells (`• ` plus ` [READY] ✓`) on decoration, roughly 20% of a ~60-column resources pane. Vertically, the frame, pane borders and two footer rows take 6 rows, about 15% of a 40-row terminal, before any data appears. The changes above recover roughly 2 columns and 3 rows, and they remove the per-row decoration entirely.

## 3. Footer: 18 shortcuts is a reference card

People don't read two rows of shortcuts. Show 5–7 at a time and let them change with the focused pane. Put the most frequent first, end with `? help`, and drop hints from the right as the terminal narrows. Move all 18 into a grouped `?` help screen. Add a `:` command mode (`:pods`, `:svc`, `:ns payments`) as the k9s-style way to switch resources. The interaction reference recommends a palette once an app has more than about 20 actions, and you're close to that. Generate the footer and the help screen from one keymap definition so they can't drift apart.

## 4. Other release blockers outside the layout

- **States:** design each one before shipping. That means loading (keep the old rows visible), an empty namespace (name the namespace and offer a next action), RBAC `forbidden` on some resource kinds (show a partial view with a retry key, not a blank pane), and API server unreachable (keep the last good data dimmed, with a `STALE 2m` marker).
- **Live updates:** track the selected row by UID, not by row index. If that pod disappears, select its nearest neighbor, and don't re-sort on every refresh. Without this, the cursor jumps while someone is about to press `d` on a pod.
- **Never block the UI on API calls**, and restore the terminal on every exit path, including panics.
- **Secrets in the YAML pane:** consider masking `data:` by default with a reveal key, since this tool will get screen-shared during incidents.
- **`NO_COLOR`:** the words `Running` and `! CrashLoop` and the heavier focus border all still carry meaning without color. Check that nothing else depends on color alone.
