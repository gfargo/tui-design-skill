# Review: Kubernetes resource browser

**Recommendation:** Before release, make two changes. First, delete the outer frame and the per-row status decoration. Second, make the layout responsive, with a drill-down fallback. "Most of us use wide monitors" covers your own desks, but it won't cover a 60-column tmux split, an SSH session from a laptop, or anyone who puts the app next to a terminal running `kubectl logs -f`. Kubernetes users do all of those things.

## 1. Clutter audit

| Measure | Count | Target |
|---|---|---|
| Border-nesting depth | **2** (double outer frame → pane border → content) | ≤ 1 |
| Signals for "this resource is ready" | **4**: bullet, `[READY]`, green, ✓ | ≤ 2 (one color + one non-color) |
| Always-on markers | Bullet on 100% of rows; `[READY]` + ✓ on ~every healthy row | Only on exceptions |
| Vertical chrome at 24 rows | 2 frame + 2 pane borders + 2 footer = **6 of 24 rows (25%)**, and no context header yet | ~3 rows |
| Per-row boilerplate | ~12 cells (`• ` + ` [READY] ✓`) repeated on every row | 0 on healthy rows |

**What to cut, specifically:**

- **The double-line outer frame.** The terminal edge already frames the app, so this border separates nothing. Double-line also reads as retro/DOS, and box-drawing characters are East Asian Ambiguous width, so on some locales every border cell can render two columns wide. Removing it gets back 2 rows and 2 columns.
- **The bullet on every row.** A marker on every row marks nothing. Show the selected row with reverse video instead.
- **`[READY]` + ✓ + green on healthy rows.** Your list is mostly healthy, so the status should stand out only where something is wrong. Use a plain status column the way `kubectl` does (`READY 1/1`, `STATUS Running`). Healthy rows get default color. Problem rows get the word (`CrashLoopBackOff`, `0/1`) plus red or yellow. That stays within the two-signal budget, keeps its meaning under `NO_COLOR`, and makes the broken pod the one thing your eye catches. A binary READY badge also hides useful information: `2/3` is not "ready", and it isn't the same as `0/3` either.
- **The 18 shortcuts in the footer.** Nobody scans 18. Show the 4–6 most useful for the focused pane, generated from your keymap so the footer can't drift from the real bindings, and put `? help` last. The full list goes in a `?` overlay grouped by context. With 18+ actions you're past the point where a `:` command mode pays off: `:pods`, `:svc`, `:ns staging`, the way k9s does it. Every bound action should also be reachable there.

Net effect at 24 rows: you go from 18 content rows to about 21, and you add a one-line header showing **cluster / context / namespace**. That header is the most important fact in a Kubernetes tool, and the current layout doesn't show it anywhere.

## 2. The floor: responsive behavior

Right now, a 140-column, three-pane layout opened at 80 columns either squeezes the panes until they're unusable or breaks the render. Use this ladder:

| Width | Layout |
|---|---|
| **120+** | Namespaces (20–24 cols) │ resources │ YAML preview |
| **80–119** | Namespaces collapse into the header (`n` or `:ns` opens a picker). Resources go full width; the YAML preview drops and `Enter`/`y` opens YAML full-screen |
| **60–79** | Single pane, drill-down: namespace → resources → YAML, with `Esc` going back. Low-priority columns (IP, NODE, AGE) drop first; NAME and STATUS are load-bearing |
| **< 48×12** (or whatever you test as the minimum) | `terminal too small: need 48x12`. `q` and `Ctrl+C` still work. Never render a broken frame |

The namespace pane should be the first to collapse, because it's the one you look at least. Namespace is mostly a context you set and then leave alone, and that's why it belongs in the header.

The panes keep single-line borders because three dynamic panes side by side need visible boundaries. Show focus with a heavy border or a bold title on the focused pane, so it still works without color. `CrashLo…` would be red; nothing else on that row has color.

There are no borders here at all, because there's only one pane and nothing to separate.

## 3. Missing states to design before release

Kubernetes tools spend a lot of time in states other than the happy path:

- **Loading:** draw the layout immediately, show a spinner with elapsed time, and keep the old rows visible during refresh.
- **Partial / forbidden:** RBAC denies listing in some namespaces all the time. Show `! forbidden: list pods in kube-system` inline. Don't show an empty list.
- **Stale / disconnected:** when the API server drops, keep the last-known rows dimmed with `STALE 2m · reconnecting (3)`. Don't blank the screen.
- **Empty:** `No pods in "staging"`, followed by `n change namespace`.

## 4. Implementation checks that go with this

- Re-layout from the current size on every resize event, and pick the breakpoint at that moment.
- Truncate cells with an ellipsis instead of wrapping. Measure terminal cell width, not string length. Pod names are ASCII, but labels and annotations in the YAML pane may not be.
- Debounce redraws from the watch stream. Don't repaint on every event.
- Add golden-frame tests at 140×40, 80×24, 60×24 and the minimum size, plus one run with `NO_COLOR=1` to confirm failures are still visible without color.

## Priority order

1. Responsive fallback and the too-small state. Without these the app breaks for real users.
2. Header showing cluster/context/namespace. Acting on the wrong cluster is the costliest mistake a user can make here.
3. Status column that marks only the exceptions; remove the bullets, `[READY]` and ✓ from healthy rows.
4. Remove the outer frame.
5. Footer down to about 6 contextual hints, plus `?` help and a `:` command mode.
6. Loading, forbidden, stale and empty states.
