**Testing a Bubble Tea app is easier than testing most TUIs.** The Elm architecture means all your logic lives in `Update(msg) (Model, Cmd)`, which is basically a pure function. You don't need a terminal. You build a model, feed it a fake keypress, and check the state that comes back.

## Layer 1: Unit-test `Update` directly (start here)

This kind of test would have caught your Tab bug within seconds:

```go
// model_test.go
package main

import (
	"testing"

	tea "github.com/charmbracelet/bubbletea"
)

func TestTabCyclesColumns(t *testing.T) {
	m := newModel() // however you build your initial model; assume 3 columns

	for _, want := range []int{1, 2, 0, 1} { // includes the wrap-around
		next, _ := m.Update(tea.KeyMsg{Type: tea.KeyTab})
		m = next.(model)
		if m.focusedCol != want {
			t.Fatalf("after Tab: focusedCol = %d, want %d", m.focusedCol, want)
		}
	}
}

func TestShiftTabCyclesBackwards(t *testing.T) {
	m := newModel()
	next, _ := m.Update(tea.KeyMsg{Type: tea.KeyShiftTab})
	if got := next.(model).focusedCol; got != 2 {
		t.Fatalf("focusedCol = %d, want 2 (wrap to last)", got)
	}
}
```

Once you have a few of these, a table-driven test that covers every keybinding works well:

```go
func press(m model, keys ...tea.KeyMsg) model {
	for _, k := range keys {
		next, _ := m.Update(k)
		m = next.(model)
	}
	return m
}

var (
	tab   = tea.KeyMsg{Type: tea.KeyTab}
	enter = tea.KeyMsg{Type: tea.KeyEnter}
	runes = func(s string) tea.KeyMsg { return tea.KeyMsg{Type: tea.KeyRunes, Runes: []rune(s)} }
)

func TestKeybindings(t *testing.T) {
	tests := []struct {
		name  string
		keys  []tea.KeyMsg
		check func(t *testing.T, m model)
	}{
		{"tab moves focus", []tea.KeyMsg{tab}, func(t *testing.T, m model) {
			if m.focusedCol != 1 { t.Errorf("focusedCol = %d", m.focusedCol) }
		}},
		{"j moves cursor down", []tea.KeyMsg{runes("j")}, func(t *testing.T, m model) {
			if m.cursor != 1 { t.Errorf("cursor = %d", m.cursor) }
		}},
		// "move card right", "delete card", etc.
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) { tt.check(t, press(newModel(), tt.keys...)) })
	}
}
```

You can also check that a quit key returns a quit command: call `cmd()` and check whether the result is a `tea.QuitMsg`.

> **Version note:** this uses Bubble Tea v1. In v2, key events are `tea.KeyPressMsg{Code: tea.KeyTab}` and similar. Check your `go.mod` and adjust.

## Layer 2: End-to-end tests with `teatest`

Charm ships [`github.com/charmbracelet/x/exp/teatest`](https://pkg.go.dev/github.com/charmbracelet/x/exp/teatest). It runs your real program in a virtual terminal, so it also exercises `Init`, commands, window-size handling and rendering:

```go
func TestFullFlow(t *testing.T) {
	tm := teatest.NewTestModel(t, newModel(), teatest.WithInitialTermSize(100, 30))

	tm.Send(tea.KeyMsg{Type: tea.KeyTab})
	tm.Type("q")

	final := tm.FinalModel(t, teatest.WithFinalTimeout(2*time.Second)).(model)
	if final.focusedCol != 1 {
		t.Errorf("focusedCol = %d", final.focusedCol)
	}
}
```

It also supports **golden-file snapshots** of the rendered screen. `teatest.RequireEqualOutput(t, out)` compares output against `testdata/*.golden`, and `go test ./... -update` regenerates the files. Some tips:
- Add `func init() { lipgloss.SetColorProfile(termenv.Ascii) }` in tests. Otherwise color codes differ between your laptop and CI.
- Add `*.golden -text` to `.gitattributes` so line endings don't get rewritten.
- Keep it to 2–4 snapshots of key screens. Golden files break on every cosmetic tweak, so they work best as a "did the layout explode?" check. Put behavior checks in Layer 1.

## Layer 3: CI

```yaml
# .github/workflows/test.yml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version-file: go.mod }
      - run: go vet ./...
      - run: go test -race ./...
```

Then turn on branch protection so PRs can't merge while it's red.

## Suggested order

1. **Today:** write `TestTabCyclesColumns`. Every bug that reaches users should get a regression test like this one.
2. **This week:** a table-driven test that covers every keybinding in your help screen. That's your refactor safety net.
3. Add the CI workflow. It takes about 10 minutes.
4. Later: one or two `teatest` flows plus a golden snapshot of the main board.

**A refactor that makes testing easier:** if logic is buried inside `View()` or depends on global state, pull it into small model methods like `m.nextColumn()` or `m.moveCard(dir)`. Those are easy to test on their own, and `Update` just calls them. If you're not already using `key.Binding` with `key.Matches`, it also gives you one list of keybindings to loop over in tests.
