## (a) Debugging without corrupting the screen

**1. Log to a file, not stdout.** Use `tracing` with a file appender and watch it from a second terminal:

```rust
// Cargo.toml: tracing, tracing-subscriber, tracing-appender
let file = tracing_appender::rolling::never(".", "debug.log");
tracing_subscriber::fmt().with_writer(file).with_ansi(false).init();
```
```sh
tail -f debug.log   # in another terminal
```

If you'd rather see logs inside the app, `tui-logger` gives you a log widget.

**2. Log the computed `Rect`s on every draw, plus the size you think you have:**

```rust
terminal.draw(|f| {
    let area = f.area();               // f.size() on ratatui < 0.28
    let l = compute_layout(area);
    tracing::debug!(?area, ?l.panel, ?l.footer, "layout");
    debug_assert!(!l.panel.intersects(l.footer), "panel overlaps footer: {l:?}");
    // ...
})?;
```

The `debug_assert!` turns an intermittent visual glitch into a panic at the exact frame where it happens. Install a panic hook that restores the terminal first (`ratatui::init()` does this for you), or the panic message gets lost.

**3. Use a real debugger if you need one.** Start the app normally, then attach from another terminal with `lldb -p <pid>` or CodeLLDB's "attach". The TUI keeps its own terminal, so the debugger doesn't interfere with it.

### Likely causes of "off by one row after some resizes"

- **Stale size.** You compute layout from a size stored at startup, from `Event::Resize(w, h)`, or from `terminal.size()` outside `draw`, while ratatui renders into `f.area()`. Always derive layout from `f.area()` inside the draw closure. Never cache `Rect`s between frames.
- **Manual Rect arithmetic**, like `Rect { y: area.height - 3, .. }` or `height: area.height - footer_h`. These forget `area.y`, round differently from the layout solver, or underflow at small sizes. Use `Layout` for everything, or `area.rows()`, `Rect::inner`, and `saturating_sub`.
- **Mixed `Percentage`/`Ratio` constraints next to a `Length` footer.** At some heights the solver rounds in a way you didn't expect. Make the footer `Length(n)` and the body `Min(0)`/`Fill(1)`.
- **Nested layouts split from the wrong parent**, e.g. splitting `f.area()` a second time instead of the body chunk.

Ratatui clips drawing to the buffer, but not to sibling areas. If a widget's `Rect` extends into the footer, its border draws there, which is exactly the symptom you're seeing.

## (b) A regression test that actually prevents it

Do two things: make the layout a pure function and check it at every size, then add rendering tests with `TestBackend`.

**1. Pull the layout out and test it at every terminal size.** This is cheap and catches the intermittent cases:

```rust
pub struct AppLayout { pub panel: Rect, pub footer: Rect, /* ... */ }

pub fn compute_layout(area: Rect) -> AppLayout {
    let [body, footer] = Layout::vertical([Constraint::Fill(1), Constraint::Length(1)]).areas(area);
    // ...
}

#[test]
fn layout_invariants_hold_at_all_sizes() {
    for w in 1..=250 {
        for h in 1..=120 {
            let area = Rect::new(0, 0, w, h);
            let l = compute_layout(area);
            assert!(!l.panel.intersects(l.footer), "overlap at {w}x{h}: {:?}", (l.panel, l.footer));
            assert!(area.contains_rect(l.panel) || l.panel.is_empty(), "panel escapes at {w}x{h}");
            // footer is the last row whenever there's room for it
            if h >= 1 { assert_eq!(l.footer.bottom(), area.bottom(), "at {w}x{h}"); }
        }
    }
}
```

If `Rect::contains_rect` isn't in your version, use `area.union(l.panel) == area`. You could use `proptest` instead, but an exhaustive loop over 30k sizes runs in milliseconds and tells you exactly which size failed.

**2. Render through `TestBackend` and resize mid-test.** This catches stale-state bugs that a pure layout test can't, because it uses the real draw path:

```rust
use ratatui::{backend::TestBackend, Terminal};

#[test]
fn footer_intact_after_resize() {
    let mut app = App::default();
    let mut term = Terminal::new(TestBackend::new(80, 24)).unwrap();
    term.draw(|f| app.render(f)).unwrap();

    for (w, h) in [(80, 23), (81, 23), (40, 10), (120, 37), (80, 24)] {
        term.backend_mut().resize(w, h);
        term.draw(|f| app.render(f)).unwrap();   // draw() picks up the new size

        let buf = term.backend().buffer();
        let footer_row: String = (0..w).map(|x| buf[(x, h - 1)].symbol()).collect();
        assert!(!footer_row.contains('─') && !footer_row.contains('└'),
                "border leaked into footer at {w}x{h}: {footer_row:?}");
    }
}
```

If your app also handles `Event::Resize` itself (by updating state), call that same handler in the test before `draw`, so the test runs the same sequence as production.

**3. Optionally, snapshot the size that failed.** Use `insta::assert_snapshot!(term.backend())`. `TestBackend` implements `Display`, so a regression shows up as a readable visual diff in review.

## Workflow

1. Add the file logging and the `debug_assert!`, then resize until it panics.
2. Write the failing size(s) into the tests above.
3. Fix it, usually by deriving layout from `f.area()` and removing hand-computed Rects.
4. The exhaustive invariant test then makes sure the bug can't come back at any size, not just the one you happened to find.
