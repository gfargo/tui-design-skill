Logging to a file shows you the problem, and a test against ratatui's `TestBackend` finds it and keeps it from coming back. Most bugs like this come from Rect arithmetic, not from the terminal, so you can usually reproduce them without a real terminal at all.

## (a) Debugging without corrupting the screen

**1. Send output somewhere other than the terminal you draw on.** Pick one:

- **Quickest:** ratatui's crossterm backend usually draws to stdout, so `eprintln!` plus `cargo run 2> debug.log` works. Run `tail -f debug.log` in a second terminal.
- **Better:** use `tracing` with a file appender, which you can leave in the code permanently:
  ```rust
  let file = std::fs::File::create("debug.log")?;
  tracing_subscriber::fmt().with_writer(file).with_ansi(false).init();
  ```
- **In-app:** the `tui-logger` crate gives you a log widget you can toggle on screen.

**2. Log the Rects, not your guesses.** In your draw function, log `frame.area()` and every chunk you compute on every frame:
```rust
tracing::debug!(area = ?frame.area(), ?panel, ?footer, "layout");
```
When the overlap shows up, the log tells you which size caused it and which Rect is wrong. Then add a tripwire so it fails loudly at the moment it happens:
```rust
debug_assert!(!panel.intersects(footer), "panel {panel:?} overlaps footer {footer:?} in {:?}", frame.area());
```

**3. Usual causes of a one-row overlap after resizing:**
- **Stale cached size.** You store `(w, h)` from `Event::Resize` and lay out from that instead of `frame.area()`. Resize events can coalesce or arrive before the draw, so always use `frame.area()` inside `draw`.
- **Hand-built Rects.** Code like `Rect { y: area.y + something, height: area.height - 1, .. }` isn't clamped to the parent the way `Layout` output is. Use `Layout`, or apply `.intersection(parent)` or `.clamp(parent)` afterwards.
- **Rects reused from the previous frame**, for example a panel area stored on `App` and reused after a resize.
- **Small terminals.** When constraints can't all fit, the solver squeezes something. Check what happens when `height` is smaller than the sum of your `Length`s.
- **Off-by-one borders**, for example hand-computing an inner area instead of using `block.inner(area)`.

## (b) Regression tests

First split your code into a pure layout function and a render function, so you can test both without a real terminal:

```rust
pub struct AppLayout { pub panel: Rect, pub sidebar: Rect, pub footer: Rect }

pub fn layout(area: Rect) -> AppLayout {
    let [body, footer] = Layout::vertical([Constraint::Min(0), Constraint::Length(1)]).areas(area);
    let [sidebar, panel] = Layout::horizontal([Constraint::Length(30), Constraint::Min(0)]).areas(body);
    AppLayout { panel, sidebar, footer }
}

pub fn ui(frame: &mut Frame, app: &App) {
    let l = layout(frame.area());
    // render widgets into l.panel, l.sidebar, l.footer
}
```

**Test 1: check every size for overlaps.** This is how you find an intermittent bug: instead of waiting for it, you try every size. It runs in milliseconds.

```rust
#[test]
fn panels_never_overlap_footer() {
    for w in 0..=250 {
        for h in 0..=100 {
            let area = Rect::new(0, 0, w, h);
            let l = layout(area);
            for (name, r) in [("panel", l.panel), ("sidebar", l.sidebar)] {
                assert!(!r.intersects(l.footer), "{name} {r:?} overlaps footer {:?} at {w}x{h}", l.footer);
                assert_eq!(area.union(r), area, "{name} {r:?} escapes {area:?}");
            }
        }
    }
}
```
If your layout depends on app state (a toggled sidebar, a dynamic footer height), use `proptest` to vary that state as well.

**Test 2: render through a sequence of resizes.** Test 1 can't catch stale-state bugs, because those only show up when you render at one size and then another. `TestBackend` can be resized between draws:

```rust
use ratatui::{backend::TestBackend, Terminal};

#[test]
fn footer_survives_resize_sequence() {
    let app = App::test_fixture();
    let mut terminal = Terminal::new(TestBackend::new(80, 24)).unwrap();

    for (w, h) in [(80, 24), (81, 23), (40, 10), (120, 50), (80, 24), (79, 7), (80, 24)] {
        terminal.backend_mut().resize(w, h);
        terminal.draw(|f| ui(f, &app)).unwrap();

        let buf = terminal.backend().buffer();
        let footer_y = h - 1;
        for x in 0..w {
            let s = buf[(x, footer_y)].symbol();
            assert!(
                !matches!(s, "─" | "└" | "┘" | "┴" | "╰" | "╯"),
                "border glyph {s:?} in footer row at x={x} after resize to {w}x{h}"
            );
        }
    }
}
```
Replace the hard-coded sizes with the one your log caught. If the bug only appears after a particular sequence of sizes, put that exact sequence in the test.

**Test 3: snapshot the size that failed.** Use `insta`. `TestBackend` implements `Display`, so the snapshot is the rendered screen as text and is easy to read in diffs:
```rust
#[test]
fn snapshot_79x7() {
    let mut terminal = Terminal::new(TestBackend::new(79, 7)).unwrap();
    terminal.draw(|f| ui(f, &App::test_fixture())).unwrap();
    insta::assert_snapshot!(terminal.backend());
}
```

**Suggested order:**
1. Add Test 1. It will probably fail immediately and print the exact size that breaks.
2. Fix the Rect math.
3. If Test 1 passes but the bug persists, the cause is stale state, so Test 2 is the one that will catch it.
4. Keep all three tests.

Two API notes: `frame.area()` and `buf[(x, y)]` need ratatui 0.28 or later. On older versions they're `frame.size()` and `buf.get(x, y)`.
