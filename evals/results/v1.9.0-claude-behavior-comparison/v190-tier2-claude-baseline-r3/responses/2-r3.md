## (a) Debugging without corrupting the screen

**1. Send debug output to stderr and redirect it to a file.** Crossterm draws on stdout, so stderr is free:

```rust
eprintln!("frame area={:?} panel={:?} footer={:?}", area, panel, footer);
```
```sh
cargo run 2> debug.log      # in another pane: tail -f debug.log
```

**2. For anything more permanent, use `tracing` with a file appender:**

```rust
let file = tracing_appender::rolling::never(".", "app.log");
tracing_subscriber::fmt().with_writer(file).with_ansi(false).init();
// ...
tracing::debug!(?area, ?panel, ?footer, "layout");
```

If you want logs inside the app, `tui-logger` gives you a log widget.

**3. Install a panic hook that restores the terminal**, so a crash doesn't leave your shell broken. `ratatui::init()` does this for you. If you set up the terminal by hand, call `ratatui::restore()` from the hook.

**4. Use a debugger by attaching to the process.** Run the app in one terminal, then in another run `lldb -p $(pgrep yourapp)` (or use the CodeLLDB "attach" config). The app keeps its own TTY, so the debugger doesn't interfere.

**5. Log the `Rect`s every frame, then resize slowly.** A one-row overlap with this pattern almost always comes from one of these:

- **A stale size.** You build the layout from a size you cached in `Event::Resize(w, h)` or from `terminal.size()`, but draw into `frame.area()`. These can differ by a frame during a resize burst. Always derive the layout from `frame.area()` inside the `draw` closure.
- **Two separate sources of geometry.** For example, the footer is placed by hand (`y: area.bottom() - 1`) while the panel comes from a `Layout` split, or the panel height comes from a percentage calculation of your own. They round differently at some heights, which explains why it's intermittent. Fix: compute every region with one `Layout` split.
- **Hand-written `Rect` arithmetic.** For example, `Rect { height: area.height - footer_h + 1, .. }`, or forgetting that `Block` borders use up rows. Use `block.inner(area)` and `Rect::inner(Margin)`, not your own math.
- **Constraints that can't all be met at small sizes**, like `Percentage` combined with `Length`. Ratatui's `Layout` never returns rects that overlap or go outside the area. So if you see an overlap, something outside `Layout` is producing a rect.

## (b) A regression test

The most useful refactor is to **move the layout into a pure function**, then test it at every size:

```rust
pub struct AppLayout { pub header: Rect, pub panel: Rect, pub sidebar: Rect, pub footer: Rect }

pub fn compute_layout(area: Rect) -> AppLayout {
    let [header, body, footer] = Layout::vertical([
        Constraint::Length(1), Constraint::Min(0), Constraint::Length(1),
    ]).areas(area);
    let [panel, sidebar] = Layout::horizontal([Constraint::Fill(3), Constraint::Fill(1)]).areas(body);
    AppLayout { header, panel, sidebar, footer }
}
```

Then check the invariants over every size, not just a few hand-picked ones. Intermittent bugs live at specific sizes:

```rust
#[test]
fn layout_regions_never_overlap_or_escape() {
    for w in 1..=200 {
        for h in 1..=80 {
            let area = Rect::new(0, 0, w, h);
            let l = compute_layout(area);
            let rects = [("header", l.header), ("panel", l.panel), ("sidebar", l.sidebar), ("footer", l.footer)];
            for (name, r) in rects {
                assert_eq!(area.intersection(r), r, "{name} escapes area at {w}x{h}: {r:?}");
            }
            for (i, (a, ra)) in rects.iter().enumerate() {
                for (b, rb) in &rects[i + 1..] {
                    assert!(!ra.intersects(*rb), "{a} overlaps {b} at {w}x{h}: {ra:?} vs {rb:?}");
                }
            }
        }
    }
}
```

That runs 16,000 cases in milliseconds. If you'd rather sample the space, `proptest` does the same job.

**Also test the real render path and resize sequences**, because a stale-state bug won't show up in a pure function. `TestBackend` covers both:

```rust
#[test]
fn footer_intact_after_resizes() {
    let mut terminal = Terminal::new(TestBackend::new(80, 24)).unwrap();
    let mut app = App::default();
    for (w, h) in [(80, 24), (79, 23), (120, 9), (40, 7), (81, 25), (80, 24)] {
        terminal.resize(Rect::new(0, 0, w, h)).unwrap();
        app.handle_event(Event::Resize(w, h));          // same path as production
        terminal.draw(|f| ui(f, &mut app)).unwrap();

        let buf = terminal.backend().buffer();
        let footer_row: String = (0..w).map(|x| buf[(x, h - 1)].symbol()).collect();
        assert!(footer_row.starts_with(" q quit"), "footer clobbered at {w}x{h}: {footer_row:?}");
    }
}
```

**Snapshot tests are optional but help.** Use `insta` with `insta::assert_snapshot!(terminal.backend())` at two or three sizes, including the one that triggered the bug. `TestBackend` implements `Display`, so the snapshot is a readable text grid, and any future layout change shows up as a visible diff.

**Recommended order:**
1. Add the stderr logging and find a size that reproduces the bug.
2. Write the sweep test and confirm it fails.
3. Move the geometry into a single `Layout` split derived from `frame.area()`.
4. Keep the sweep test and the resize-sequence test as the regression guard.
