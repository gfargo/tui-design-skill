## Rule #1: Don't debug through the terminal Ink is drawing on

Ink redraws its output region on every frame by moving the cursor up and erasing lines. Anything else that writes to the same TTY can break that, so the output garbles. By default (`patchConsole: true`), Ink catches `console.*` calls and prints them above the UI. That protection doesn't cover these cases:

- `process.stdout.write` / `process.stderr.write` called directly (including by libraries, spinners, or progress bars)
- Child processes using `stdio: 'inherit'`
- Logs written after `unmount()` / `exit()`, or before the first render
- Code that sets `patchConsole: false`
- A UI taller than the terminal. Ink can't erase what has scrolled off the screen, so you get duplicated or smeared frames. This often looks like a logging problem but isn't one.

**Fix: write debug output to a file and watch it in a second terminal.**

```ts
// debug.ts
import fs from 'node:fs';
const LOG = process.env.INK_DEBUG_LOG;
export const dbg = (...args: unknown[]) => {
  if (!LOG) return;
  fs.appendFileSync(
    LOG,
    `${new Date().toISOString()} ${args.map(a => typeof a === 'string' ? a : JSON.stringify(a)).join(' ')}\n`
  );
};
```

```sh
# terminal 1
tail -f /tmp/ink.log
# terminal 2
INK_DEBUG_LOG=/tmp/ink.log node dist/cli.js
```

The writes are synchronous, so nothing is lost if the process crashes. Ink never sees this output.

If you want messages inside the app instead, use `useStdout().write(...)` or `useStderr().write(...)`. Ink prints those above the UI without corrupting it.

## Rule #2: Look at the actual frames

- **`render(<App />, { debug: true })`**: Ink stops erasing and prints every frame one after another. You can see exactly what was rendered and when. If your state change appears in a frame here but not in normal mode, the problem is terminal or layout, not React.
- **ink-testing-library**: This is the deterministic option. `lastFrame()` and `frames` give you rendered strings with no TTY involved, so you can reproduce the bug in a test:

  ```ts
  const { lastFrame, stdin } = render(<App />);
  stdin.write('j');
  await new Promise(r => setTimeout(r, 0));
  expect(lastFrame()).toContain('selected: 2');
  ```
- **React DevTools**: Install `react-devtools-core`, run `npx react-devtools`, then start your app with `DEV=true`. You can inspect live props, state and hooks, and the profiler shows whether a component re-rendered at all.

## Bug #2: The reducer runs but the screen doesn't change

Work down this list, using the file logger to answer each question:

1. **Does the reducer return a new reference?** Log `dbg('same?', prev === next)` at the end of the reducer. If you mutate the state (`state.items.push(x); return state;`), React compares the old and new state, sees the same object, and skips the render. This is the most common cause by far.
2. **Did the component re-render?** Put `dbg('render Foo', value)` in the body of the component that displays the value.
   - If it didn't re-render, check whether it reads state from a different source: a stale closure in `useInput` (common with `useState` plus a handler that captures an old value), a module-level variable or ref, or a `React.memo` child whose props didn't change.
3. **Is the content inside `<Static>`?** `<Static>` writes each item once and never updates it. If you change an item that has already been written, nothing changes on screen. Only content outside `<Static>` re-renders.
4. **Is it clipped by layout?** Look for a fixed `height`, `overflow="hidden"`, or a UI taller than the terminal. The `debug: true` frames will show the value missing from the output even though React rendered it.
5. **Is the event loop blocked or the process exiting?** Ink throttles its writes to the terminal. If you dispatch and then run a long synchronous loop, or call `process.exit()` or `exit()` right away, the frame may never be written. Exiting via `useApp().exit()` and `await waitUntilExit()` lets the last frame finish.
6. **Are there two React or Ink copies, or two `render()` calls?** Run `npm ls react ink`. Duplicate copies or a second Ink instance can mean your state updates go to a tree that isn't the one being shown.

Run the steps in that order (reducer reference, then render log, then `debug: true` frames) and you'll find which layer is dropping the update: the state, React's rendering, or Ink's output to the terminal.
