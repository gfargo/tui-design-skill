The two features hit SSH differently, so they need different fixes:

- **Copy:** the clipboard you want is on the user's local machine, and only their terminal emulator can reach it. So you send it an escape sequence (OSC 52) and let the terminal do the copy.
- **Open:** the file is on the remote host. So the editor should run on the remote host, inside the same terminal, not on the user's laptop.

(Your working directory is empty, so this is a general design with sketch code, written for ratatui + crossterm.)

## 1. `y` to copy: OSC 52

OSC 52 is an escape sequence that tells the terminal emulator "put this text on the system clipboard." It travels over SSH like any other output, so it works from any distance.

```rust
use base64::{engine::general_purpose::STANDARD, Engine};
use std::io::{self, Write};

fn osc52_copy(text: &str) -> io::Result<()> {
    let seq = format!("\x1b]52;c;{}\x07", STANDARD.encode(text));
    let mut out = io::stdout().lock();
    out.write_all(seq.as_bytes())?;
    out.flush()
}
```

You can write this to stdout between ratatui frames. It doesn't move the cursor or draw anything, so it won't corrupt the screen.

### The tmux catch

By default (`set-clipboard external`), tmux **drops OSC 52 sent by programs running inside it**. You have two ways around that:

1. **Ask tmux to do the copy.** On tmux 3.2+, `tmux load-buffer -w -` reads from stdin, stores it in a tmux paste buffer, and also sends OSC 52 to the outer terminal. This works with the default `external` setting, so users don't have to change their config. Recommended.
2. Tell users to add `set -g set-clipboard on`, which makes tmux forward OSC 52 from your app. Use this as the fallback for older tmux.

(Avoid the DCS passthrough wrapper `\ePtmux;…`. Since tmux 3.3 it also needs `allow-passthrough on`, so it's more config and more fragile.)

```rust
use std::process::{Command, Stdio};

pub enum CopyVia { Tmux, Osc52, Native }

pub fn copy(text: &str) -> io::Result<CopyVia> {
    if std::env::var_os("TMUX").is_some() {
        if let Ok(mut child) = Command::new("tmux")
            .args(["load-buffer", "-w", "-"])
            .stdin(Stdio::piped())
            .stdout(Stdio::null())
            .stderr(Stdio::null())
            .spawn()
        {
            child.stdin.take().unwrap().write_all(text.as_bytes())?;
            if child.wait()?.success() {
                return Ok(CopyVia::Tmux);
            }
        }
    }

    let over_ssh = std::env::var_os("SSH_TTY").is_some()
        || std::env::var_os("SSH_CONNECTION").is_some();
    if !over_ssh {
        // Local session: a native clipboard works even in terminals without OSC 52.
        if let Ok(mut cb) = arboard::Clipboard::new() {
            if cb.set_text(text).is_ok() {
                return Ok(CopyVia::Native);
            }
        }
    }

    osc52_copy(text)?;
    Ok(CopyVia::Osc52)
}
```

**Things to know:**
- **You can't tell whether OSC 52 worked.** Terminals don't report back. Always show a toast ("Copied req-8f3a… to clipboard") and print the full ID somewhere the user can select it by hand if the copy fails.
- **Terminal support is mixed.** Kitty, WezTerm, Alacritty, Ghostty, foot and Windows Terminal support it. iTerm2 supports it but makes users turn it on ("Applications in terminal may access clipboard"). VTE-based terminals like GNOME Terminal don't support it. Put a short "clipboard not working?" section in your README.
- **Nested tmux** (tmux on the laptop, SSH, tmux on the server): the outer tmux also needs `set -g set-clipboard on`.
- **Size limits:** some terminals cap OSC 52 payloads. Request IDs are tiny, so this won't matter.

## 2. Click a path to open it: catch the click yourself and run `$EDITOR` in the terminal

The terminal's own link handling (OSC 8 hyperlinks, cmd-click on paths) opens files **on the user's laptop**. Over SSH those paths don't exist there. The approach that works everywhere:

1. Turn on mouse capture.
2. Remember where you drew each path on screen.
3. On a click, pause the TUI, run the user's editor on the remote host, and restore the TUI when it exits.

This works the same locally, over SSH, and in tmux, because the editor runs where the files are.

### Track where paths are drawn

```rust
use ratatui::layout::{Position, Rect};

pub struct FileTarget { pub path: std::path::PathBuf, pub line: Option<u32> }

#[derive(Default)]
pub struct HitMap(Vec<(Rect, FileTarget)>);

impl HitMap {
    pub fn clear(&mut self) { self.0.clear() }
    pub fn push(&mut self, area: Rect, t: FileTarget) { self.0.push((area, t)) }
    pub fn at(&self, col: u16, row: u16) -> Option<&FileTarget> {
        self.0.iter().find(|(r, _)| r.contains(Position::new(col, row))).map(|(_, t)| t)
    }
}
```

Each frame, clear the map. When you render a log line, find the `path:line` matches with a regex and record the screen area each one occupies. Then handle the click:

```rust
Event::Mouse(m) if m.kind == MouseEventKind::Down(MouseButton::Left) => {
    if let Some(t) = app.hits.at(m.column, m.row) {
        open_in_editor(&mut terminal, &t.path, t.line)?;
    }
}
```

### Pause the TUI and run the editor

```rust
use crossterm::{execute, terminal::*, event::{EnableMouseCapture, DisableMouseCapture}};

fn open_in_editor(term: &mut ratatui::DefaultTerminal, path: &Path, line: Option<u32>) -> io::Result<()> {
    let editor = std::env::var("VISUAL")
        .or_else(|_| std::env::var("EDITOR"))
        .unwrap_or_else(|_| "vi".into());
    let mut words = shell_words::split(&editor).unwrap_or_else(|_| vec![editor.clone()]);
    let program = words.remove(0);

    disable_raw_mode()?;
    execute!(io::stdout(), LeaveAlternateScreen, DisableMouseCapture)?;

    let status = Command::new(&program)
        .args(&words)
        .args(line_args(&program, path, line))
        .status();

    enable_raw_mode()?;
    execute!(io::stdout(), EnterAlternateScreen, EnableMouseCapture)?;
    term.clear()?; // force a full redraw
    status.map(|_| ())
}

fn line_args(program: &str, path: &Path, line: Option<u32>) -> Vec<String> {
    let p = path.display().to_string();
    let Some(n) = line else { return vec![p] };
    let name = Path::new(program).file_name().and_then(|s| s.to_str()).unwrap_or("");
    match name {
        "code" | "code-insiders" | "cursor" => vec!["-g".into(), format!("{p}:{n}")],
        "hx" | "helix" | "subl" | "zed"     => vec![format!("{p}:{n}")],
        _ /* vi, vim, nvim, nano, emacs, micro, kak */ => vec![format!("+{n}"), p],
    }
}
```

**Details that matter:**
- **Add a keyboard shortcut too.** For example, `Enter` or `o` opens the path on the selected line. Some users won't have the mouse available, and some will turn it off (next point).
- **Mouse capture takes over normal text selection.** Users can still select text by holding Shift while dragging (Option on iTerm2). Put this in your help screen, and consider a `--no-mouse` flag.
- **Relative paths:** logs often contain paths relative to the service's working directory. Add a `--root` option (or a config setting) to resolve them against.
- **VS Code Remote-SSH users** often have `EDITOR="code --wait"`. Inside a VS Code terminal, that `code` connects back to their local VS Code window, so the same code path works for them.

### Optional extra: OSC 8 links for GUI-editor users

If some users want the file to open in their **local** GUI editor, you can also wrap paths in OSC 8 hyperlinks pointing at a URL template they configure, e.g.:

```
vscode://vscode-remote/ssh-remote+{host}{path}:{line}
```

That opens the remote file in local VS Code through Remote-SSH. Two caveats: tmux only passes these links through from 3.4+ (with `terminal-features` set to include `hyperlinks`), and ratatui's width calculations don't account for escape sequences. ratatui's `hyperlink` example shows a workaround. Treat it as an opt-in setting, not the default.
