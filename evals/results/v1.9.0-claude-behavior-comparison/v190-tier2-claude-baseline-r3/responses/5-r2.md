There's no code in the working directory, so this is a general design with snippets that assume ratatui and crossterm. Both features rely on the same idea: anything tied to the user's machine (the clipboard) goes through the terminal emulator as an escape sequence, and anything tied to the files (the editor) runs on the host where the TUI runs.

## 1. Copying with `y`: OSC 52

OSC 52 is an escape sequence that tells the terminal emulator to set the system clipboard. It travels over the same byte stream as everything else, so SSH doesn't matter. The text lands on the clipboard of the machine the user is sitting at.

```
ESC ] 52 ; c ; <base64(text)> BEL
```

**tmux is the tricky part.** By default tmux won't forward OSC 52 from applications (`set-clipboard` defaults to `external`). The most reliable approach is to let tmux handle it: `tmux load-buffer -w -` (tmux 3.2+) puts the text in a tmux buffer and sends OSC 52 to the outer terminal. tmux already knows what that terminal supports. Because tmux runs on the same host as your app, shelling out to it is fine, even over SSH.

```rust
use base64::{engine::general_purpose::STANDARD, Engine};
use std::io::{self, Write};
use std::process::{Command, Stdio};

pub enum CopyVia { Tmux, Osc52 }

pub fn copy_to_clipboard(text: &str) -> io::Result<CopyVia> {
    if std::env::var_os("TMUX").is_some() {
        // Preferred: tmux stores the buffer and forwards OSC 52 to the outer terminal itself.
        if let Ok(mut child) = Command::new("tmux")
            .args(["load-buffer", "-w", "-"])
            .stdin(Stdio::piped())
            .stdout(Stdio::null())
            .stderr(Stdio::null())
            .spawn()
        {
            child.stdin.take().unwrap().write_all(text.as_bytes())?;
            if child.wait()?.success() {
                return Ok(CopyVia::Tmux);
            }
        }
        // Older tmux: wrap OSC 52 in DCS passthrough (needs `allow-passthrough on` on 3.3+).
        let seq = format!("\x1bPtmux;\x1b\x1b]52;c;{}\x07\x1b\\", STANDARD.encode(text));
        write_raw(&seq)?;
        return Ok(CopyVia::Osc52);
    }
    write_raw(&format!("\x1b]52;c;{}\x07", STANDARD.encode(text)))?;
    Ok(CopyVia::Osc52)
}

fn write_raw(seq: &str) -> io::Result<()> {
    // Write straight to the tty, outside ratatui's buffer. This is safe to call between draws.
    let mut out = io::stdout().lock();
    out.write_all(seq.as_bytes())?;
    out.flush()
}
```

Things to tell users or put in your README:
- **Terminal support:** Works in iTerm2, kitty, WezTerm, Alacritty, Ghostty, foot, Windows Terminal and xterm (xterm needs `allowWindowOps`). iTerm2 also needs "Applications in terminal may access clipboard" turned on. Terminal.app doesn't support it, and VTE-based terminals have historically lacked it too.
- **tmux config:** If the clipboard isn't reaching the outer terminal, add `set -g set-clipboard on` and, if needed, `set -as terminal-features ',xterm-256color:clipboard'`. Even when that fails, `load-buffer` leaves the ID in a tmux buffer, so `prefix ]` still pastes it.
- **No confirmation:** OSC 52 never reports whether it worked. Show a status line like `Copied req-8f3a… (via tmux)` so users know what was attempted.
- **Optional local fallback:** When neither `SSH_TTY` nor `TMUX` is set, you can also call the `arboard` crate as a belt-and-braces step for terminals without OSC 52.

## 2. Opening a path: in-app click handling plus `$EDITOR` on the host

Over SSH the file lives on the remote host. A terminal hyperlink to `file:///var/log/...` would open on the user's laptop, where that file doesn't exist. Running `$EDITOR` from your app opens it where the file actually is, and it works the same locally, over SSH and in tmux.

**Hit-testing:** During render, record where each path appears. When the user left-clicks, look up which path is at that position:

```rust
pub struct ClickTarget { pub area: Rect, pub path: PathBuf, pub line: Option<u32> }

// In render: when you lay out a log line, compute the path span's x offset with
// unicode_width and push a ClickTarget { area: Rect::new(x, y, w, 1), .. }.
// Clear the Vec at the start of each frame.

// In the event loop:
if let Event::Mouse(MouseEvent { kind: MouseEventKind::Down(MouseButton::Left), column, row, .. }) = ev {
    if let Some(t) = app.targets.iter().find(|t| t.area.contains(Position::new(column, row))) {
        open_in_editor(terminal, &t.path, t.line)?;
    }
}
```

**Opening the editor:** Inside tmux, open the file in a new tmux window so the log view stays live. Otherwise, suspend the TUI, run the editor, then restore:

```rust
fn open_in_editor(terminal: &mut DefaultTerminal, path: &Path, line: Option<u32>) -> io::Result<()> {
    let editor = std::env::var("VISUAL")
        .or_else(|_| std::env::var("EDITOR"))
        .unwrap_or_else(|_| "vi".into());
    let line_arg = line.map(|l| format!("+{l}")).unwrap_or_default();
    // `sh -c '$EDITOR "$@"'` handles EDITOR values with flags (e.g. "nvim -R") without manual parsing.
    let script = format!("{editor} \"$@\"");
    let args: Vec<&OsStr> = [line_arg.as_ref(), path.as_os_str()]
        .into_iter()
        .filter(|a| !a.is_empty())
        .collect();

    if std::env::var_os("TMUX").is_some() {
        Command::new("tmux")
            .args(["new-window", "--", "sh", "-c", &script, "sh"])
            .args(&args)
            .status()?;
        return Ok(());
    }

    crossterm::execute!(io::stdout(), DisableMouseCapture, LeaveAlternateScreen)?;
    crossterm::terminal::disable_raw_mode()?;
    let result = Command::new("sh").args(["-c", &script, "sh"]).args(&args).status();
    crossterm::terminal::enable_raw_mode()?;
    crossterm::execute!(io::stdout(), EnterAlternateScreen, EnableMouseCapture)?;
    terminal.clear()?;
    result.map(|_| ())
}
```

The `+N` line syntax works in vim, nvim, nano and emacs. Helix wants `path:N`, so make the command template configurable, e.g. `editor_cmd = "hx {path}:{line}"`.

**Caveats:**
- **Native text selection:** Mouse capture turns off normal drag-to-select in the terminal. Users can usually hold Shift (Option in iTerm2) to bypass it, but add a key to toggle mouse capture as well.
- **Keyboard access:** Also bind `o` or Enter to "open the path on the selected line." Some users won't have a working mouse (mosh, odd terminals), and keyboard users will prefer it anyway.
- **tmux and mouse events:** tmux passes mouse events to apps that request them, so clicks should reach your app inside tmux too.

## Optional: OSC 8 hyperlinks for GUI-editor users

Some users run VS Code Remote-SSH or similar. For them, you could wrap paths in OSC 8 hyperlinks pointing at a URL built from a template they configure, e.g. `vscode://vscode-remote/ssh-remote+{host}{path}:{line}`. Then the terminal handles the click and opens their local GUI editor connected to the remote host.

Keep it opt-in, for three reasons:
- ratatui doesn't support OSC 8 natively. You'd need the cell-chunking workaround from ratatui's `hyperlink` example.
- tmux only passes OSC 8 through from 3.4, and needs `terminal-features ',*:hyperlinks'`.
- It conflicts with your own mouse capture: when the app captures the mouse, the terminal never sees the click.

## Summary

| Feature | Mechanism | Works over SSH | tmux |
|---|---|---|---|
| `y` copy | OSC 52 (or `tmux load-buffer -w`) | Yes, uses the local clipboard | Yes, via `load-buffer -w`, with passthrough as fallback |
| Click path | Mouse capture + `$EDITOR` on the host | Yes, the editor runs where the file is | Yes, opens in a new tmux window |
| (Optional) GUI editor | OSC 8 + URL template | Yes, with a remote-aware URL | Needs tmux ≥ 3.4 |
