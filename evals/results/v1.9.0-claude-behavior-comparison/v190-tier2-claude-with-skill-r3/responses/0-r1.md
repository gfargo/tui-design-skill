The good news is that Bubble Tea apps are easier to test than most TUIs. In Bubble Tea, `Update(msg)` is the only place state changes, so a test can build the model, send it a key message and check the state that comes back. Your Tab bug can be caught that way in a few milliseconds, with no terminal and no CI setup beyond `go test`.

Build three layers of tests, with most of them in the first:

| Layer | What it catches | Share of tests |
|---|---|---|
| **1. `Update` unit tests** | Broken keys, focus logic, card moves, filtering. **This layer would have caught the Tab bug.** | Most of them |
| **2. Golden files of the rendered screen** at fixed sizes | Layout breaks, missing columns, broken truncation | A handful |
| **3. One `teatest` run of the whole program** | Problems with startup, the first window-size message, and quitting | One or two |

Write layer 1 today, add layer 2 this week, and treat layer 3 as optional.

## Step 0: Check your Bubble Tea version

Look at `go.mod`. Key messages are built differently in each version:

| | v1 (`github.com/charmbracelet/bubbletea`) | v2 (`charm.land/bubbletea/v2`) |
|---|---|---|
| Tab | `tea.KeyMsg{Type: tea.KeyTab}` | `tea.KeyPressMsg{Code: tea.KeyTab}` |
| Shift+Tab | `tea.KeyMsg{Type: tea.KeyShiftTab}` | `tea.KeyPressMsg{Code: tea.KeyTab, Mod: tea.ModShift}` |
| Letter | `tea.KeyMsg{Type: tea.KeyRunes, Runes: []rune{'q'}}` | `tea.KeyPressMsg{Code: 'q', Text: "q"}` |

The examples below use v2. For v1, swap in the literals from the left column.

## Step 1: Pin down the Tab bug first

Write the test for the bug that already happened before anything else. Keep the key messages in small helpers so the tests stay readable:

```go
// model_test.go
package main

import (
	"testing"

	tea "charm.land/bubbletea/v2"
)

var (
	tab      = tea.KeyPressMsg{Code: tea.KeyTab}
	shiftTab = tea.KeyPressMsg{Code: tea.KeyTab, Mod: tea.ModShift}
)

// press runs a sequence of messages through Update and returns the final model.
func press(t *testing.T, m model, msgs ...tea.Msg) model {
	t.Helper()
	for _, msg := range msgs {
		next, _ := m.Update(msg)
		m = next.(model)
	}
	return m
}

func TestTabCyclesColumns(t *testing.T) {
	tests := []struct {
		name string
		keys []tea.Msg
		want int // focused column index
	}{
		{"tab moves right", []tea.Msg{tab}, 1},
		{"tab wraps to first", []tea.Msg{tab, tab, tab}, 0}, // 3 columns
		{"shift+tab wraps to last", []tea.Msg{shiftTab}, 2},
		{"tab then shift+tab returns", []tea.Msg{tab, shiftTab}, 0},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			m := press(t, newTestModel(), tt.keys...)
			if m.focused != tt.want {
				t.Errorf("focused = %d, want %d", m.focused, tt.want)
			}
		})
	}
}
```

Replace `m.focused` with your own field name. `newTestModel()` should build a model with fixed fake data: three columns and a few cards, with no disk or network access.

**Then test Tab in every focus state.** Refactors usually break a key like Tab in one of two ways:

- **A child component swallows it.** The key gets forwarded to a `textinput` or `list` before your Tab case runs.
- **A global key fires when it shouldn't.** For example, `q` quits while someone is typing a card title.

So add cases like:

```go
func TestTabWhileEditingDoesNotSwitchColumns(t *testing.T) {
	m := newTestModel()
	m = press(t, m, tea.KeyPressMsg{Code: 'n', Text: "n"}) // open "new card" input
	m = press(t, m, tab)
	if m.focused != 0 {
		t.Errorf("tab leaked out of the text input: focused = %d", m.focused)
	}
}
```

Write the same kind of test for card moves, delete with confirmation, filter and Esc. Those are the 5–8 actions your team uses every day, and each test is a few lines. **Every bug that reaches users should get a test like this before it's fixed.**

**Checking commands:** `Update` also returns a `tea.Cmd`. Call it and check the message it returns. For example, `q` should return a command whose message is a `tea.QuitMsg`.

**If `Update` is hard to test,** that tells you what to refactor first. The usual causes are:
- package-level globals
- file or network I/O done directly inside `Update` (move it into a `tea.Cmd`)
- the store being created inside the model

Fix that with one small, behavior-preserving change, then write the tests.

## Step 2: Golden files for the screen

A golden file is a saved copy of the screen output. The test fails when the output changes, and a flag rewrites the file when the change was intended. Snapshot the board at the sizes people actually use: **80×24, 60×24** (a split tmux pane) and **your smallest supported size**, where the app should show a clear "terminal too small" message.

```go
import "github.com/charmbracelet/x/exp/golden"
import "github.com/charmbracelet/x/ansi"

func TestView(t *testing.T) {
	for _, sz := range []struct{ w, h int }{{80, 24}, {60, 24}, {40, 12}} {
		t.Run(fmt.Sprintf("%dx%d", sz.w, sz.h), func(t *testing.T) {
			m := press(t, newTestModel(), tea.WindowSizeMsg{Width: sz.w, Height: sz.h})
			out := ansi.Strip(m.render()) // layout only; colors are noise here
			golden.RequireEqual(t, []byte(out))
		})
	}
}
```

- **Make output deterministic.** The most common cause of flaky goldens is color detection: the escape codes change with `TERM`, `COLORTERM` and `NO_COLOR`. Either strip ANSI codes as above, or pin the color profile:
  - v2: `tea.WithColorProfile(colorprofile.ASCII)`
  - v1: `lipgloss.SetColorProfile(termenv.Ascii)`
- **Pull the frame into a helper.** Having `View()` call a `render() string` helper keeps the frame easy to test in either version.
- **Freeze time.** Use fake timestamps in the test data, or "updated 3m ago" will change on every run.
- **Updating goldens:** run `go test ./... -update`, and **look at the diff in code review**. That diff is where layout changes get caught.
- **Add `*.golden -text` to `.gitattributes`** so git doesn't rewrite line endings in them.

## Step 3 (optional): One full-program smoke test

`teatest` runs the real program against in-memory buffers, so it needs no terminal and works in plain CI containers. Import paths:
- v2: `github.com/charmbracelet/x/exp/teatest/v2`
- v1: `github.com/charmbracelet/x/exp/teatest`

Write one test that starts the app, waits for the board to appear, presses Tab, then quits:

```go
tm := teatest.NewTestModel(t, newTestModel(), teatest.WithInitialTermSize(80, 24))
teatest.WaitFor(t, tm.Output(), func(b []byte) bool {
	return bytes.Contains(b, []byte("Done")) // a column title
}, teatest.WithDuration(5*time.Second))
tm.Send(tab)
tm.Send(tea.KeyPressMsg{Code: 'q', Text: "q"})
tm.WaitFinished(t, teatest.WithFinalTimeout(2*time.Second)) // always set this; it hangs forever without it
```

Keep it to one or two of these. They're slower and more fragile than layer 1, and they only add coverage of how the program starts up and shuts down.

## CI

```yaml
# .github/workflows/test.yml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version-file: go.mod }
      - run: go test -race ./...
```

`-race` matters here because `tea.Cmd`s run in goroutines. Make the check required on your main branch so a broken Tab key can't be merged.
