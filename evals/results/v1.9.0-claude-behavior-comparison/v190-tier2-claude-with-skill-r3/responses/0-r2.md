You don't need a terminal to test most of a Bubble Tea app. `Update` is a function: it takes a model and a message and returns a new model. So most of your tests can be ordinary `go test` cases that send a fake keypress and check the resulting state. No PTY, no screen scraping, and they run in any CI container.

I couldn't see your code (there's no Go source in this workspace), so the examples below use placeholder names. The plan is the same for any Bubble Tea app.

## The three layers, cheapest first

**1. Unit tests on `Update` (most of your tests).** Build a model with fixed data, send key messages, and check state. This is the test that would have caught the Tab bug within seconds:

```go
// keys_test.go
func press(m tea.Model, msgs ...tea.Msg) model {
	for _, msg := range msgs {
		m, _ = m.Update(msg)
	}
	return m.(model)
}

var (
	// Bubble Tea v2 (charm.land/bubbletea/v2):
	tab      = tea.KeyPressMsg{Code: tea.KeyTab}
	shiftTab = tea.KeyPressMsg{Code: tea.KeyTab, Mod: tea.ModShift}
	// Bubble Tea v1 (github.com/charmbracelet/bubbletea):
	// tab      = tea.KeyMsg{Type: tea.KeyTab}
	// shiftTab = tea.KeyMsg{Type: tea.KeyShiftTab}
)

func TestTabCyclesColumns(t *testing.T) {
	m := newTestModel() // 3 columns: Todo, Doing, Done; fixture cards, no disk I/O

	tests := []struct {
		name string
		keys []tea.Msg
		want int
	}{
		{"starts on first", nil, 0},
		{"tab moves right", []tea.Msg{tab}, 1},
		{"tab wraps", []tea.Msg{tab, tab, tab}, 0},
		{"shift+tab wraps left", []tea.Msg{shiftTab}, 2},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := press(m, tt.keys...).focusedCol; got != tt.want {
				t.Fatalf("focused column = %d, want %d", got, tt.want)
			}
		})
	}
}
```

Send messages through the **top-level** model's `Update`, not a column's handler. Regressions like yours usually happen in the routing: a child component (a `textinput`, a `list`, a new modal) starts handling Tab before your switch sees it. A test on the inner handler would still pass while the app is broken.

Write one table like this for each of your 5–8 most-used actions: move card, open, edit, delete, filter, quit. Also add a test that loops over every binding your help view lists and checks that each one changes state. That way the help text can't silently drift from what the app actually does.

**2. Golden-file tests on `View` (a handful).** Render the screen at fixed sizes and compare it to a saved snapshot. This catches layout breakage: a column that vanishes at 60 columns, truncation bugs, a border that wraps.

```go
func TestView(t *testing.T) {
	for _, sz := range []struct{ w, h int }{{80, 24}, {60, 24}, {120, 40}} {
		t.Run(fmt.Sprintf("%dx%d", sz.w, sz.h), func(t *testing.T) {
			m := press(newTestModel(), tea.WindowSizeMsg{Width: sz.w, Height: sz.h})
			out := ansi.Strip(render(m)) // github.com/charmbracelet/x/ansi
			golden.RequireEqual(t, []byte(out)) // github.com/charmbracelet/x/exp/golden
		})
	}
}
```

- `render(m)` is a small helper you write. On v1 it just returns `m.View()`. On v2, `View()` returns a `tea.View` value, so the helper pulls out its text content.
- Golden files go in `testdata/TestView/80x24.golden`. After an intentional UI change, regenerate them with `go test ./... -update`, then review the diff in the PR. That diff shows reviewers what the change did to the screen.
- Stripping ANSI keeps the snapshots stable. Color escape codes change with `TERM`, `COLORTERM` and `NO_COLOR`, and that's the most common reason snapshot tests flake in CI. If you want snapshots that include color, pin the color profile instead.
- Add `*.golden -text` to `.gitattributes` so git doesn't rewrite line endings in them.
- Include one golden for an empty board and one for a column with a very long card title.

**3. teatest (one or two flows, optional).** `teatest` runs the whole program against in-memory buffers, still without a PTY. For v2 the import is `github.com/charmbracelet/x/exp/teatest/v2`; plain `x/exp/teatest` is the v1 version. Use it for a "start, Tab twice, move a card, quit cleanly" smoke test, mainly to check that `Init` commands and quitting work. Two gotchas:
- Always pass `teatest.WithFinalTimeout(...)`. Without it, `FinalModel`, `FinalOutput` and `WaitFinished` block forever.
- Raise the `WaitFor` duration to about 5 seconds; the 1-second default is tight for CI.

Don't make this layer the main suite. It's slower and more fragile than layer 1.

## Small refactors that make this possible

- **Add a `newTestModel()` constructor** that takes fixture data instead of reading from your storage. If `Update` currently reads or writes disk directly, move that into a `tea.Cmd`. Then tests can check the returned command or call it, and the UI stops blocking on I/O as a bonus.
- **Add accessors if the state is hard to read.** If "which column is focused" is buried in component internals, a `func (m model) FocusedColumn() int` costs nothing.
- **Testing commands:** `Update` also returns a command. Call it and check the message it produces, for example that `q` produces `tea.QuitMsg`. `tea.BatchMsg` is a `[]tea.Cmd` you can unpack and run.

## CI

```yaml
# .github/workflows/test.yml
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version-file: go.mod }
      - run: go test -race ./...
```

Nothing terminal-specific is needed. Make it a required check on the branch so a refactor can't merge with a failing test.
