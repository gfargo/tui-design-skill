You test a Bubble Tea app the same way you test any other Go code: call functions and check the results. In Bubble Tea, `Update(msg)` is the only place state changes, and it just takes a message and returns a new model. A test can send it a fake Tab keypress and check which column has focus. That needs no terminal and no PTY, and it runs in milliseconds on any CI runner.

Start with that one test, then build out in three layers, with most tests at the bottom.

## Step 1: Write the test that would have caught last week's bug

I haven't seen your code, so the field names below (`focused`, `columns`, `newModel`) are guesses. Rename them to match yours. The examples use Bubble Tea v2; v1 differences are noted after the code.

```go
// model_test.go
package main

import (
    "testing"

    tea "charm.land/bubbletea/v2"
)

var (
    tab      = tea.KeyPressMsg{Code: tea.KeyTab}
    shiftTab = tea.KeyPressMsg{Code: tea.KeyTab, Mod: tea.ModShift}
)

// press feeds keys through Update and returns the resulting model.
func press(t *testing.T, m model, keys ...tea.KeyPressMsg) model {
    t.Helper()
    for _, k := range keys {
        next, _ := m.Update(k)
        m = next.(model)
    }
    return m
}

func TestTabCyclesColumns(t *testing.T) {
    m := newTestModel() // fixture board: e.g. Todo / Doing / Done, a few cards each
    n := len(m.columns)

    for i := 1; i <= n; i++ {
        m = press(t, m, tab)
        if want := i % n; m.focused != want {
            t.Fatalf("after %d tabs: focused=%d, want %d", i, m.focused, want)
        }
    }
}

func TestShiftTabWrapsBackward(t *testing.T) {
    m := press(t, newTestModel(), shiftTab)
    if want := len(m.columns) - 1; m.focused != want {
        t.Fatalf("shift+tab from first column: focused=%d, want %d", m.focused, want)
    }
}
```

**On v1:** keys are `tea.KeyMsg{Type: tea.KeyTab}` and `tea.KeyMsg{Type: tea.KeyShiftTab}`, and the import is `github.com/charmbracelet/bubbletea`.

Two common ways Tab "silently stops working" after a refactor, both of which this test catches:

- **A value receiver.** A helper like `func (m model) focusNext()` changes a copy of the model, so the change is thrown away. It compiles and doesn't crash; it just does nothing.
- **Another component takes the key first.** A text input, list filter or new modal handles Tab before your column logic sees it.

Once the helper exists, a table of "keys in, expected state out" cases is cheap to extend. Cover every binding your team uses daily:

```go
func TestKeys(t *testing.T) {
    tests := []struct {
        name  string
        keys  []tea.KeyPressMsg
        check func(t *testing.T, m model)
    }{
        {"tab moves focus", []tea.KeyPressMsg{tab}, func(t *testing.T, m model) {
            if m.focused != 1 { t.Errorf("focused=%d", m.focused) }
        }},
        {"j moves cursor down", []tea.KeyPressMsg{{Code: 'j', Text: "j"}}, func(t *testing.T, m model) {
            if m.cursor() != 1 { t.Errorf("cursor=%d", m.cursor()) }
        }},
        // move card right, delete card, open edit, Esc closes modal, …
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) { tt.check(t, press(t, newTestModel(), tt.keys...)) })
    }
}
```

**Testing commands:** if `Update` returns a `tea.Cmd`, call it and check the message it produces. For example, `q` should produce `tea.QuitMsg`. A `tea.BatchMsg` is a plain slice of Cmds that you can unpack and run one by one.

This layer should hold most of your tests: focus, navigation, moving cards, and the add/edit/delete operations on the board. If moving a card currently lives inside `Update`, move it into a plain function like `func (b *Board) Move(card, toCol int) error` and test that directly. This is the one refactor worth doing first, because it makes every later refactor safer.

## Step 2: Golden tests for what the screen shows

State tests miss bugs where the state is right but the screen is wrong, such as the focus highlight no longer being drawn. Golden tests cover that. You render `View()` at a fixed terminal size and compare it to a committed file (`testdata/*.golden`). `github.com/charmbracelet/x/exp/golden` handles the comparison. Charm's own v2 app, crush, tests this way rather than with a full harness.

```go
func TestView(t *testing.T) {
    for _, sz := range []struct{ w, h int }{{80, 24}, {60, 24}, {40, 12}} {
        t.Run(fmt.Sprintf("%dx%d", sz.w, sz.h), func(t *testing.T) {
            m := newTestModel()
            next, _ := m.Update(tea.WindowSizeMsg{Width: sz.w, Height: sz.h})
            m = press(t, next.(model), tab) // focus column 2 so the highlight is in the snapshot
            golden.RequireEqual(t, []byte(m.View().Content)) // v1: m.View()
        })
    }
}
```

- **Sizes:** check 80×24, a 60-column tmux split, and your declared minimum (40×12 above is a placeholder). A three-column kanban board is where layout breaks. If you don't yet know what your board does at 60 columns, these snapshots will show you.
- **Color profile:** most flaky golden tests come from color detection. Output changes with `TERM`, `COLORTERM` and `NO_COLOR`, so CI and laptops produce different snapshots. Force plain ASCII output in tests: on v1 call `lipgloss.SetColorProfile(termenv.Ascii)` in `TestMain`; on v2 use the program option `tea.WithColorProfile(colorprofile.ASCII)` in the harness tests below. As a bonus, an ASCII snapshot still has to show focus without color, through a marker, border change or bold text. That's an accessibility check you get for free.
- **Updating snapshots:** run `go test ./... -update`, and **read the diff in review**. That review step is the point of the whole layer.
- **`.gitattributes`:** add `*.golden -text` so git never rewrites line endings in the snapshot files.

## Step 3: One or two end-to-end tests with `teatest`

`teatest` runs your real program, including `Init`, command handling and real message ordering, against in-memory buffers. It doesn't use a PTY, so it works on plain CI containers. Use it for one or two smoke tests, not as the main suite: these tests are slower and the most likely to flake.

```go
// v2: github.com/charmbracelet/x/exp/teatest/v2   (v1: github.com/charmbracelet/x/exp/teatest)
func TestSmoke(t *testing.T) {
    tm := teatest.NewTestModel(t, newTestModel(),
        teatest.WithInitialTermSize(80, 24),
        teatest.WithProgramOptions(tea.WithColorProfile(colorprofile.ASCII)),
    )
    teatest.WaitFor(t, tm.Output(), func(b []byte) bool {
        return bytes.Contains(b, []byte("Todo"))
    }, teatest.WithDuration(5*time.Second)) // the default 1s timeout is too tight for CI
    tm.Send(tea.KeyPressMsg{Code: tea.KeyTab})
    tm.Send(tea.KeyPressMsg{Code: 'q', Text: "q"})
    tm.WaitFinished(t, teatest.WithFinalTimeout(2*time.Second))
    if m := tm.FinalModel(t, teatest.WithFinalTimeout(2*time.Second)).(model); m.focused != 1 {
        t.Fatalf("focused=%d", m.focused)
    }
}
```

**Always pass `WithFinalTimeout`.** Without it, `WaitFinished`, `FinalModel` and `FinalOutput` wait forever if the app doesn't quit, and the CI job hangs instead of failing.

## Step 4: CI

```yaml
# .github/workflows/test.yml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version-file: go.mod }
      - run: go test -race ./...
```

Run with `-race` because command goroutines and timers in a TUI often have data races that never show up in normal use.
