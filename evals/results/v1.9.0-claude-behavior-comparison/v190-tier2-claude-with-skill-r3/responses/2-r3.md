You can't fix this reliably until you know the exact size that triggers it, so the first goal is to capture that size. That means getting diagnostics off the screen your app is drawing on.

## Why the panel can overlap at all

The areas returned by a single Ratatui `Layout` split never overlap. The one exception is if you asked for overlap with negative spacing (`.spacing(-1)` / `Spacing::Overlap`). So if a panel's bottom border lands on the footer row, one of these is probably happening:

1. **The panel's `Rect` doesn't come from the same split as the footer.** Common causes are hand-built `Rect::new(..)` math, or a terminal size you saved from `Event::Resize` instead of reading `frame.area()`. A saved size is the most likely cause of a bug that only shows up after some resizes. Resize events can arrive in bursts or out of step with your draws, and `frame.area()` is the only size that's correct for the current frame.
2. **A custom widget draws outside its `area`.** `Rect::bottom()` is *exclusive* (`y + height`), so the last row is `bottom() - 1`. The buffer only clips to the screen, not to your `Rect`.
3. **Negative spacing or `Spacing::Overlap`** somewhere in the layout chain.
4. **Content-sized constraints** (such as `Length(items.len() + 2)`) feeding rect math you do yourself after the split.

Drawing the footer last would hide the symptom without fixing the bad rect, so don't do that.

## (a) Debugging without corrupting the screen

`println!` breaks in raw mode and on the alternate screen, so write logs to a file and watch it from a second terminal:

```rust
use std::{fs::File, sync::Mutex};
use tracing_subscriber::EnvFilter;

fn init_tracing() -> color_eyre::Result<()> {
    let file = File::create("app.log")?;
    tracing_subscriber::fmt()
        .with_writer(Mutex::new(file))
        .with_ansi(false)
        .with_env_filter(EnvFilter::from_default_env())
        .init();
    Ok(())
}
```

```sh
RUST_LOG=debug cargo run      # terminal 1
tail -f app.log               # terminal 2
```

Then log every rect on every draw, and log resize events alongside them:

```rust
fn draw(&self, frame: &mut Frame) {
    let area = frame.area();
    let l = compute_layout(area);
    tracing::debug!(?area, ?l.panels, ?l.footer, "layout");
    debug_assert!(
        !l.panels.iter().any(|p| p.intersects(l.footer)),
        "panel overlaps footer at {area:?}: {l:?}",
    );
    // ... render
}

// in the event handler
Event::Resize(w, h) => tracing::debug!(w, h, "resize event"),
```

The `debug_assert!` makes the bug fail loudly. Ratatui's panic hook (installed by `ratatui::run()` / `init()`) restores the terminal before the panic message prints. So in a debug build, the first bad frame leaves you with a normal shell and a message containing the exact size that failed. Compare the `resize event` lines with the `area` lines in the log: if they disagree, you have a saved size somewhere (cause 1).

Other options:
- **`tui-logger`** gives you an in-app log pane.
- **A debug pane** toggled by a `show_debug` flag can render `format!("{layout:#?}")` beside the UI.
- **A debugger** should be attached from a *second* terminal (`lldb -p <pid>`). If you stop the process in its own terminal, that terminal is still in raw mode on the alternate screen.

## (b) Regression tests that keep it fixed

### 1. Pull the layout out into a pure function and check it at every size

Overlap is a property of the layout, not of rendering, so test it with no terminal at all. A full sweep over every width and height takes milliseconds and covers far more than a few chosen sizes:

```rust
#[derive(Debug)]
pub struct AppLayout { pub header: Rect, pub panels: [Rect; 2], pub footer: Rect }

pub fn compute_layout(area: Rect) -> AppLayout { /* the only place rects are made */ }

#[test]
fn layout_regions_never_overlap_at_any_size() {
    for w in MIN_W..=250 {
        for h in MIN_H..=80 {
            let area = Rect::new(0, 0, w, h);
            let l = compute_layout(area);
            let regions = [("header", l.header), ("left", l.panels[0]),
                           ("right", l.panels[1]), ("footer", l.footer)];

            for (name, r) in regions {
                assert_eq!(r.intersection(area), r, "{name} escapes {w}x{h}: {l:?}");
            }
            for (i, (a_name, a)) in regions.iter().enumerate() {
                for (b_name, b) in &regions[i + 1..] {
                    if a.is_empty() || b.is_empty() { continue; }
                    assert!(!a.intersects(*b), "{a_name} overlaps {b_name} at {w}x{h}: {l:?}");
                }
            }
            assert_eq!(l.footer.bottom(), area.bottom(), "footer not pinned at {w}x{h}");
        }
    }
}
```

Below `MIN_W`×`MIN_H`, draw a "terminal too small" message rather than a squeezed layout, and test that state too.

### 2. Replay a resize sequence through the real draw path

Test 1 can't catch causes 1 and 2: a saved size, or a widget drawing outside its rect. For those, drive the app through `TestBackend` with a sequence of sizes that shrinks and grows. Send the app the same `Resize` events it gets in real use, because the bug may be in your resize handler:

```rust
#[test]
fn footer_row_survives_resize_sequence() {
    let mut app = App::fixture();
    let mut terminal = Terminal::new(TestBackend::new(80, 24)).unwrap();

    for (w, h) in [(80, 24), (60, 24), (80, 23), (120, 40), (60, 17), (81, 25), (80, 24)] {
        terminal.backend_mut().resize(w, h);
        app.handle(Event::Resize(w, h));
        terminal.draw(|f| app.draw(f)).unwrap();

        let buf = terminal.backend().buffer();
        let footer: String = (0..w).map(|x| buf[(x, h - 1)].symbol()).collect();
        assert!(!footer.contains(['└', '┘', '─']), "border in footer at {w}x{h}: {footer:?}");
        assert!(footer.starts_with(" q quit"), "footer missing at {w}x{h}: {footer:?}");
    }
}
```

Add the failing size from your log to that list as a named case. Odd heights are common culprits because of rounding in `Percentage`/`Ratio`.

### 3. Check that custom widgets stay inside their area

If any panel is a custom widget, fill a larger buffer with a marker character, render the widget into a smaller area inside it, and check that nothing outside the area changed:

```rust
#[test]
fn panel_widget_stays_inside_its_area() {
    let outer = Rect::new(0, 0, 40, 12);
    let inner = Rect::new(2, 2, 30, 6);
    let mut buf = Buffer::filled(outer, Cell::new("X"));
    MyPanel::fixture().render(inner, &mut buf);

    for y in outer.top()..outer.bottom() {
        for x in outer.left()..outer.right() {
            if !inner.contains(Position::new(x, y)) {
                assert_eq!(buf[(x, y)].symbol(), "X", "wrote outside area at ({x},{y})");
            }
        }
    }
}
```

### 4. Snapshots at fixed sizes

Add `insta::assert_snapshot!(format!("app_{w}x{h}"), terminal.backend())` at 80×24, 60×24, your minimum, and the size that failed, and review changes with `cargo insta review`. Snapshots record text only, not styles. That's enough to catch a border on the footer row.

Tests 1 and 2 are the ones that prevent a repeat. Test 1 checks the layout itself, and test 2 checks that what you draw actually uses that layout. Whichever test fails first also shows you which of the four causes you have.
