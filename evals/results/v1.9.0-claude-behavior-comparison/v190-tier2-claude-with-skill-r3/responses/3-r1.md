You can work through both symptoms in order. Each step either rules out a cause or points to it.

## 1. Garbled `console.log` output

Ink patches `console.*` by default (`patchConsole: true`). Each patched call is printed above the live UI and then the UI is repainted. A plain `console.log` therefore should **not** garble anything. If output interleaves or tears, some write skipped the patch and went straight to the terminal. Ink doesn't know those extra lines exist, so its next in-place redraw erases or overwrites the wrong lines.

Look for these, most likely first:

- **Direct `process.stdout.write` / `process.stderr.write`** in your code or a dependency. Logging libraries often write to the stream directly instead of calling `console`.
- **A logger that saved `console.log` before `render()` ran**, e.g. `const log = console.log` at module load. It keeps the unpatched original.
- **Child processes with `stdio: 'inherit'`**, which write straight to your TTY. Capture their output with `spawn`/`execFile` and pipe it into state or `<Static>`. For an interactive child, use `suspendTerminal`.
- **`ora` or other spinners/prompts** running next to Ink. Use Ink's own spinner instead.
- **`patchConsole: false`** set somewhere in your render options.

**Workflow:** don't debug into the screen Ink owns. Send traces to a file and watch it in a second pane:

```ts
// debug-log.ts
import {createWriteStream} from 'node:fs';
import {format} from 'node:util';

const out = process.env.DEBUG_LOG ? createWriteStream(process.env.DEBUG_LOG, {flags: 'a'}) : null;
export const dbg = (...args: unknown[]) => out?.write(`${new Date().toISOString()} ${format(...args)}\n`);
```

```sh
# pane 1
tail -f /tmp/app.log
# pane 2
DEBUG_LOG=/tmp/app.log node dist/cli.js
```

That fixes the garbling straight away. To find what's bypassing the patch, grep for `stdout.write`, `stderr.write`, `stdio: 'inherit'`, and any saved `console.log` references.

## 2. The reducer runs but the screen never changes

Split the problem in two: **is the component re-rendering?** If yes, **is the frame Ink renders the one you expect?**

**Step A: does the component re-render?** Put `dbg('List render', state.version)` at the top of the component that should change. If the reducer log fires and the render log doesn't, the bug is on the React side:

- **The reducer mutated state and returned the same reference.** React sees `Object.is(prev, next)` and skips the render. This is the most common cause. Log `dbg(prev === next)` inside the reducer.
- **The component is inside `<Static>`.** Static items render once and never re-render. Live, changing content must stay outside `<Static>`.
- **A `memo`'d child gets props that didn't change**, or a zustand selector reads a field that didn't change.
- **The dispatch went to a different instance**: `render()` called twice, a duplicated module or store, or a second Context provider.

To check props and state without guessing, run with React DevTools. Install `react-devtools-core`, run `DEV=true node dist/cli.js`, and in another terminal run `npx react-devtools`. This only inspects the tree and props; it can't profile.

**Step B: it re-renders, but the frame looks wrong.** Render with `render(<App />, {debug: true})`. Each update is appended as its own frame instead of redrawn in place, so you can find the exact update where the output differs from what you expect. Typical causes:

- **The text is clipped.** A fixed `height`, `overflow="hidden"`, or `wrap="truncate-*"` hides the changed part, or a virtualized slice doesn't include the updated row.
- **A stray direct write from section 1** made Ink lose track of the screen, so the correct frame was painted in the wrong place and then overwritten. Fix the garbling first; it can cause this symptom too.

## 3. Lock it in with a test

Once you know the cause, reproduce it without a real terminal using ink-testing-library:

```tsx
import {render} from 'ink-testing-library';
const tick = () => new Promise(r => setTimeout(r, 0));

const {lastFrame, frames, stdin} = render(<App />);
stdin.write('j');          // or trigger the action that dispatches
await tick();              // input and re-render are async; always await
expect(lastFrame()).toContain('updated value');
// `frames` holds every rendered frame, the test-side equivalent of debug: true
```

If the test passes but the real terminal still looks wrong, the bug is in terminal output, i.e. a bypassing write. If the test fails too, it's in your state or render logic, and you can fix it without running the app.

**In short:** traces go to a file, never stdout. Check render count before frame content. Use `debug: true` to see frames, DevTools to see props and state, and an ink-testing-library test to keep the fix from regressing.
