Both symptoms come down to one question: where did the chain break? Ink's pipeline is: something writes, or state changes → a component re-renders → Ink produces a frame → the frame shows up in the visible area. You can check each step on its own instead of guessing.

## Step 0: Log to a file and record every frame

```ts
// debug-log.ts
import {appendFileSync} from 'node:fs';
export const dlog = (...a: unknown[]) =>
  process.env.DEBUG_LOG && appendFileSync(process.env.DEBUG_LOG, a.map(String).join(' ') + '\n');
```

```sh
DEBUG_LOG=/tmp/app.log node dist/cli.js      # pane 1
tail -f /tmp/app.log                          # pane 2
```

```ts
render(<App />, {debug: process.env.INK_DEBUG === '1'});
```

- **The file log** keeps your tracing off the screen Ink controls. That removes the "is my debugging causing the bug?" problem.
- **`debug: true`** makes Ink append every frame as separate output instead of redrawing in place. You can scroll back and see which frame went wrong, or whether a frame was produced at all.

## Problem 1: console.log garbles the UI

Ink patches `console.*` by default (`patchConsole: true`). It prints each log line above the live area and then redraws. So `console.log` should not corrupt anything. If output garbles, something is writing to the terminal without going through Ink. Look for these:

| Cause | How to spot it | Fix |
|---|---|---|
| `process.stdout.write` / `process.stderr.write` called directly (by you or a dependency) | grep for `stdout.write` | Use `useStdout().write()` / `useStderr().write()`, or the file log |
| A child process with `stdio: 'inherit'` | grep `spawn`/`exec` options | Pipe the output and render it (e.g. through `<Static>`), or run the child inside `useApp().suspendTerminal(...)` (Ink 7.1+) |
| A second terminal-drawing library (ora, cli-progress, Inquirer, a second `render()` call) | grep imports | Use only Ink inside Ink, e.g. `<Spinner>` from `@inkjs/ui` |
| Logs written before `render()` or after unmount | logs appear at startup or exit | Print after `await waitUntilExit()` |
| `patchConsole: false` set somewhere | check the render options | Remove it |
| Running under `nodemon` | arrow keys also misbehave | `node --watch` or `nodemon --no-stdin` |

Even when nothing bypasses the patch, a lot of `console.log` calls is still costly: each call redraws the live area. Use the file log for frequent tracing.

## Problem 2: The reducer runs but the screen never changes

Add one log line at each step. The first step where the log stops tells you the cause.

**1. Does the reducer return a new reference?**
```ts
const next = reducer(state, action);
dlog('changed?', next !== state);
```
If you mutate the existing object (`state.items.push(x); return state;`), React sees the same reference and skips the re-render. This is the most common cause. The same applies to a Zustand selector that returns a mutated object.

**2. Does the component that displays the value re-render?**
```ts
dlog('render <Panel>', value);   // top of the component body
```
If it doesn't log:
- **Different instance:** you're dispatching to one store or provider and reading from another. Check for two `<Provider>`s, a store created inside a component, or two `render()` calls.
- **`React.memo` with stale props:** it's comparing a reference that never changes.
- **Not mounted:** a conditional branch or route is rendering something else.

**3. Does Ink produce a frame?**
Run with `INK_DEBUG=1`. If the component re-renders but no new frame appears, check whether a synchronous call (`execSync`, `readFileSync`, a CPU-heavy loop) runs right after the dispatch. That blocks the event loop, so Ink can't paint until it finishes. Switch to async APIs or a worker.

**4. The frame is produced but you can't see the change.** It's being drawn somewhere hidden:
- **Inside `<Static>`:** items there render once and never update. Only append-only content belongs in it.
- **Clipped:** `overflow="hidden"`, a fixed `height`, `display="none"`, or `wrap="truncate-end"` cutting off the changed text.
- **Outside the visible slice** of a virtualized list (`items.slice(top, top + height)`), or outside a `contentOffsetY` window.
- **In the alternate screen:** `alternateScreen: true` discards anything written during teardown.

## Step 5: Turn the fix into a test

When you find the bug, write a test that would have caught it, using ink-testing-library:

```tsx
const {lastFrame, frames, stdin} = render(<App />);
stdin.write('\u001B[A');
await new Promise(r => setTimeout(r, 0));   // frames update asynchronously
expect(lastFrame()).toContain('Counter: 1');
// frames.length tells you whether a new frame was produced at all
```

Also add a reducer unit test that checks `next !== prev`. It runs without a terminal and catches the mutation bug from step 1.

**Short version:** the file log plus `debug: true` show you where the chain breaks. If you're seeing garbled output, something wrote to the terminal without going through Ink. If the state never shows up, it's usually a mutated object, a store mix-up, or something hidden by `<Static>` or clipping.
