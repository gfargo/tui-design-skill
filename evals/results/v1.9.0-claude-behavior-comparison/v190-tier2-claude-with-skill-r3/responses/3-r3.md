Ink's console handling explains the first problem, and the second one usually comes down to a single question you can check directly.

## Problem 1: garbled `console.log` output

**`console.log` itself is almost never the problem.** Ink's `patchConsole` option is on by default. Ink catches `console.*` calls, prints the message above the live UI, and redraws. So when output garbles, **something is writing to the terminal without going through Ink**. Look for these, roughly from most to least common:

1. **Direct `process.stdout.write` / `process.stderr.write`** in your code or in a library (loggers like pino or winston with a stdout transport, `ora`, progress bars, `debug`).
2. **Child processes with `stdio: 'inherit'`** (or `execa` with inherited output). The child writes straight to the TTY while Ink is drawing. Capture its output and render it, or hand the terminal over with `suspendTerminal` if the child is interactive.
3. **Writes from outside Ink's patched console**: a worker thread, a second `render()` call, or a log line after unmount (before `waitUntilExit()` resolves).
4. **`patchConsole: false`** set somewhere, or a framework like Pastel calling `render()` for you with options you didn't choose.

**Fix: send debug output somewhere Ink doesn't own.** A tiny file logger is the most reliable:

```ts
// debug.ts
import {appendFileSync} from 'node:fs';
const path = process.env.DEBUG_LOG;
export const dbg = (...args: unknown[]) => {
  if (path) appendFileSync(path, `${new Date().toISOString()} ${args.map(a =>
    typeof a === 'string' ? a : JSON.stringify(a)).join(' ')}\n`);
};
```

```sh
DEBUG_LOG=/tmp/app.log node dist/cli.js   # pane 1
tail -f /tmp/app.log                       # pane 2
```

The synchronous append is fine for debugging and keeps lines in order. Don't leave it in hot paths in production. For an occasional line *inside* the UI, use `useStderr().write()` or `<Static>`; both go through Ink. Never use raw `process.stdout.write`, since Ink owns stdout.

## Problem 2: the reducer runs but the screen doesn't change

First, answer one question: **did Ink produce a frame with the new value?**

```tsx
render(<App />, {debug: true});
```

With `debug: true`, Ink prints every frame below the previous one instead of redrawing in place. Run the action and read the frames.

### A: no frame shows the new value (a React/state problem)

React decided nothing changed, or the component isn't subscribed to the state that changed. Check these in order:

- **Mutation.** `state.items.push(x); return state;` returns the same reference, so React skips the render. The reducer "runs" and nothing happens. Return new objects. A unit test can catch this: `expect(next).not.toBe(prev)`.
- **Wrong subscription.** A Zustand selector picks a different slice than the one that changed, or you have two store instances (for example, a store created inside a component, or imported through two different module paths).
- **Stale closure.** A `setInterval`, emitter listener or `useEffect` callback captured old state and dispatches based on it. Use functional updates (`setX(x => ...)`) or read from the store when the callback runs.
- **Blocked event loop.** `execSync`, `readFileSync` on a big file or a CPU-heavy loop means the update lands but nothing paints until the call returns. Your file log's timestamps will show this.

**React DevTools** answers most of these quickly. Install `react-devtools-core`, run the app with `DEV=true`, then run `npx react-devtools` separately and check the component's props and state after the dispatch. It shows the tree and props only; it doesn't profile.

### B: a frame has the new value but you can't see it (a rendering/layout problem)

- **It's inside `<Static>`.** Static items render once and never update. This is the most common Ink-specific cause. Anything that changes must live outside `<Static>`.
- **It's clipped.** A fixed `height` or `overflow="hidden"` hides the new rows, a `contentOffsetY` is wrong, or a `display="none"` branch is active.
- **The live area is taller than the terminal.** In inline mode, Ink can't redraw lines that have already scrolled off. Make the window bigger, or use `alternateScreen: true` for full-screen apps.
- **Text wrap or truncation** pushes the value off the visible line. Try a wide terminal to confirm.

## Lock it in with a test

Once you know which branch you're in, reproduce the bug without a real terminal using `ink-testing-library`. This becomes your regression test:

```tsx
import {render} from 'ink-testing-library';
const tick = () => new Promise(r => setTimeout(r, 0));

const {lastFrame, frames, stdin} = render(<App />);
stdin.write('j');      // or trigger whatever dispatches
await tick();          // renders are async, so always await after input
console.log(frames);   // every frame, like debug mode
expect(lastFrame()).toContain('expected value');
```

If the test passes but the real app fails, suspect something about the real terminal: something bypassing Ink's stdout (problem 1), terminal size or clipping, or the event loop being blocked.

## Summary workflow

1. Send all debug output to a file and `tail -f` it in another pane. This removes problem 1 entirely.
2. Run with `{debug: true}` to tell a state bug (no new frame) from a render bug (new frame you can't see).
3. For a state bug, check mutation, subscription, stale closures and blocking calls, and use React DevTools to confirm.
4. For a render bug, check `<Static>`, clipping, height and wrapping.
5. Write an `ink-testing-library` test for the bug, and unit-test the reducer for immutability.
