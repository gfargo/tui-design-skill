## Short answer

No. A process can't change its parent's working directory. Your TUI runs as a child of the shell, and `cwd` belongs to each process. When your binary calls `std::env::set_current_dir`, only its own cwd changes, and that change disappears when it exits. (You could hack around this with ptrace/gdb tricks or `TIOCSTI` keystroke injection, but they're fragile and often disabled, e.g. `TIOCSTI` has been off by default since Linux 6.2. Don't use them.)

## The real pattern: a shell function wrapper

Every tool that does this (yazi, broot, ranger, lf, nnn, zoxide, fzf's `cd` widgets) works the same way. **The binary reports the chosen path, and a shell function the user installs does the `cd`.** A shell function runs inside the user's shell process, so its `cd` sticks.

There are two ways to hand the path back.

### Option A: a temp file (what yazi does with `--cwd-file`)

The most robust option, because stdout stays free for your TUI.

```rust
// on quit-with-selection
if let Some(path) = args.cwd_file {
    std::fs::write(path, selected_dir.as_os_str().as_encoded_bytes())?;
}
```

```zsh
# bash/zsh
fp() {
  local tmp="$(mktemp -t fp-cwd.XXXXXX)" cwd
  command fp "$@" --cwd-file="$tmp"
  if cwd="$(<"$tmp")" && [ -n "$cwd" ] && [ "$cwd" != "$PWD" ]; then
    builtin cd -- "$cwd"
  fi
  rm -f -- "$tmp"
}
```

```fish
function fp
    set tmp (mktemp -t fp-cwd.XXXXXX)
    command fp $argv --cwd-file=$tmp
    if set cwd (cat -- $tmp); and test -n "$cwd"; and test "$cwd" != "$PWD"
        builtin cd -- $cwd
    end
    rm -f -- $tmp
end
```

### Option B: print the path to stdout (fzf style)

`cd "$(fp)"`. This only works if your TUI does **not** draw to stdout, because `$(...)` captures it. Render to `/dev/tty` (or stderr) instead:

```rust
use std::fs::OpenOptions;
let tty = OpenOptions::new().read(true).write(true).open("/dev/tty")?;
let backend = ratatui::backend::CrosstermBackend::new(tty);
// ... run the app; on exit:
println!("{}", selected.display());
```

Crossterm reads input from the tty by default when stdin isn't a terminal (with the `use-dev-tty` feature this is more reliable). Option B is nice for composability (`vim "$(fp)"`), but it's easier to break. I'd make the file approach the primary `cd` mechanism and keep stdout output as an optional mode.

## Making installation painless

Users won't want to copy shell snippets by hand, so do what zoxide and starship do and ship an `init` subcommand that prints the wrapper:

```zsh
# in ~/.zshrc
eval "$(fp init zsh)"
```

Store the snippets with `include_str!` and pick one per shell (`bash`, `zsh`, `fish`, `nu`, `powershell`). That also lets you change the wrapper later without users editing their rc files.

## Details worth getting right

- **Cancel vs. select:** if the user quits without choosing, write nothing (or exit non-zero). The wrapper's `-n` check then skips the `cd`.
- **Name collisions:** if the function and the binary share a name, call the binary with `command fp` as shown, or the function will recurse. Some tools give the function a different name instead (yazi recommends `y`, broot uses `br`).
- **Odd paths:** write the raw path with no trailing newline, and use `cd --` so names starting with `-` work. Paths containing newlines are rare, but the file approach handles them better than stdout.
- **Restore the terminal before exiting** (leave the alternate screen, disable raw mode). Otherwise the `cd` happens in a garbled terminal.
