# Changing the parent shell's directory

**Your program can't do it directly.** Every process has its own working directory. A child process like your TUI can change its own directory, but it can't change its parent shell's. When your binary exits, its directory goes with it. This is an OS rule, not a missing Rust feature.

## The standard pattern: a shell wrapper function

`cd` only works when the shell itself runs it, so tools like yazi, broot, zoxide, lf, nnn and ranger all do the same thing:

1. The user runs a **shell function**, not your binary directly.
2. The function runs your binary, which reports the chosen path back.
3. The function calls `cd` itself, inside the user's shell.

There are two ways to send the path back.

### Option A: write to a temp file (yazi's `--cwd-file`)

This is the most robust option, because stdout stays free for the TUI.

```rust
// on quit-with-selection
if let Some(path) = args.cwd_file {
    std::fs::write(&path, selected_dir.as_os_str().as_encoded_bytes())?;
}
```

```zsh
# bash/zsh
fp() {
  local tmp="$(mktemp -t fp-cwd.XXXXXX)" cwd
  command fp "$@" --cwd-file="$tmp"
  if cwd="$(<"$tmp")" && [ -n "$cwd" ] && [ "$cwd" != "$PWD" ]; then
    builtin cd -- "$cwd"
  fi
  rm -f -- "$tmp"
}
```

```fish
# fish
function fp
    set tmp (mktemp -t fp-cwd.XXXXXX)
    command fp $argv --cwd-file=$tmp
    if set cwd (cat -- $tmp); and test -n "$cwd"; and test "$cwd" != "$PWD"
        builtin cd -- $cwd
    end
    rm -f -- $tmp
end
```

### Option B: print the path to stdout

```zsh
fp() { local d; d="$(command fp "$@")" && [ -n "$d" ] && cd -- "$d"; }
```

**Catch:** `$(...)` captures stdout, so your TUI must not draw to stdout. Render to `/dev/tty` (or stderr) instead:

```rust
let tty = std::fs::OpenOptions::new().read(true).write(true).open("/dev/tty")?;
let backend = ratatui::backend::CrosstermBackend::new(tty);
```

Crossterm reads input from the tty by default on Unix (the `use-dev-tty` feature makes this more reliable), so it works while stdout is captured. If you skip this, the TUI's output disappears into the variable and the user sees a blank screen. That's the most common bug with this approach.

## Details that make it feel polished

- **Ship the wrapper from your binary.** Use the zoxide/starship pattern: `fp init zsh` prints the function, and the user adds `eval "$(fp init zsh)"` to their rc file. You can then update the wrapper without asking users to edit their dotfiles.
- **Separate "quit" from "quit and cd".** For example, `q` exits with the path and `Q` exits without it, or use a non-zero exit code to mean "don't cd".
- **Use `builtin cd` / `command fp`.** This avoids recursion when the function has the same name as the binary, and it bypasses user aliases.
- **Handle odd paths.** Write raw bytes with no trailing newline and quote everything, so paths with spaces or newlines survive.
- **Optionally detect a missing wrapper.** Your wrapper can set an environment variable like `FP_WRAPPED=1`. If it's absent, the binary can print a hint about `fp init`.

## Hacks to avoid

- **TIOCSTI** (injecting `cd /path\n` into the terminal's input). It's disabled by default on Linux 6.2+, restricted on macOS, and is a known security hole.
- **Attaching a debugger to the parent and calling `chdir()`.** It's technically possible but fragile and needs elevated privileges. Don't ship it.

**Recommendation:** use Option A (`--cwd-file`) together with an `fp init <shell>` subcommand. That's yazi's approach, it keeps stdout free, and it works the same way in bash, zsh, fish, nushell and PowerShell.
