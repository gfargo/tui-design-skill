Neither problem has a clever technical fix. Both come down to good defaults and being honest with the user about what the app knows.

## 1. Nerd Font icons with a fallback

**You can't detect whether a Nerd Font is installed.** The terminal draws the glyphs, and your app has no way to ask it which font it's using. No standard env var exists for this either. If you guess, users who don't have the font will see tofu (`□`) or blank boxes.

The usual approach:

**Have an icon set in several tiers and let the user choose. Default to a safe tier.**

```rust
#[derive(Clone, Copy, Debug, Default, clap::ValueEnum, serde::Deserialize)]
pub enum IconMode {
    Nerd,
    #[default]
    Unicode, // standard symbols every modern terminal font has: ✓ ✗ ● ▸ ⚠
    Ascii,   // [ok] [x] * > !  (safe for dumb terminals, screen readers, logs)
}

pub struct Icons {
    pub ok: &'static str,
    pub err: &'static str,
    pub warn: &'static str,
    pub folder: &'static str,
    pub sync: &'static str,
}

impl Icons {
    pub const fn for_mode(mode: IconMode) -> Self {
        match mode {
            IconMode::Nerd    => Icons { ok: "\u{f00c}", err: "\u{f00d}", warn: "\u{f071}", folder: "\u{f07b}", sync: "\u{f021}" },
            IconMode::Unicode => Icons { ok: "✓", err: "✗", warn: "⚠", folder: "▸", sync: "↻" },
            IconMode::Ascii   => Icons { ok: "+", err: "x", warn: "!", folder: ">", sync: "~" },
        }
    }
}
```

Resolve the mode in this order: **CLI flag (`--icons nerd`) → env var (`MYAPP_ICONS=nerd`) → config file → default**. Build `Icons` once at startup and pass it around, or keep it in your `App` state. Widgets should never hard-code glyphs.

Practical tips:
- **Keep the icon out of the width calculation.** Nerd Font glyphs live in the Private Use Area. `unicode-width` counts them as 1 cell, but many terminals draw them as 2 cells, which breaks table and column alignment. Always put a space after the icon and avoid packing icons tightly into fixed-width columns.
- **Don't use an icon as the only signal.** Show `✓ synced` or a color plus a word, not just a glyph. That way the ASCII tier still reads well, and it also helps colorblind and screen-reader users.
- **Make opting in easy.** Mention `--icons nerd` in `--help` and the README. You could also put a one-line hint in the about or help screen. Users who have a Nerd Font will turn it on.
- Optionally, add a `myapp --icon-test` command that prints every glyph in each tier so users can check what their terminal renders.

## 2. A polled API that sometimes times out

The main rule: **a timeout is a status, not an event.** Don't let it clear the screen, open a modal, or freeze input.

**Architecture**
- **Never make network calls on the render/input thread.** Run the poller in a background task (tokio task or thread) and send results to the UI loop over a channel. The UI keeps redrawing and responding to keys no matter what the network is doing.
- **Don't let requests overlap.** If a request is still in flight when the next tick arrives, skip that tick. Make the request timeout shorter than the poll interval.
- **Back off on failure.** Use exponential backoff with jitter and a cap, e.g. 2s → 4s → 8s → … → 60s. Reset to the normal interval after a success.

**UI state**

```rust
enum Conn {
    Loading,                                   // first load only, nothing to show yet
    Live { updated: Instant },
    Stale { updated: Instant, failures: u32, retry_at: Instant, last_err: String },
    Down  { failures: u32, retry_at: Instant, last_err: String }, // never had data
}
```

**What the user sees**
- **Keep showing the last good data.** Don't blank it out. Data a few seconds old is much more useful than an empty pane.
- **Show how fresh the data is.** Put something like `updated 3s ago` in the status bar or block title. Once it's stale, show `⚠ stale · updated 47s ago · retrying in 8s`. Optionally dim the stale content (`Modifier::DIM`).
- **Don't react to a single failure.** One timeout isn't worth alerting on. After 1 failure, quietly change the indicator (e.g. a yellow dot). After about 3 in a row, show the explicit stale or warning text.
- **Let the user retry manually.** For example, `r` retries immediately and resets the backoff. Show the key hint while the app is in an error state.
- **Make the error details available without forcing them on screen.** Keep `last_err` on the state and show it in a details popup or a `?` view rather than in the main layout.
- **Use a spinner only for the first load,** or as a tiny in-flight marker in the status bar. Don't put a full-screen spinner over existing data on every poll.
- **Never print errors to stderr while the TUI is running,** because it corrupts the screen. Log to a file instead (`tracing-appender`, or `tui-logger` for an in-app log pane).
- **Mark recovery clearly but briefly.** When a request succeeds again, set the status back to `Live`, and if you like, flash `reconnected` in the status bar for a couple of seconds.

The two answers follow the same idea. **Start with a safe baseline, add the nicer behavior only when you know it will work, and never let something the app can't control** (the font, the network) **break the layout or block input.**
