These have different answers. For Textual, you need a Python profiler because Textual doesn't include one. For Ink, React DevTools helps, but it only measures part of the render cost.

## 1. Textual DataTable with 50k rows

**First, check whether something is blocking the event loop.** Textual runs on asyncio, so asyncio's debug mode will log any callback that holds the loop for too long:

```bash
PYTHONASYNCIODEBUG=1 textual run --dev app.py
# in another terminal:
textual console
```

Lines like `Executing <Task ...> took 0.850 seconds` point to the handler that's freezing the UI. You can lower the threshold with `asyncio.get_running_loop().slow_callback_duration = 0.05` in `on_mount`.

**Then get a real profile.** Two good options:

- **py-spy** attaches to a running process without changing your code, so it works well while you reproduce the lag:
  ```bash
  sudo py-spy record -o profile.svg --pid <PID>    # flame graph
  sudo py-spy top --pid <PID>                      # live view
  ```
  macOS requires `sudo`.
- **pyinstrument** handles async well and gives readable call trees:
  ```bash
  pyinstrument -r html -o profile.html app.py
  ```
  It takes over the terminal, so reproduce the lag, quit the app, and then open the report.

**Common causes with large DataTables:**

| Symptom | Likely cause | Fix |
|---|---|---|
| Slow initial load | Calling `add_row` 50k times | Call `add_rows(rows)` once |
| Load freezes the UI | Building or loading data on the main loop | Move it into a `@work(thread=True)` worker and add the rows when it finishes |
| Slow load or updates | Auto-width columns (`width=None`) measure every cell | Set explicit column widths |
| Slow scrolling | Cells are heavy Rich renderables (`Text` with markup or styles) | Use plain strings where possible |
| Slow sort or filter | Calling `sort()` or `clear()` + re-add on every keystroke | Debounce the input, or filter your data model and rebuild in one batch |
| Lag on every update | Calling `update_cell` in a tight loop | Batch the updates. If that isn't enough, render only a window of the data yourself |

DataTable only renders visible rows, so if scrolling itself is slow, check per-cell render cost or a custom `render_line`. Raw row count is less likely to be the problem.

## 2. Ink with React DevTools

**Yes, you can use them, but they only cover part of the cost.** If you already have DevTools connected (`DEV=true` + `react-devtools-core` + `npx react-devtools`), the **Profiler tab** works: click record, use the CLI, then stop. It shows which components rendered, why they rendered, and how long reconciliation took. That's useful for finding wasted re-renders, such as unstable props, context that changes too often, or missing `memo`.

**What it misses:** after React commits, Ink still has to run Yoga layout, turn the tree into a string, diff it, and write it to stdout. In Ink apps that part is often the real bottleneck, especially with large or frequently changing output, and React DevTools doesn't see any of it. Its timings are also inflated, because it requires React's dev build and the DevTools bridge adds its own overhead.

To profile the whole pipeline, use Node's profiler:

```bash
node --cpu-prof dist/cli.js        # writes a .cpuprofile; open it in Chrome DevTools → Performance
# or, live:
node --inspect dist/cli.js          # then open chrome://inspect
```

Look for time spent in Yoga or `calculateLayout`, Ink's output/render functions, and `stream.write`, in addition to React.

**Ink-specific fixes:**
- Put append-only output such as logs and completed items in `<Static>`, so Ink doesn't redraw it every frame.
- Throttle fast state updates like progress or streaming tokens. Updating state 1000 times a second means 1000 layout passes.
- Keep the dynamic part of the tree small. Ink redraws the whole non-static region on every update.

**Logging render times without DevTools:** you can wrap a subtree in React's `<Profiler onRender={...}>`. Write the results to a file, not `console.log`, because Ink intercepts console output and the logging will interfere with rendering.

**Summary:** use React DevTools to find components that re-render when they shouldn't, and `--cpu-prof` to find where the time actually goes.
