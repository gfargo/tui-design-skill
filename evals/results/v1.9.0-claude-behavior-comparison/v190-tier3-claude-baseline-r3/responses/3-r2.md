Both are measurement questions, so here's how to get real numbers in each case.

## Textual DataTable with 50k rows

**1. Use a sampling profiler that attaches from outside the process.** `cProfile` writes its output into the terminal your app is using. `py-spy` doesn't touch the terminal at all:

```bash
# Flame graph of a session (macOS needs sudo)
sudo py-spy record -o profile.svg -- python app.py

# Or attach to a running app and watch live hot spots
sudo py-spy top --pid <pid>
```

Repeat the slow action a few times (initial load, scrolling, sorting, moving the cursor), quit, then open `profile.svg` in a browser. `pyinstrument` also works if you'd rather profile one code path, such as the function that loads the data.

**2. Time things with the Textual dev console.** Run `textual console` in one terminal and `textual run --dev app.py` in another. Then use `self.log(...)` with `time.perf_counter()` around suspect sections. Don't `print`, because stdout is your UI.

**3. Check these first, since they cause most 50k-row slowness:**
- **Adding rows one at a time.** Calling `add_row` in a loop does bookkeeping on every row. Build the list and call `add_rows(rows)` once.
- **Auto-width columns.** The table measures cell content to size columns. Setting explicit `width=` in `add_column` avoids that work.
- **Rich `Text` objects in every cell.** These cost more than plain strings. Use strings unless the cell actually needs styling.
- **Loading on the main thread.** If the freeze happens while fetching or parsing data, move that work into a `@work(thread=True)` worker and hand the rows back to the table.
- **Sorting or clearing and refilling often.** Re-sorting 50k rows on every keystroke, or calling `clear()` and refilling, is expensive. Debounce it, or filter the data before it reaches the table.

Rendering itself is only done for the visible rows, so if the profile shows time in painting, check for custom renderables or very wide rows.

## Ink: will React DevTools work?

**Partly.** Ink in dev mode can connect to standalone React DevTools, and the **Profiler tab** works there. It shows which components re-rendered on each commit and how long they took. Turn on "Record why each component rendered" in its settings, which is the most useful part.

DevTools leaves out two things that matter for a CLI:

1. **Ink's own work after React commits.** That's Yoga layout, turning the tree into a string, and writing to the terminal. That's often where the time actually goes, and DevTools doesn't measure it.
2. **Accurate absolute timings.** Dev builds are much slower than production, so use the Profiler for relative comparisons and for finding re-renders, not for real millisecond costs.

To see the whole pipeline, use Node's profiler:

```bash
node --cpu-prof dist/cli.js      # writes a .cpuprofile; open it in Chrome DevTools → Performance
# or
node --inspect-brk dist/cli.js   # attach via chrome://inspect and record live
```

**Other useful tools:**
- React's `<Profiler onRender={...}>` component logs `actualDuration` per commit without DevTools. Write the output to a file, not stdout.
- `render(<App/>, { debug: true })` prints every frame instead of redrawing in place, so you can see how many frames you're producing.
- Recent Ink versions have a `maxFps` option to throttle redraws. Check that your version supports it.
- **Common fixes:** put append-only output (logs, completed items) in `<Static>` so it isn't laid out again each frame. Throttle high-frequency state updates such as progress ticks and streaming data. Memoize subtrees that don't change.

**In short:** for Textual, start with a `py-spy` flame graph. For Ink, React DevTools will tell you what re-renders too often, but you need `node --cpu-prof` to see the whole cost of drawing a frame.
