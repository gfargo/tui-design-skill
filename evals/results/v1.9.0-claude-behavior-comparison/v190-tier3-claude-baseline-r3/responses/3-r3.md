## Textual: profiling the 50k-row DataTable

**1. Use a sampling profiler that attaches from outside.** Your TUI owns the terminal, so you want a profiler that doesn't print to it.

```bash
# Live view of hot functions while you scroll, sort, or load in the app
sudo py-spy top --pid $(pgrep -f your_app.py)

# Or record a flame graph for the whole session
sudo py-spy record -o profile.svg -- python your_app.py
```

macOS needs `sudo` for py-spy. `pyinstrument` and `cProfile` (`python -m cProfile -o out.prof app.py`, then open it with `snakeviz out.prof`) also work, because they only report after the app exits. Reproduce the slow action a few times so it stands out in the profile.

**2. Time specific steps with the Textual devtools console.**

```bash
textual console              # terminal 1
textual run --dev app.py     # terminal 2
```

Then wrap the code you suspect with `time.perf_counter()` and send the result to `self.log(...)`. Don't use `print`, because it ends up in the TUI.

**3. Likely culprits at 50k rows:**
- **Adding rows one at a time.** Each `add_row` call does its own bookkeeping and can trigger a refresh. Use a single `add_rows(...)` call instead.
- **Auto-sized columns.** Without a width, the table has to measure cell content to size each column. Pass `add_column(..., width=N)` to skip that.
- **Heavy cell values.** Rich `Text` objects or markup in every cell cost more to render than plain strings. Use simple values where you can.
- **Loading on the event loop.** If the UI freezes while data loads, move the fetch or parse into `@work(thread=True)` and push results back with `call_from_thread`.
- **Sorting or filtering by rebuilding the table.** At this size, also consider paging, or keeping the full dataset outside the widget and only loading a slice into it.

The DataTable only renders visible lines, so if scrolling itself is slow, the profile will usually show something unexpected, such as per-cell work or a watcher firing too often.

## Ink: can you use React DevTools?

Partly. If you already have it connected (Ink + `react-devtools-core`, running `DEV=true` with `npx react-devtools`), the **Profiler tab works**. It's good at one thing: **showing which components re-render, how often, and why.** Turn on "Record why each component rendered while profiling" in its settings. That's often the main problem in Ink apps, for example a spinner or timer state high in the tree that re-renders everything.

It doesn't show the full cost, though:
- **It only measures React's own work.** A lot of Ink's per-frame cost happens after React finishes: Yoga layout, building the output string, and erasing and rewriting the terminal. None of that appears in the Profiler.
- **The numbers are inflated.** The dev build of React plus the DevTools connection add overhead, so trust relative comparisons between components, not absolute milliseconds.

To see the whole frame, use Node's profiler:

```bash
node --cpu-prof dist/cli.js      # writes a .cpuprofile on exit; open it in Chrome DevTools > Performance
# or
node --inspect dist/cli.js       # attach via chrome://inspect and record live
```

For lightweight, always-available timing, wrap subtrees in React's `<Profiler onRender={...}>` and **append the results to a file**. Writing to stdout or the console will corrupt Ink's output.

A common fix once you find the hot spot: put long, append-only output (logs, completed items) in `<Static>` so Ink stops redrawing it every frame.
