No, a program can't change its parent shell's directory. A process can only change its own working directory, and that's what `std::env::set_current_dir` does. Your picker runs as a child of the shell, so when it exits, the shell is still where it was. Nothing in Rust, no signal and no IPC trick changes that. Only the shell can run `cd`.

The usual fix is a small shell function. Your binary writes the chosen directory somewhere, and a function in the user's shell reads it and runs `cd` after your binary exits. yazi (`--cwd-file`) and ranger (`--choosedir`) both work this way.

## Pattern 1: `--cwd-file` plus a wrapper function (recommended)

**Rust side:** accept a path argument and write the final directory to it **after** you've restored the terminal:

```rust
use std::{os::unix::ffi::OsStrExt, path::PathBuf};
use clap::Parser;

#[derive(Parser)]
struct Args {
    /// Write the final directory to this file on exit (for shell cd-on-exit)
    #[arg(long, value_name = "PATH")]
    cwd_file: Option<PathBuf>,
}

fn main() -> color_eyre::Result<()> {
    let args = Args::parse();
    let terminal = ratatui::init();
    let outcome = App::new().run(terminal);
    ratatui::restore(); // restore first, even if run() errored

    if let (Ok(Outcome::ChangeDir(dir)), Some(path)) = (&outcome, &args.cwd_file) {
        // Raw bytes, no trailing newline: works for non-UTF-8 paths
        // and paths containing newlines
        std::fs::write(path, dir.as_os_str().as_bytes())?;
    }
    outcome.map(|_| ())
}
```

Give the user two different quit keys. yazi uses `q` to quit and `cd`, and `Q` to quit without changing directory. Esc or Ctrl-C should never move the user.

**Shell side** (bash/zsh, the same shape yazi documents):

```bash
function p() {
    local tmp="$(mktemp -t "picker-cwd.XXXXXX")" cwd
    command picker "$@" --cwd-file="$tmp"
    IFS= read -r -d '' cwd < "$tmp"
    [ "$cwd" != "$PWD" ] && [ -d "$cwd" ] && builtin cd -- "$cwd"
    command rm -f -- "$tmp"
}
```

A few details that matter:
- **`command picker`** stops the function from calling itself if the user names it `picker`.
- **`read -r -d ''`** reads the whole file, so it pairs with writing no trailing newline.
- **`[ -d "$cwd" ]`** guards against an empty file, which is what you get when the user quits without `cd`.
- **`builtin cd --`** skips any `cd` alias the user has, and handles directory names that start with `-`.

Fish needs its own version (`set tmp (mktemp ...)`, `read -z`, `cd -- $cwd`). Document it next to the bash/zsh one.

## Pattern 2: print the path to stdout, draw the UI elsewhere

If you'd rather support `cd "$(picker)"`, stdout has to stay clean. Ratatui's default backend draws on stdout, so you'd need to draw on `/dev/tty` instead, as fzf does, or on stderr (`CrosstermBackend::new(std::io::stderr())`). This works fine for simple pickers. It's more fragile than Pattern 1, though: anything else that writes to stdout, such as a panic message or debug print, can end up inside the path the shell tries to `cd` into. Pattern 1 doesn't have that problem, so use it as your main approach. A `--print` mode for Pattern 2 is a reasonable extra.

## Distributing the wrapper

Don't expect users to copy and paste it from your README. Ship a subcommand that prints it, the way zoxide and starship do:

```bash
# user adds to ~/.zshrc:
eval "$(picker init zsh)"
```

Your `init` subcommand can embed the function from `include_str!("shell/picker.zsh")`, one file per shell, so the function stays in step with your flag names across versions. Also let users choose the function name (e.g. `--cmd p`), as zoxide does.

**Don't edit the user's rc file for them.** Print the line and tell them where to add it ("Add this to the end of ~/.zshrc"). That's what zoxide, starship and mise do.

In short, your binary decides where to go, and a function in the user's shell does the `cd`.
