## 1. Nerd Font icons: make them opt-in, because you can't detect the font

**You can't reliably tell whether a Nerd Font is installed.** No terminal lets a program ask "is a Nerd Font active?" Fonts also fall back glyph by glyph, so even a correct guess based on the font name can be wrong. Don't try to detect it. Make icons a setting and default it to non-Nerd glyphs. Established tools work this way:

- **lazygit** uses `gui.nerdFontsVersion: "2" | "3" | ""`, and empty (the default) means no icons.
- **eza** uses `--icons=always|automatic|never`. Its `automatic` checks whether output goes to a terminal, not whether the font exists.
- **starship** ships three presets: Nerd Font, plain Unicode and plain text.

**Ask which Nerd Fonts version, not just on or off.** Nerd Fonts v3 moved the Material Design icon codepoints (`F500–FD46` → `F0001+`). An app that assumes v2 shows the wrong glyphs or empty boxes on a v3 font. If you offer Nerd icons, accept `nerd-v3` (and `nerd-v2` only if you care about it).

**Use three fallback levels: Nerd → Unicode → ASCII**, all in one table:

```rust
#[derive(Clone, Copy, Default, clap::ValueEnum, serde::Deserialize)]
#[serde(rename_all = "kebab-case")]
pub enum IconSet { NerdV3, #[default] Unicode, Ascii }

pub struct Icons { pub folder: &'static str, pub ok: &'static str, pub err: &'static str, pub warn: &'static str }

impl IconSet {
    pub const fn icons(self) -> Icons {
        match self {
            IconSet::NerdV3  => Icons { folder: "\u{f024b}", ok: "\u{f05e0}", err: "\u{f0159}", warn: "\u{f0026}" },
            IconSet::Unicode => Icons { folder: "▸", ok: "✓", err: "✗", warn: "!" },
            IconSet::Ascii   => Icons { folder: ">", ok: "+", err: "x", warn: "!" },
        }
    }
}
```

- Look up the setting in this order: `--icons` flag, then a `MYAPP_ICONS` env var, then `icons = "nerd-v3"` in the config file, then the default. Document it in `--help` and in the README's first screenshot caption.
- **The icon should never be the only way to tell what something is.** Always pair it with a word or label, like `✗ timeout`. Then a missing glyph (shown as `□`), `NO_COLOR` or a screen reader still makes sense.
- **Allow for width.** Nerd glyphs sit in the Private Use Area. `unicode-width` counts them as 1 cell, but many fonts draw them wider. Always put a space after the icon and never pack icons into a column with no gap. Use `Span::width()` / `cell_width()` for layout, never `.len()`.
- Test it: take a `TestBackend` snapshot for each `IconSet` at 80×24 and 60 columns.

## 2. Polling timeouts: keep the old data on screen and mark it stale

**One timeout is not an error screen.** Keep the last good data visible, show how old it is, and only escalate after repeated failures. Don't blank the view or open a modal.

### State model

```rust
enum Feed {
    Live,                                        // last poll succeeded
    Refreshing,                                  // request in flight, old rows still shown
    Stale { failures: u32, last_error: String }, // last-known-good, dimmed
}

struct App {
    data: Option<Snapshot>,       // None only before the first success
    fetched_at: Option<Instant>,
    feed: Feed,
    in_flight: bool,
    next_poll: Instant,
    selected_id: Option<RowId>,   // track by ID, not index
}
```

### The fetch never runs on the UI thread

```rust
fn spawn_fetch(client: Client, tx: mpsc::UnboundedSender<AppEvent>) {
    tokio::spawn(async move {
        let res = match tokio::time::timeout(Duration::from_secs(3), client.fetch()).await {
            Ok(r) => r.map_err(|e| e.to_string()),
            Err(_) => Err("timed out after 3s".into()),
        };
        let _ = tx.send(AppEvent::Fetched(res));
    });
}
```

On each tick, call `spawn_fetch` only if `!in_flight && now >= next_poll`, so slow requests never pile up. Handle the result in `update`, not in the draw code:

- **Ok:** store the data, set `fetched_at`, set `feed = Live`, reset the backoff, and find the selected row again by its ID.
- **Err:** keep `data` as it is. Increment `failures` and set `next_poll` with exponential backoff and a little jitter (5s → 10 → 20 → max 60s). Write the error to the message log.

### What the user sees, by number of failures

| Situation | UI |
|---|---|
| Refreshing | Rows stay put. A small spinner in the header, shown only if the request takes more than ~200 ms. |
| 1 failure | Data unchanged. The header age turns muted, like `updated 9s ago`. No popup. |
| ≥2 failures, or data older than ~3× the interval | Rows dimmed. Header shows `STALE 1m · retry in 20s (3) · r retry now`. |
| No data has ever loaded | This is the **error** state, not stale: `✗ Cannot reach api.example.com (timed out after 3s)` with `r retry · l log · q quit`. |
| Recovery | `✓ Reconnected` in the status line, gone after 3–5 s. |

```
80 cols
 Builds (prod)                     STALE 1m ⋅ retry in 20s (3) ⋅ r retry now
 ▸ api-deploy      running   4m                                    <- dimmed
   web-build       passed   12m
 r retry ⋅ / filter ⋅ enter open ⋅ p pause ⋅ ? help

60 cols  (shorter header text, footer trimmed from the right)
 Builds (prod)              STALE 1m ⋅ retry 20s ⋅ r
 r retry ⋅ / filter ⋅ ? help
```

The word `STALE` and the age carry the meaning. Dimming is only extra, because some terminals ignore the faint attribute and `NO_COLOR` removes color.

### Details that are easy to miss

- **Keep the selection steady.** Track the selected row by a stable ID. If that row disappears, select its neighbor, not row 0. Don't re-sort on refresh. Consider a `p` key to pause updates.
- **Let users act.** `r` retries now and resets the backoff. Store every error with a timestamp in a message log the user can reopen.
- **Pause polling when the terminal loses focus.** Turn on focus reporting (`EnableFocusChange` in crossterm) and refresh right away when focus returns. In tmux this needs `focus-events on`.
- **A temporary failure must never change saved state.** Don't drop a panel from the config because the API was down. btop has an open bug of exactly this kind.
- **Test it** with a unit test on `update`: feed it `Fetched(Err)` ×3 and then `Fetched(Ok)`, and check the feed state, backoff timing and that the selection is kept. Then add a `TestBackend` snapshot of the stale frame at 80×24 and 60×24.
