**Short version:** for Textual, attach `py-spy` to the running app. For Ink, no. React DevTools there only shows the component tree and props, so use `node --cpu-prof`.

## 1. Textual app with 50k rows

None of Textual's built-in tools measure speed. `textual console` and `textual run --dev` give you logs and live CSS reload. `textual diagnose` reports on your environment. There's no frame-rate display either. To see where time goes, use a sampling profiler on the running process:

```sh
# terminal 1
python myapp.py

# terminal 2 (attaching usually needs sudo on macOS)
sudo py-spy record -o profile.svg --pid <pid> --idle
```

- **This needs no code changes**, so you're profiling the app exactly as it runs.
- **Use `--idle`.** py-spy skips idle threads by default, and Textual's main loop spends most of its time waiting. If you record over a quiet stretch without `--idle`, the flame graph can come out almost empty.
- **On Python 3.15+**, the standard library has the same thing built in: `python -m profiling.sampling attach <pid>`.

**Profile one slow action at a time.** "Sluggish" could mean the initial load, scrolling, sorting, or slow response to keys, and each one points to a different cause. Start recording, do only that action a few times, then stop. Common causes with a large `DataTable`:

- **Inserting the rows.** If the flame graph is mostly `add_row`, that's your cost. Switching to `add_rows()` won't help, because it just calls `add_row()` once per row. Build the row data before you touch the widget, and look at whether you really need all 50k rows at once. You could page them in, or filter before inserting.
- **Blocking the event loop.** Heavy synchronous work in an `async def` handler with no `await` freezes the whole UI. Loading data, parsing, and sorting in Python all count. Move that work to `@work(thread=True)` and send results back with `self.app.call_from_thread(...)`. A plain `@work` won't help here because it still runs on the event loop. If you start a new load while an old one is running, check `worker.is_cancelled` so stale results get dropped.
- **Drawing the table.** `DataTable` only draws the rows on screen, so 50k rows shouldn't make each frame slow. If the profile shows lots of time in rendering anyway, look for per-cell work you added yourself, like building heavily styled Rich `Text` for every cell or rebuilding the table when one value changes. Update only the cells that changed.

## 2. Ink CLI: React DevTools won't profile it

The DevTools setup you already have (`react-devtools-core` with `DEV=true` and `npx react-devtools`) is fine for inspecting the live component tree and props. It can't profile, though, because Ink's renderer doesn't turn on the features React's Profiler needs. You'll get an empty or useless Profiler tab.

Use Node's CPU profiler:

```sh
node --cpu-prof dist/cli.js   # writes a .cpuprofile file when the process exits
```

Open the file in Chrome DevTools (Performance panel) or in speedscope. Make sure the app exits cleanly (`useApp().exit()`, or `await waitUntilExit()` at the top level), because the profile is only written on exit.

Common causes of slow Ink renders:

- **Components that re-render whenever their parent updates.** Fix with `React.memo` and stable props and callbacks.
- **Misusing `<Static>`.** Output that never changes, like finished log lines, should go in `<Static>` so it isn't redrawn. Content that does change shouldn't go in it.
- **A long list that's mounted but hidden or clipped.** Scrolling with `contentOffsetY` only shifts and clips the view. Ink still lays out and draws every child, so 20,000 rows cost 20,000 rows on every frame. Render only `items.slice(top, top + height)` inside a box with a fixed height.
- **Something that's always animating**, such as `ink-spinner`, which keeps triggering redraws.

Ink 8 has two settings that reduce redraw work for high-frequency updates. `incrementalRendering: true` rewrites only the changed part of each line. A lower `maxFps` (the default is 30) also helps. For streaming text, try `useDeferredValue`, which only fully works with `render(<App />, {concurrent: true})`.

**Don't log to the screen** in either app while you investigate. In Ink, send tracing to `useStderr().write()` or a file you `tail -f`. In Textual, use `textual console`. Writing straight to stdout or file descriptor 1 corrupts the display, which can look like a performance problem.
