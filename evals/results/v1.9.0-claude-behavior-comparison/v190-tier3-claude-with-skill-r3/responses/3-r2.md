## 1. Textual: finding what's slow with 50k rows

**Use a sampling profiler on the running process.** Textual has no built-in performance tooling. `textual console` / `textual run --dev` only show logs, `textual diagnose` is an environment report, and there's no FPS overlay.

```sh
# Start the app normally, then from another terminal:
pgrep -f myapp.py                                  # get the PID
sudo py-spy record -o profile.svg --pid <PID>      # do the slow thing, then Ctrl+C
```

Open `profile.svg`, which is a flame graph. You don't need to change any code, but attaching usually needs `sudo` on macOS. On Python 3.15+ you can use the built-in sampler instead: `python -m profiling.sampling attach <PID>`.

Two things to watch for:

- **Add `--idle` if the flame graph is nearly empty.** py-spy skips idle threads by default, and Textual's main loop spends most of its time waiting. A short recording can show almost nothing without it.
- **Record each slow action separately**, for example one run for the initial load, one for scrolling, one for sorting. Sorting or filtering 50k rows behaves very differently from scrolling.

What you'll probably find:

- **Synchronous work inside an `async def` handler.** If the handler builds or loads 50k rows without ever hitting an `await`, it blocks the whole UI while it runs. Move that work to `@work(thread=True)`. Plain `@work` still runs on the event loop, so it doesn't help with CPU-heavy work. Hand the results back to the table on the UI thread with `call_from_thread`.
- **Switching to `add_rows()` won't help.** It just loops over `add_row()` and pays the same cost per row. If the flame graph shows most of the time in row insertion, the fix is to insert fewer rows or do the work off the UI thread.
- **Rendering usually isn't the problem.** `DataTable` already only draws the rows on screen. If scrolling is smooth but loading, sorting or filtering is slow, the cost is in your data handling, and the flame graph will show which function.

## 2. Ink: can you use React DevTools for profiling?

**No. Use it to inspect the component tree, but use `node --cpu-prof` to profile.** Ink's renderer doesn't set the flags React's Profiler needs, so the DevTools Profiler tab won't give you real render timings. Your existing DevTools setup (`react-devtools-core`, `DEV=true`, `npx react-devtools`) is still useful for checking props and state, just not for timing.

```sh
node --cpu-prof --cpu-prof-dir=./profiles dist/cli.js
# Do the slow interaction, then quit cleanly (the profile is written on exit)
```

Load the `.cpuprofile` file into Chrome DevTools' Performance panel or into speedscope.app. Make sure the app exits normally, because the profile is only written on exit.

The usual causes in Ink:

1. **Components that re-render on every parent update** because they aren't memoized. Wrap leaf components in `React.memo` and keep callbacks and objects stable.
2. **Long lists that are mounted but hidden.** Scrolling with `contentOffsetY` only shifts and clips the view: Ink still lays out and draws every row on every frame. Render only the visible rows: `items.slice(top, top + height)` inside a fixed-height box.
3. **Misusing `<Static>`.** Output that only ever gets appended should go in `<Static>` so it's never re-rendered. Content that changes shouldn't go in it.
4. **An always-animating component**, like `ink-spinner`, that keeps triggering renders even when nothing else changes.
5. **Too many frames.** For streaming text or log tailing, try `incrementalRendering: true` (Ink 8), a lower `maxFps` (default is 30), and `useDeferredValue` with `render(<App />, {concurrent: true})`.

If a specific frame looks wrong rather than slow, `render(<App />, {debug: true})` prints each update one after another instead of redrawing in place.

In both apps, send any timing logs you add to a file or stderr. Writing to stdout corrupts the screen the app is drawing on.
