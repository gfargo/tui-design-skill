**Short answers:** for Textual, attach `py-spy` to the running app. Textual's own dev tools won't show you what's slow. For Ink, no: React DevTools can show you the component tree, but it can't profile Ink. Use `node --cpu-prof` instead.

## 1. Textual app slow with a 50k-row DataTable

Textual's built-in tools don't measure performance. `textual console` shows logs, `textual diagnose` reports on your environment, and there's no FPS overlay. Use a sampling profiler on the live process. It needs no code changes:

```sh
# start the app normally, then from another terminal:
sudo py-spy record -o profile.svg --pid <pid> --idle
```

- **`--idle` matters here.** Textual's main loop spends most of its time awaiting, and py-spy leaves out idle threads by default. Without the flag, a recording over a quiet stretch can look nearly empty.
- Attaching usually needs `sudo`, especially on macOS.
- On Python 3.15+, the standard library has its own version: `python -m profiling.sampling attach <pid>`.
- Record the specific thing that feels slow (the initial load, scrolling, sorting, filtering) in separate runs. That way each flame graph answers one question.

**What to look for in the flame graph at 50k rows:**

- **Row insertion.** `DataTable` already virtualizes rendering, so drawing 50k rows usually isn't the bottleneck. Loading them often is. Note that `add_rows()` is a plain loop over `add_row()`, so switching to it won't speed up a slow bulk insert. If insertion dominates, the fixes are to load fewer rows, or to load them in a background worker so the UI stays responsive while it fills.
- **Synchronous work in an `async def` handler.** If a handler parses, sorts, or filters 50k rows without ever hitting an `await`, it freezes the whole UI while it runs. In the profile this shows up as one long frame under your handler. Move that work to `@work(thread=True)`. A bare `@work` still runs on the event loop, so it won't help with CPU-bound work. Send results back with `self.app.call_from_thread(...)`.
- **Your own per-row formatting.** Building a Rich `Text` object, or doing string work, for every cell of every row adds up quickly at 50k rows.

To time specific code sections, run `textual console` in one terminal and `textual run --dev app.py` in another. Then log `time.perf_counter()` deltas with `self.log(...)`. Don't write to `sys.__stdout__` or fd 1, because that bypasses Textual's capture and corrupts the screen.

## 2. Ink CLI: can React DevTools profile it?

**No. It can inspect the tree and props, but not profile.** Ink's reconciler doesn't set the flags React's Profiler needs, so the Profiler tab won't give you usable data. Your current setup (the `react-devtools-core` peer, `DEV=true`, and `npx react-devtools`) is still useful for checking which components exist and what props they received.

**For profiling, use Node's CPU profiler:**

```sh
node --cpu-prof ./dist/cli.js   # writes a .cpuprofile when the process exits
```

Load the `.cpuprofile` file into Chrome DevTools' Performance panel or into speedscope. Make sure the app exits cleanly (`useApp().exit()`, then `await waitUntilExit()`), or the profile may never get written.

**Common places Ink spends its time:**

- **Unmemoized components** that re-render on every parent update. Try `React.memo`, stable callbacks, and narrower state selectors.
- **`<Static>` misuse.** Either append-only output (like logs) isn't in `<Static>` and gets repainted every frame, or content that changes was put in `<Static>`, which never re-renders.
- **Long lists that aren't virtualized.** `contentOffsetY` only shifts and clips. Yoga still lays out every child, and Ink still paints it. Mount only `items.slice(top, top + height)` inside a fixed-height box.
- **Something that's always animating**, like `ink-spinner`, which keeps the render cycle busy even when nothing else changes.

**Rendering options worth trying once you know the cause:**

- `render(<App />, {incrementalRendering: true})` (Ink 8) rewrites only the changed parts of the output.
- A lower `maxFps` (the default is 30) reduces how often frames are drawn.
- For streaming output, use `useDeferredValue` with `concurrent: true`.

**For "which frame went wrong" questions**, `render(<App />, {debug: true})` prints each update as separate output instead of redrawing in place. Send high-volume tracing to stderr or a file you `tail -f`. Never send it to stdout, because Ink owns stdout.
