Treat terminal size as a layout input: **drop lower-priority panes as space shrinks, and give the current directory a guaranteed usable width.** Equal thirds works only when every pane has room to do its job.

For a Miller layout, the priority is usually **current → preview → parent**. The current directory is essential; the other two provide context.

A sensible starting policy is:

| Terminal width | Layout | Suggested allocation |
|---|---|---|
| 120+ columns | Parent · current · preview | Parent 20–28, current 36+, preview gets the rest |
| 90–119 | Current · preview | Current roughly 45%, preview gets the rest |
| 60–89 | Current only | Full width; preview available on demand |
| Below 60 | Compact current directory | Names first; minimal chrome and metadata |

These are starting points, not universal breakpoints. Derive the actual thresholds from **minimum useful content widths plus borders and gaps**. If your preview needs 40 columns, don’t keep it visible at 25 just to preserve the three-pane arrangement.

In Ratatui, choose the layout mode before constructing its constraints:

```rust
enum LayoutMode {
    ThreePane,
    TwoPane,
    SinglePane,
}

fn layout_mode(width: u16) -> LayoutMode {
    match width {
        120.. => LayoutMode::ThreePane,
        90..=119 => LayoutMode::TwoPane,
        _ => LayoutMode::SinglePane,
    }
}
```

Use the available **body rectangle’s width**, rather than a cached terminal width. In three-pane mode, cap the parent’s width and let the current directory and preview absorb additional space. Ratatui’s `Constraint::Length`, `Min`, `Max`, and `Fill` are more useful here than three `Percentage(33)` constraints.

The layout change needs a few accompanying behaviors:

- **Keep hidden panes accessible.** Provide a preview toggle that replaces the directory view at narrow widths, with an obvious return action. Keep parent navigation available through your existing keybindings.
- **Preserve selection and scroll position across modes.** Resizing should change presentation without resetting navigation or rereading the directory unnecessarily.
- **Reduce directory metadata before sacrificing filenames.** Hide owner, permissions, timestamps, and eventually size as width decreases. Right-align any retained metadata so long names cannot push it around.
- **Truncate names deliberately.** Preserve extensions where useful, such as `quarterly-repo….pdf`. Measure terminal display width, not UTF-8 byte length or character count; avoid splitting grapheme clusters.
- **Adapt the preview itself.** Wrap text, truncate long lines, or choose a compact summary according to preview type. Skip expensive preview rendering when its pane is hidden.

Height needs its own policy. At **80×24**, aim for one breadcrumb row, one status/help row, and as many file rows as possible. At short heights, collapse verbose help and consider dropping pane borders. Keep errors visible through a compact status message or dismissible overlay.

Also handle genuinely tiny rectangles safely: use saturating arithmetic for inset calculations, avoid indexing empty lists, and render a minimal message when there’s no room for a usable list. A tmux split can become much smaller than your intended minimum during resizing.

Finally, verify the transitions with Ratatui’s `TestBackend`. Cover **220×50, 120×30, 100×24, 80×24, 60×20, 40×10**, plus widths immediately around each breakpoint. Check that selection stays visible, text stays within bounds, and resizing repeatedly doesn’t lose state.

Your practical target should be: **80×24 is a comfortable single-pane file manager; 60 columns remains fully navigable; wider terminals progressively add context.**
