Here’s what’s making it busy, in priority order:

| Observation | Why it hurts | Change |
|---|---|---|
| **Three border layers** around pipeline and detail content | Your eye crosses several boundaries that separate nothing | Remove the application frame and innermost boxes. Use whitespace and one divider between panes |
| `▶` appears on **all five rows** | It cannot identify selection; it also suggests expandable items | Show a marker only on the selected row, or use reverse video |
| `✅ PASSED ✅` repeats success three times | Successful state competes with the failure for attention | Use `PASS` once, optionally colored. Avoid emoji in aligned columns |

| Logs repeat `[INFO]`, the full date, and `::` | Boilerplate pushes the actual messages away from the scanning edge | Use short times; show the date once. Retain severity when it distinguishes something |
| Every section has similar visual weight | Nothing tells you “look here first” | Emphasize selection and failures; mute headings, timestamps, and completed successes |
| `Enter Select` and `Tab Switch Pane` lack visible outcomes | The sketch shows neither a unique selection nor pane focus | Preview on navigation; make Enter explicitly open logs. Mark the focused pane |

The cost is measurable: **eight box outlines occupy this 19-line sketch**, and **six lines contain only framing**. Meanwhile, only three log messages fit.

I’d keep this as a full-screen monitoring session with a stable list-and-inspector layout. Assuming the main loop is *scan status → choose a job → inspect its output*, logs deserve most of the inspector’s height.

At roughly 120 columns, something like this would be calmer. The `>` below represents selection; reverse video could replace it in the actual app.

```text
  Job                 Status      │

  test-e2e            RUNNING     │ 14:22:09  Running vet + lint ...
  deploy-stg          WAITING     │
                                  │
                                  │
                                  │

↑/↓ navigate   Enter logs   Tab focus   r refresh   ? help   q quit
```

This assumes branch and commit belong to the shared run. If they vary by job, keep them in the selected job’s summary instead. Likewise, label the list **Jobs** if these are jobs within one pipeline.

A few behavioral choices make that layout work:

- Keep `PASS` readable but quiet; give `FAIL` stronger emphasis. Status words preserve meaning without color.
- Distinguish **selection** from **focus**: the selected job stays identifiable when logs have focus; the focused pane gets a bold, marked heading.
- Preserve selection by job ID during refresh. Don’t automatically move failed jobs above the cursor as updates arrive.
- For live logs, show `FOLLOWING` or `PAUSED · 37 new`. Scrolling upward pauses follow; `End` resumes it.
- Show stale or disconnected data explicitly. A last-known `PASS` must not imply the connection is healthy.

In the log view, `Esc` returns to the list with selection and scroll position restored. Truncate long job names in the list and reveal them in detail. A reasonable initial minimum is **60×12**; below that, show the required and current dimensions while keeping quit available.
