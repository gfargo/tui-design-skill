I’d change the default layout before building. Your four panels contain useful information, but giving them equal space will make the pod list and logs harder to use. Namespace selection happens occasionally; scanning pods and investigating one pod happen constantly.

Design around this loop: **choose namespace → filter pods → select pod → inspect health/events → read logs → return to list**.

**1. Make the pod list primary; make namespaces a picker.**

Keep cluster/context/namespace in the header. Open a searchable namespace picker on demand, including “all namespaces.” That frees a quarter of the screen without losing context.

Give the pod table most of the width, with columns such as:

`NAME  READY  STATUS  RESTARTS  AGE`

Add node and namespace when space or scope requires them. Keep names single-line and reveal the full value in inspection.

**2. Replace “every field” with a useful summary and deeper views.**

All labels and annotations can consume the details panel on their own. Start with:

- Readiness, status reason, restarts, and age.
- Node, pod IP, and owner.
- Failing conditions and recent warning events.

Put labels, annotations, host IP, QoS, and complete conditions behind expandable sections or a full-screen describe/YAML view. Events deserve easy access: they often explain Pending or CrashLoopBackOff more directly than raw metadata.

Also, `Running` doesn’t necessarily mean healthy. Show `READY 0/1` and the actual waiting/termination reason; don’t turn the entire row green just because the pod phase is Running.

**3. Give logs room—and explicit behavior.**

A quarter-screen log tail will truncate many application messages. Prefer a full-width bottom pane that can expand to full-screen. Show the pod **and container** in its title, with a container picker and access to previous-container logs.

Define follow mode before coding:

- Scrolling upward pauses following.
- Show `PAUSED · new lines available`.
- An explicit action resumes following.
- Searching or reading older lines must not snap back to the bottom.

Preserve pod selection by UID when updates arrive. Opening logs should bind them to a clearly named target; changing the selected pod must never leave old logs under a new title.

A wide layout could look like this; the drawing is schematic:

```text
160×50
context: prod-eu   namespace: payments   watch: connected
Pods /filter                         | api-7d · Summary
NAME       READY STATUS     RST AGE  | Ready: 0/1
> api-7d   0/1   CrashLoop    8  2h   | Reason: CrashLoopBackOff
  worker   1/1   Running      0  3d   | Node: node-03
                                     | Recent warning events...
-------------------------------------+---------------------
Logs: api-7d / app                         FOLLOWING
...
/ filter   Enter inspect   l logs   n namespace   ? help
```

**4. Design the smaller layouts now.**

| Size | Behavior |
|---|---|
| 160×50 | Pod table plus summary; full-width logs when opened. |
| 100×30 | Hide the side summary; inspection replaces the main view. |
| 80×24 | One primary view: pods, details, or logs. Preserve selection and scroll when switching. |
| 60×24 | Same single-pane workflow; drop optional columns and shorten header/hints. |
| Below a declared 60×16 minimum | Show a truthful “Need 60×16; current size …” message and retain quit controls. |

The 60-column fallback should be usable, not merely avoid crashing:

```text
context: prod-eu  ns: payments
Pods                                      watch: connected
NAME                         READY STATUS
> api-7d                     0/1   CrashLoop
  worker                     1/1   Running
...

/ filter  Enter inspect  l logs  n namespace  ? help
```

**5. Reduce chrome and make focus unmistakable.**

Your proposed borders have nesting depth **one**, which is fine. But assuming equal quadrants, one-row header/footer, and independent borders, borders alone consume about **10% of the 160×50 screen**. At 80×24 that rises to about **20%**, before titles, column headings, or help.

Remove the namespace box, replace paired adjoining edges with shared separators, and avoid boxing the header/footer. Rounded corners are fine where a border earns its space.

Use a reverse-video selected row and a marked or bold focused-pane title. Keep status text plus color; adding a checkmark and another status marker would repeat the same signal. Show roughly five contextual shortcuts in the footer and all 14 in `?` help.

**Before implementation, sketch the failure states too:** initial loading, no pods, no filter matches, partial data, permission denied, disconnected/stale watch, and unavailable logs. Keep existing data visible during reconnect, labeled with its last update time.

Ratatui fits this well. Keep Kubernetes watches and log streaming off the input/render path, bound log retention, and verify rendered layouts with `TestBackend` at the sizes above. Plan clean terminal restoration and a linear `--no-tui` mode early.

The biggest improvement is making space follow the investigation: a strong pod list, compact health summary, and logs that can take over when needed.
