Before release, I’d focus on reducing visual noise, making status meaningful, and handling smaller terminals.

1. **Remove the outer frame.** It uses space without adding structure. Keep subtle dividers between namespaces, resources, and YAML, and give only the focused pane a strong border or accent.

2. **Replace repetitive row decoration with useful signals.** Drop the leading bullets and redundant `[READY] ✓`. Use one compact status field with distinct states such as `Ready`, `Pending`, `Failed`, and `Unknown`. Don’t rely on green alone, and distinguish the selected row from keyboard focus.

3. **Make status resource-specific.** A Deployment’s `3/4` readiness, a Job’s completion state, and a Pod’s restart count are more useful than a universal “ready” label. Keep names prominent and align secondary fields for scanning.

4. **Reduce the shortcut footer.** Show a handful of contextual actions plus `? Help`. Put all 18 shortcuts in a searchable help overlay, grouped by navigation, resource actions, and YAML actions. Keep destructive actions clearly labeled.

5. **Add responsive behavior now.** Wide monitors still host split terminals and enlarged text. At narrower widths, collapse namespaces into a picker and let YAML open as a full-width detail view. Preserve selection and focus when resizing; truncate long names consistently and provide a way to reveal them.

6. **Make context and exceptional states explicit.** Keep the current cluster/context and namespace visible. Design loading, empty results, permission errors, disconnected watches, and stale data before release. Avoid presenting stale status as current.

I’d gate release on a keyboard-only walkthrough at 80, 100, and 140 columns, with long resource names, a large namespace list, color disabled, and a cluster connection that drops mid-session. Those cases will expose more usability problems than further border styling.
