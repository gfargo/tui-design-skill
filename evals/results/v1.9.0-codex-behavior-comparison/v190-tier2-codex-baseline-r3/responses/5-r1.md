Use **OSC 8 hyperlinks** for paths and **OSC 52 clipboard writes** for `y`. These are escape sequences sent to the user’s terminal, so they can work over SSH without `pbcopy` or `xclip`.

There’s one distinction to make up front: copying can reach the local clipboard; opening a remote file requires an editor or terminal configured to access that remote host.

### Click a path: OSC 8

Wrap the displayed path in a hyperlink:

```text
ESC ] 8 ; ; URI ESC \ visible path ESC ] 8 ; ; ESC \
```

For example, a local file link might target:

```text
file:///home/alice/project/src/main.rs
```

In Rust:

```rust
fn hyperlink(uri: &str, label: &str) -> String {
    format!("\x1b]8;;{uri}\x1b\\{label}\x1b]8;;\x1b\\")
}
```

Use a URL library to build and percent-encode the URI. Sanitize control characters in labels and targets—especially when paths originate in logs.

**OSC 8 asks the terminal to open a URI; it does not specify an editor.** The terminal’s link handler decides what happens, often requiring Ctrl-click or Cmd-click.

For SSH sessions, choose a documented strategy:

- `file://remote-host/absolute/path` identifies the remote file, but terminal support for opening it varies.
- An editor-specific remote URI can open it in a local editor with SSH support. For example, VS Code supports links shaped like `vscode://vscode-remote/ssh-remote+HOST/absolute/path`.
- Make the URI template configurable so users can select their editor and SSH host alias.

Keep an ordinary keyboard “open” action as well if you want to launch an editor **on the remote machine**. That is a separate behavior from a terminal hyperlink.

### Press `y`: OSC 52

Encode the request ID as Base64 and emit an OSC 52 sequence:

```rust
use base64::{engine::general_purpose::STANDARD, Engine};
use std::io::{self, Write};

fn copy_request_id(id: &str) -> io::Result<()> {
    let encoded = STANDARD.encode(id.as_bytes());
    let mut out = io::stdout().lock();

    write!(out, "\x1b]52;c;{encoded}\x07")?;
    out.flush()
}
```

Here, `c` selects the clipboard. SSH forwards the sequence to the local terminal, which performs the clipboard write.

Emit it only for an explicit user action such as `y`. Some terminals disable OSC 52 or impose size limits. There is no broadly portable success acknowledgment, so “Copy requested” is more accurate than “Copied.”

### Make tmux work

Prefer tmux’s native clipboard support first. In the user’s **remote** `~/.tmux.conf`:

```tmux
# Permit applications inside panes to set the clipboard.
set -s set-clipboard on
```

`on` matters: `external` allows tmux itself to set the clipboard, but does not accept clipboard writes from applications inside panes.

tmux also needs to recognize the outer terminal’s clipboard capability. On recent tmux, if it is not detected, add an entry matching the actual outer terminal type, for example:

```tmux
set -as terminal-features ',xterm-256color:clipboard'
```

The terminal itself must also permit OSC 52 clipboard writes. This configuration belongs to each user’s environment; your application should document it rather than silently modify it.

An alternative is explicit tmux passthrough:

```tmux
set -g allow-passthrough on
```

Wrap the **whole OSC 52 sequence** in tmux’s DCS envelope, doubling every embedded ESC byte:

```rust
fn tmux_passthrough(sequence: &str) -> String {
    format!("\x1bPtmux;{}\x1b\\", sequence.replace('\x1b', "\x1b\x1b"))
}
```

Use this as an opt-in compatibility mode, not an unconditional response to `$TMUX`. Native handling generally needs no wrapping; nested tmux sessions require additional handling at each layer.

Recent tmux versions also support OSC 8 hyperlinks natively. Older versions or terminal combinations may require upgrades or passthrough.

Ship configurable link targets, plain OSC 52 by default, an optional tmux passthrough mode, and a short terminal/tmux setup guide. Neither feature is universally supported, so preserve readable paths and a selectable request ID as fallbacks.
