Every refactor breaks something: last week Tab-cycling between columns silently stopped working and nobody noticed for two days. Start with the behavior that broke: **Tab should move focus to the next column and wrap back to the first.** You can test that without opening a terminal.

Bubble Tea makes this practical because most behavior lives in three places:

- `Update` handles messages and changes state.
- `View` turns state into terminal output.
- Commands perform work and return messages.

For a ~1,500-line app, I’d start with direct `Update` tests, a few rendering checks, and one CI job.

**1. Turn last week’s bug into your first test**

Put the test in the same Go package as your model so it can inspect internal state. Adapt the model and field names here:

```go
func TestTabCyclesColumns(t *testing.T) {
	m := initialModel() // Use deterministic local data.

	// Assuming three columns and initial focus on column zero.
	for step, want := range []int{1, 2, 0} {
		next, _ := m.Update(tea.KeyMsg{Type: tea.KeyTab})
		m = next.(model) // Use *model if your model is a pointer.

		if m.focusedColumn != want {
			t.Fatalf(
				"Tab press %d: focused column = %d, want %d",
				step+1, m.focusedColumn, want,
			)
		}
	}
}
```

This example uses Bubble Tea v1’s message types; v2 uses a different keyboard API, but the testing approach is the same.

The test exercises the actual keyboard handler, including wrapping. Checking a helper such as `nextColumn()` alone could miss a broken key binding.

**2. Build a small behavior checklist**

Test the actions your team would notice losing:

| Behavior | Useful assertion |
|---|---|
| Tab / Shift+Tab | Focus advances, reverses, and wraps |
| Up / Down | Selection stays within valid bounds |
| Move card | Card leaves the source and appears in the destination |
| Empty column | Navigation and moving cards don’t panic |
| Edit mode | Typing edits text; navigation shortcuts behave as intended |
| Resize | Layout handles narrow and small dimensions |
| Save failure | An error becomes visible; edits remain recoverable |

Include sequences, such as “move the last card out of a column, then press Down.” Those often expose bugs that isolated key presses miss.

**3. Test rendering selectively**

Set an explicit terminal size by sending a `tea.WindowSizeMsg`, then call `View()`. Start with assertions that column titles, card text, and error messages appear.

A few golden-file tests—comparing rendered output with a checked-in expected file—can catch layout regressions. Keep them focused: whole-screen snapshots can become noisy whenever spacing or styling changes. Fix the size, test data, and color settings so output is deterministic.

**4. Keep disk and network work out of navigation tests**

Use an in-memory board for keyboard tests. For persistence, test the storage code separately using `t.TempDir()`.

When an operation returns a command, test both sides where relevant:

- The command produces the expected result message.
- `Update` handles success and failure messages correctly.

Remember that calling `Update` directly does **not** automatically execute its returned command.

**5. Run the tests on every pull request**

For GitHub Actions, a minimal workflow is:

```yaml
name: Go tests
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - run: go test ./...
      - run: go vet ./...
```

You don’t need terminal automation to get useful protection. Later, one pseudo-terminal smoke test can check startup, input delivery, and quitting; tools such as `github.com/charmbracelet/x/v teatest` support that style of testing—use the actual module path `github.com/charmbracelet/x/exp/teatest` if compatible with your Bubble Tea version.

Your first milestone can be small: **Tab regression test, card-movement test, empty-column test, and green CI.** Add a regression test whenever a bug appears, and before each refactor, cover the behavior you’re about to touch.
