I've got a Bubble Tea app in Go — a small kanban TUI, ~1500 lines — that my team relies on daily. Every refactor breaks something: last week Tab-cycling between columns silently stopped working and nobody noticed for two days. I want automated tests running in CI so this stops happening, but honestly I don't even know how you test a TUI. Where do I start?

codex
Start by testing the **keyboard behavior your team depends on**. You don’t need to launch a terminal to catch the Tab regression: Bubble Tea’s `Update` method accepts messages, so a test can send the same key message a terminal would send and inspect the resulting model.

For a 1,500-line app, I’d start with three layers, in this order.

**1. Test state changes through `Update`**

Write the test that would have caught last week’s bug. For example, assuming your model stores the selected column as an index:

```go
func TestTabCyclesColumns(t *testing.T) {
    m := newTestModel() // Three columns; column 0 selected.

    for _, want := range []int{1, 2, 0} {
        next, _ := m.Update(tea.KeyMsg{Type: tea.KeyTab})
        m = next.(model) // Use *model here if your model is a pointer.

        if m.selectedColumn != want {
            t.Fatalf("after Tab: selected column = %d, want %d",
                m.selectedColumn, want)
        }
    }
}
```

Adapt the constructor and field names to your app. This example uses the Bubble Tea v1 API.

That one test covers both advancing and wrapping around. Add tests for your other daily workflows:

- Moving a card between columns preserves its contents.
- Creating, editing, and deleting a card affects the intended card.
- Escape cancels an edit without saving.
- Navigation keys typed into an editor don’t also move the board.
- Empty columns and an empty board don’t panic.

Send messages through `Update` instead of directly calling navigation helpers. That exercises the key dispatch where regressions like yours often happen.

**2. Test rendering selectively**

Call `View()` with a known model and check that essential content appears: column titles, card titles, empty-state text, and editing prompts.

For a few representative screens, you can also use **golden tests**: compare the rendered string with an approved file. Set a fixed window size first, and keep color settings deterministic.

Don’t snapshot every screen variation. Whole-screen comparisons can produce lots of noise when spacing changes, while still missing broken interaction.

**3. Add a small integration test**

Once the state tests are working, use a harness such as Charm’s `teatest` to run the Bubble Tea program, send input, and check output or the final model.

Start with one short journey: open the board, press Tab, move a card, quit. This checks that program initialization and message handling work together. Most behavior should still live in the faster `Update` tests.

For CI, the initial requirement can simply be:

```sh
go test ./...
```

Run it on every pull request. Once persistence and background work have reliable test fixtures, add `go test -race ./...` as well.

If saving currently happens directly inside `Update`, introduce a small seam so tests can use an in-memory store or temporary directory. Keep asynchronous work in commands, and test the messages returned by that work separately. You don’t need a large architectural rewrite first.

**Your first milestone:** put the Tab-cycle regression test in CI, then add five or six tests for the workflows your team uses most. Whenever a bug appears, reproduce it with a failing test before fixing it. That gives you useful protection quickly, without turning testing into another refactor.
