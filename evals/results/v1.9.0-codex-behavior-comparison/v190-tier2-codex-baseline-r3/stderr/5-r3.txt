user
My Rust log-viewer TUI shows file paths and request IDs. Users keep asking for two things: click a path to open the file in their editor, and press y to copy the request ID. The catch is half of them run it over SSH, often inside tmux, so I can't just shell out to pbcopy/xclip. How do I make both features work, including the tmux case?

codex
Use **OSC 8 hyperlinks** for paths and **OSC 52 clipboard writes** for request IDs. These are terminal escape sequences: they travel over SSH to the user’s terminal, so you don’t need clipboard utilities on the remote machine.

### Clickable paths: OSC 8

Render the visible path inside a hyperlink:

```text
ESC ] 8 ; ; file://hostname/absolute/path ESC \
/absolute/path
ESC ] 8 ; ; ESC \
```

In Rust:

```rust
fn hyperlink(uri: &str, label: &str) -> String {
    format!("\x1b]8;;{uri}\x1b\\{label}\x1b]8;;\x1b\\")
}
```

Build the URI with a URL library so spaces, `#`, and other special characters are encoded correctly. Use absolute paths, and sanitize displayed log text so it cannot inject terminal control sequences.

**Opening in an editor is the terminal’s responsibility.** Users configure their terminal’s file-link handler and typically modifier-click the link. Over SSH, include the **remote hostname** in the URI. A remote `file://host/path` link does not automatically give the local editor access to that file; users need a handler that understands remote paths, an SSH-aware editor integration, or a remote filesystem mount. A configurable URI template is useful for those setups.

Also check your TUI library: some renderers strip or mismeasure embedded escape sequences. Prefer its hyperlink support where available.

### Copy on `y`: OSC 52

Base64-encode the selected request ID and write an OSC 52 sequence to the terminal:

```rust
use base64::{engine::general_purpose::STANDARD, Engine as _};
use std::io::{self, Write};

fn copy_request_id(id: &str) -> io::Result<()> {
    let encoded = STANDARD.encode(id.as_bytes());
    let mut out = io::stdout().lock();
    write!(out, "\x1b]52;c;{encoded}\x07")?;
    out.flush()
}
```

Here, `c` selects the clipboard. Emit this through your TUI’s output mechanism between rendering operations so writes cannot interleave.

The local terminal must support and permit OSC 52 clipboard writes. There is generally no reliable acknowledgment, so report “Copy sent to terminal” rather than claiming verified success. Request IDs are small enough to avoid typical payload limits.

### tmux: use its native support first

For clipboard writes originating in an application inside tmux, users generally need:

```tmux
# ~/.tmux.conf
set -s set-clipboard on
```

`on` lets applications inside tmux set the clipboard. `external` lets tmux itself set the outside clipboard but does **not** grant that ability to applications inside it.

tmux must also recognize OSC 52 support in the **outer terminal**. If detection fails, users can add a matching terminal feature, for example:

```tmux
# Match the actual outer terminal's TERM.
set -as terminal-features ',xterm-256color:clipboard'
```

Use a recent tmux with OSC 8 hyperlink support for clickable paths. SSH itself needs no special configuration.

If native clipboard forwarding cannot be used, offer an **explicit tmux passthrough mode**:

```rust
fn tmux_passthrough(sequence: &str) -> String {
    format!("\x1bPtmux;{}\x1b\\", sequence.replace('\x1b', "\x1b\x1b"))
}
```

Wrap the entire OSC 52 sequence with this function. The doubling of every inner `ESC` is required. This route needs:

```tmux
set -g allow-passthrough on
```

Do not automatically wrap everything merely because `$TMUX` is set: native forwarding is preferable, and nested tmux sessions require handling each layer.

For the app, expose `clipboard = auto | osc52 | tmux-passthrough | off` and configurable path-link templates. Keep paths readable and request IDs selectable when terminal features are unavailable.
