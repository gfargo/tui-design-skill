**Start by testing `Update` directly.** Bubble Tea lets you feed in a key message and inspect the resulting model without opening a terminal. That would have caught your Tab regression, and it runs with ordinary `go test` in CI.

Using the tui-design skill’s Go guidance, I’d build three layers, with most tests in the first.

**1. Turn the Tab bug into your first regression test**

Check `go.mod` for your Bubble Tea major version. This example assumes **v1** (`github.com/charmbracelet/bubbletea`); adapt the model constructor and fields to your app:

```go
// model_test.go — same package as your model
func TestTabCyclesColumns(t *testing.T) {
    m := newModel() // fixture with Todo, Doing, Done
    m.focusedColumn = 0

    for step, want := range []int{1, 2, 0} {
        next, _ := m.Update(tea.KeyMsg{Type: tea.KeyTab})
        m = next.(model) // use *model if yours is pointer-based

        if m.focusedColumn != want {
            t.Fatalf("Tab %d: focused column = %d, want %d",
                step+1, m.focusedColumn, want)
        }
    }
}
```

On **v2** (`charm.land/bubbletea/v2`), send:

```go
tea.KeyPressMsg{Code: tea.KeyTab}
```

Send the message through the **top-level `Update`**, rather than testing only a `nextColumn()` helper. That also catches regressions where an early return or child widget swallows Tab.

Next, cover the actions your team depends on:

- Shift+Tab cycles backward and wraps.
- Moving a card changes its column without losing or duplicating it.
- Navigation works when a column is empty.
- Editing and filtering route keys correctly; typing `q` doesn’t quit.
- Canceling an edit leaves the card unchanged.
- Save failures preserve the board and expose an error.

For async work, use a fake store. Test the returned command against that fake, then feed its success or failure message back into `Update`. Keep disk and network work inside commands; don’t make tests depend on real services or sleeps.

**2. Add a few rendered-frame tests**

State assertions catch “Tab didn’t change focus.” Render tests catch “focus changed, but users can’t see it.”

Build deterministic fixtures, send `tea.WindowSizeMsg`, and compare `View()` against reviewed golden files. Start with:

| Fixture | What it protects |
|---|---|
| Populated board, focused column | Visible focus and card layout |
| Empty board | Useful empty state |
| Error state | Error visibility without losing cards |
| 80×24 and 60×24 | Layout at common terminal sizes |
| Declared minimum and below it | Honest too-small behavior |

Pin terminal size, color profile, theme, data, and time. Include a card title with wide characters. Review golden diffs like code; don’t automatically regenerate them in CI.

**3. Add one program-level smoke test**

Charm’s `teatest` runs Bubble Tea with in-memory input/output, so CI doesn’t need an interactive terminal:

- v1: `github.com/charmbracelet/x/exp/teatest`
- v2: `github.com/charmbracelet/x/exp/teatest/v2`

Use it for one flow: **start → wait until ready → Tab → verify focus → quit**. Wait for observable conditions and set explicit completion timeouts.

Synthetic messages don’t verify terminal byte decoding or terminal restoration. Add one or two real PTY tests later if those become a risk; they shouldn’t carry your main regression suite.

**Put the first test in CI immediately.** Assuming GitHub Actions:

```yaml
# .github/workflows/test.yml
name: Test
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true
      - run: go test -race -timeout=2m ./...
```

For a 1,500-line app, you don’t need a testing framework or a major rewrite. Start with the Tab regression, prove the test fails when Tab handling is removed, and make that check required for merging. Then add tests around each daily workflow and every bug you fix.
