Start with a regression test for Tab **by calling `Update` directly**. Bubble Tea lets you test most behavior without opening a terminal: construct a model, send a key message, and inspect the returned state.

For a 1,500-line app, you can add this incrementally without a major refactor.

**1. Lock down column navigation first**

Here’s an illustrative test for Bubble Tea v1. Adapt the model constructor and field names to your app:

```go
package main

import (
    "testing"

    tea "github.com/charmbracelet/bubbletea"
)

func TestTabCyclesColumns(t *testing.T) {
    m := newModel() // fixture with three columns, first focused

    for step, want := range []int{1, 2, 0} {
        updated, _ := m.Update(tea.KeyMsg{Type: tea.KeyTab})
        m = updated.(model) // use *model if that's your implementation

        if m.focusedColumn != want {
            t.Fatalf(
                "Tab press %d: focused column = %d, want %d",
                step+1, m.focusedColumn, want,
            )
        }
    }
}
```

For Bubble Tea v2, import `charm.land/bubbletea/v2` and send:

```go
tea.KeyPressMsg{Code: tea.KeyTab}
```

Use the major version already in your `go.mod`; testing doesn’t require an upgrade.

This test exercises the app’s actual key routing, including wraparound. Testing only an extracted `nextColumn()` helper would miss a refactor that accidentally stops forwarding Tab.

Next, cover the behaviors your team depends on:

- Shift+Tab cycles backward, including wraparound.
- Up/down selection stays valid in empty and populated columns.
- Moving a card updates the source, destination, and selection correctly.
- Opening and dismissing an editor restores focus.
- Keys typed into an editor don’t trigger board shortcuts.
- Save failures retain the card and show an error.

**2. Keep side effects controllable**

`Update` should change state and return commands; disk or network work belongs inside those commands.

For a save flow, test two things separately:

- A fake storage implementation receives the expected card when the command runs.
- Sending a success or failure message into `Update` produces the correct state.

Use temporary directories for persistence tests. Keep tests independent of real team boards, wall-clock time, and network access. Always retain the model returned by `Update`.

**3. Add a few rendered-frame tests**

Correct focus state doesn’t guarantee a visible focus indicator. Golden tests compare `View()` output against a reviewed file and catch that second class of regression.

Start with a populated board, an empty board, and an error or editor state. Pin fixture data, terminal dimensions, theme, and color profile. Cover:

- **80×24:** normal board layout.
- **60×24:** narrow layout, ideally showing the focused column if three columns no longer fit.
- **Your minimum size:** an honest “terminal too small” state.

Send `tea.WindowSizeMsg` through `Update` before rendering, and test resizing an existing model too. Include a long title and a title containing wide Unicode characters to catch clipping errors.

Review golden diffs like code changes; don’t automatically regenerate them in CI.

**4. Use a harness only for a small integration layer**

Charm’s `teatest` runs the Bubble Tea program with in-memory input/output and works without a terminal in CI:

| Bubble Tea version | Harness import |
|---|---|
| v1 | `github.com/charmbracelet/x/exp/teatest` |
| v2 | `github.com/charmbracelet/x/exp/teatest/v2` |

Add one flow: start with fixture data → wait for the board → send Tab → verify the focused column → quit. Use bounded waits and an explicit final timeout, rather than sleeps.

`teatest` doesn’t use a real PTY, so it doesn’t prove raw-mode or terminal restoration behavior. Add one or two PTY smoke tests later if those are recurring risks; they shouldn’t carry the main suite.

**5. Run the tests on every pull request**

For GitHub Actions, assuming a root-level `go.mod`:

```yaml
name: Tests

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true
      - run: go test -race ./...
```

Make that job a required check before merging.

Your first milestone is small: **the Tab regression test, a handful of core workflow tests, and required CI**. Temporarily break the Tab handler locally and confirm the test fails. That gives you immediate evidence that this exact regression will be caught next time.
