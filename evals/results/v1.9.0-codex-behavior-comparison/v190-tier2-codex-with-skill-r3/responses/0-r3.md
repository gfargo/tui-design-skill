Start with a regression test for Tab **by calling `Update` directly**. Most Bubble Tea behavior can be tested with ordinary Go tests, without opening a terminal.

For a 1,500-line app, you don’t need a rewrite or a large testing framework. Build coverage in three layers.

### 1. Test keys and state first

Bubble Tea already gives you a useful testing boundary:

```text
model + message → updated model + command
```

Create a small board fixture, send a Tab message, and assert which column has focus. Test the parent model’s `Update`, so you also catch key-routing mistakes between the board and child components.

Here’s a **Bubble Tea v1** example. Adapt the constructor and field names to your app:

```go
package main

import (
    "testing"

    tea "github.com/charmbracelet/bubbletea"
)

func TestTabCyclesColumns(t *testing.T) {
    // Fixture: three columns, first column focused.
    m := newTestBoard("Todo", "Doing", "Done")

    for step, want := range []int{1, 2, 0, 1} {
        updated, _ := m.Update(tea.KeyMsg{Type: tea.KeyTab})
        m = updated.(model) // Use *model if yours has pointer receivers.

        if got := m.focusedColumn; got != want {
            t.Fatalf(
                "Tab press %d: focused column = %d, want %d",
                step+1, got, want,
            )
        }
    }
}
```

If your `go.mod` uses **`charm.land/bubbletea/v2`**, use that import and replace the key message with:

```go
tea.KeyPressMsg{Code: tea.KeyTab}
```

Use your existing major version; adding tests doesn’t require a migration.

Then cover the actions your team depends on:

| Behavior | Useful assertion |
|---|---|
| Tab / Shift+Tab | Focus moves and wraps correctly |
| Up / Down | Selection stays within bounds, including empty columns |
| Move card | Card leaves one column and enters the intended one |
| Delete / cancel | Cancel preserves the card; confirm removes it |
| Search or edit | Typing `q` doesn’t trigger the board’s quit handler |
| Resize | Focus and selection survive layout changes |
| Save failure | Changes remain recoverable and an error is visible |

Assert user-visible outcomes, rather than internal helper calls. As a sanity check, temporarily disable Tab handling: the new test should fail.

**For async work:** inject a fake storage dependency. Exercise the returned command against that fake, inspect its result message, then feed that message into `Update`. Test both success and failure. Direct `Update` tests don’t automatically execute returned commands.

### 2. Add a few rendered-frame tests

State tests catch broken navigation. They won’t catch a focus indicator disappearing.

Golden tests compare `View()` output against a reviewed file in `testdata/`. Start with just a few meaningful frames:

- A populated board with an unmistakably focused column.
- An empty board.
- A save error or confirmation dialog.
- The board at 80×24, 60×24, and your declared minimum size.

Send `tea.WindowSizeMsg` before rendering. Also test resizing an existing model: startup-only fixtures can miss stale layout calculations.

At 60 columns, verify your intended fallback—such as showing only the focused column—and below the minimum, verify the “terminal too small” state.

Keep fixtures deterministic: fixed card order, timestamps, dimensions, and styling. Pin color behavior too: v1 supports `lipgloss.SetColorProfile(termenv.Ascii)`; v2 program tests support `tea.WithColorProfile(colorprofile.ASCII)`. Review golden diffs instead of automatically accepting updates.

### 3. Add one program-level smoke test

Charm’s **teatest** runs the Bubble Tea program with in-memory input/output, so it works in CI without a terminal:

- v1: `github.com/charmbracelet/x/exp/teatest`
- v2: `github.com/charmbracelet/x/exp/teatest/v2`

Use it for one short flow: **start → wait for board readiness → Tab → verify focus → quit**. Use bounded waits for observable output, not arbitrary sleeps, and always set a final timeout.

Teatest doesn’t use a real PTY. Later, add one or two PTY tests if you need to verify actual keyboard decoding, terminal restoration, or suspend/resume.

### Put the first test in CI immediately

For GitHub Actions:

```yaml
# .github/workflows/test.yml
name: Test

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true
      - run: go test -race -count=1 -timeout=60s ./...
```

Make this check required before merging.

Your first milestone should be small: **Tab wrapping, card movement, empty-column navigation, and CI**. Those tests protect daily workflows immediately; add rendered frames and the smoke test next.
