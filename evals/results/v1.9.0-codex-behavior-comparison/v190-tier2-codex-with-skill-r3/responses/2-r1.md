Use **file-based tracing to capture the failing geometry**, then test both the rectangle math and the rendered frame. A one-row overlap suggests an off-by-one calculation or stale dimensions; the intermittent timing also makes queued resize events worth checking.

**(a) Debug without touching the terminal**

Initialize tracing before entering the TUI. For Tokio, a nonblocking writer keeps file I/O off the rendering task:

```rust
// tracing, tracing-subscriber (env-filter), tracing-appender
let file = std::fs::File::create("app.log")?;
let (writer, _log_guard) = tracing_appender::non_blocking(file);

tracing_subscriber::fmt()
    .with_env_filter(tracing_subscriber::EnvFilter::from_default_env())
    .with_ansi(false)
    .with_writer(writer)
    .init();

// Keep _log_guard alive until shutdown.
```

Run with `RUST_LOG=debug` and `tail -f app.log` in another terminal. `eprintln!` and `dbg!` also corrupt the display when stderr points at the same terminal. A debugger should likewise attach from another terminal or an IDE.

Log the resize event dimensions **and the actual draw dimensions**, plus the panel and footer rectangles:

```rust
tracing::debug!(?area, ?panel, ?footer, "frame layout");
```

Include a frame/event sequence number if you need to correlate async activity.

The geometry should follow these rules:

- Use `frame.area()` inside every draw. A queued `Event::Resize(w, h)` can already be outdated by the time you process it.
- Give one UI task ownership of `Terminal`, layout, and drawing; background tasks send messages.
- Treat resize as invalidating the display and schedule a draw.
- `Rect::bottom()` is **exclusive**. The last occupied row is `bottom() - 1`, when height is nonzero.
- A block’s borders are already inside its rectangle. Use `block.inner(panel)` for content; don’t add a border row to the panel’s height.

Reserve the footer first, then split panels **only inside the body**:

```rust
use ratatui::layout::{Constraint, Layout, Rect};

fn regions(area: Rect) -> (Rect, Rect) {
    let [body, footer] = Layout::vertical([
        Constraint::Min(0),
        Constraint::Length(1),
    ])
    .areas(area);
    (body, footer)
}
```

For any nonempty panel above the footer, assert:

```rust
debug_assert!(panel.bottom() <= footer.y);
```

Avoid “fixing” this by drawing the footer last: that can conceal overlapping rectangles.

**(b) Write a regression test at two layers**

First, extract your real layout into a pure function and assert that every panel stays within the body and does not intersect the footer. Cover odd/even heights, breakpoint neighbors, and nonzero origins such as `Rect::new(3, 2, 80, 24)`—that catches code that mistakes height for an absolute coordinate.

Then use Ratatui’s `TestBackend` to exercise the **production renderer**. Keep the same app and terminal across a shrink/grow sequence; isolated fresh renders can miss stale geometry:

```rust
use ratatui::{backend::TestBackend, Terminal};

#[test]
fn resize_keeps_panel_border_above_footer() -> std::io::Result<()> {
    let mut app = App::test_fixture(); // deterministic data and footer
    let mut terminal = Terminal::new(TestBackend::new(80, 24))?;

    for (w, h) in [
        (80, 24), // includes first draw
        (80, 23),
        (60, 12),
        (61, 13),
        (80, 24),
    ] {
        terminal.backend_mut().resize(w, h);
        terminal.autoresize()?;

        // If your app handles resize messages, drive that production
        // handler here too, before drawing.
        terminal.draw(|frame| app.draw(frame))?;

        insta::assert_snapshot!(
            format!("resize_{w}x{h}"),
            terminal.backend()
        );
    }

    Ok(())
}
```

Replace that sequence with the exact one captured in your logs. Review the expected snapshots with `cargo insta review`: verify the panel’s bottom border occupies the row above the footer and the complete footer remains visible. Also add direct assertions for those cells so an accidentally accepted snapshot cannot weaken the invariant. Text snapshots don’t assert styles; compare `Buffer`s if styling matters.

Test 80×24, a 60-column split, your declared minimum, and one size below it. At narrow widths, prioritize the primary pane and move secondary panels behind navigation; below the minimum, render a truthful “terminal too small” state. Keep one border per panel and avoid a redundant outer frame that consumes another pair of rows.

`TestBackend` verifies layout and rendering, not Crossterm’s real resize delivery or terminal cleanup. If deterministic tests pass while the live bug persists, add one PTY smoke test that resizes the running app and checks the final screen. That is where event ordering and terminal integration belong.
