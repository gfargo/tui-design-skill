Use three layers: **safe logging → frame history → React tree inspection**. A reducer running proves an action was processed; it doesn’t prove React committed different visible output.

1. **Check who owns terminal output.** Ink defaults to `patchConsole: true`: it intercepts `console.*`, prints above the live UI, and repaints. Garbling suggests the patch is disabled or something bypasses it—often `process.stdout.write()`, a logger writing directly to a stream, or a child with inherited stdio.

   Keep high-volume traces in a file and `tail -f` from another terminal. For occasional component diagnostics, use Ink’s `useStderr().write()`. Raw stderr is not isolated if it reaches the same terminal.

2. **Make rendered frames observable.**

   ```tsx
   render(<App />, {
     patchConsole: true,
     debug: true,
   });
   ```

   `debug: true` appends updates instead of rewriting the live region. Reproduce one action and inspect the resulting frames:
   
   - New value appears: investigate terminal output interference.
   - New value is absent: investigate state, subscriptions, and rendering.

3. **Inspect the component that should change.** Install the optional `react-devtools-core` dependency, run the CLI with `DEV=true`, and launch `npx react-devtools` separately. Inspect state and props from the reducer owner down to the visible leaf.

   Check these common causes:

   - **Same object returned:** mutating state and returning it can trigger React’s `Object.is` bailout. Return new objects along every changed path.
   - **Stale derived data:** check `useMemo` dependencies, `React.memo` comparators, and store selectors.
   - **Wrong state owner:** confirm the visible component subscribes to the provider/store receiving the action.
   - **Changing content inside `<Static>`:** already-rendered items are permanent; put changing values in the live tree.
   - **Hidden or clipped output:** check conditional rendering, `display`, dimensions, and overflow.

   Ink supports DevTools tree/props inspection, **not React Profiler recording**.

4. **Turn the reproduction into a small regression test.** Test the reducer’s value and identity changes first. Then drive the component with `ink-testing-library`, await the asynchronous update, and assert `lastFrame()` contains the new value. A reducer test alone won’t catch a disconnected or stale view.

If updates are merely delayed or the UI freezes, inspect blocking work next: synchronous subprocesses, large synchronous reads, or CPU loops block rendering and input. Use `node --cpu-prof` for performance investigation.

The useful checkpoint is: **action → new state identity → committed props/state → rendered text → terminal display**. Find the first boundary where the expected value disappears.
