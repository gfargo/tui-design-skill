A normal Rust process **can’t change its parent shell’s working directory**. `std::env::set_current_dir()` changes only the picker process’s directory; that change disappears when it exits.

The standard pattern is a **shell function wrapping the executable**:

1. The picker returns the selected directory.
2. The function runs `cd` inside the user’s existing shell.

For Bash or Zsh:

```sh
function cdp() {
    local selected
    selected="$(command my-picker "$@")" || return
    if [[ -n "$selected" ]]; then
        builtin cd -- "$selected"
    fi
}
```

Your Rust program writes just the selected path to stdout:

```rust
println!("{}", selected_dir.display());
```

Render the TUI to **stderr or `/dev/tty`**, since stdout is being captured. On cancellation, return a nonzero exit status or emit no path. Quoting `"$selected"` preserves spaces, and `--` handles paths starting with `-`.

**Yazi uses the same principle**, commonly through a temporary file: a shell wrapper passes `--cwd-file`, Yazi writes its final directory there, and the wrapper reads it and executes `cd`. That keeps the directory output separate from the terminal UI.

So yes, you can deliver the behavior users want—but the final `cd` must run in shell integration, not in the Rust child process.
