codex
For **Textual**, first separate the cost of **loading rows** from **interacting with the populated table**. For **Ink**, a working React DevTools connection does **not** establish that the Profiler is supported.

**Textual: measure a specific slow action**

Reproduce these separately with the same 50k-row dataset:

- Initial population.
- Scrolling and moving the cursor.
- Sorting, filtering, or updating cells.
- Resizing the terminal.

Time data preparation and table insertion independently with `time.perf_counter()`. Insertion timing alone misses layout and painting that happen afterward, so also capture a CPU profile while reproducing the sluggish interaction:

```bash
# Sampling profile; install py-spy separately.
py-spy record -o textual-profile.svg -- python -m your_app
```

Or use Python’s built-in profiler for call counts and cumulative time:

```bash
python -m cProfile -o textual.prof -m your_app
python -m pstats textual.prof
```

At the `pstats` prompt, use `sort cumulative` and `stats 30`. Deterministic profiling adds overhead, so use it to identify expensive call paths rather than judge responsiveness.

Look for where time accumulates:

| Hot path | What to investigate |
|---|---|
| Your formatting or data conversion | Repeated work; precompute reusable values |
| Rich measurement / column sizing | Expensive cell renderables; test fixed column widths |
| Layout / rendering | Frequent refreshes, changing dimensions, update frequency |
| Sorting / filtering | Work performed synchronously on the UI thread |

DataTable renders visible content, but storing, measuring, sorting, or updating 50k rows can still be expensive. Compare bulk `add_rows()` against repeated individual updates, and test fixed widths as a controlled experiment. Move blocking I/O to workers; CPU-heavy Python may need a process. Keep widget mutations on Textual’s UI thread.

**Ink: distinguish component rendering from the whole terminal pipeline**

React DevTools can inspect an Ink component tree without necessarily supporting profiling. Profiling depends on the Ink/React renderer version and whether the renderer build enables profiling. Browser React DOM profiling instructions don’t automatically apply.

For a reliable starting point, profile Node itself:

```bash
node --cpu-prof dist/cli.js
```

Exit normally after reproducing the slowdown, then load the resulting `.cpuprofile` in Chrome DevTools’ **Performance** panel. This captures JavaScript costs across your app, React reconciliation, Yoga layout, output generation, and terminal writes. Time spent waiting for the terminal may need separate wall-clock measurement.

If your renderer supports it, React’s `<Profiler onRender={...}>` helps locate costly component subtrees. Its timings describe React rendering, **not total terminal frame latency**. Buffer measurements or write them to a file so logging doesn’t distort the CLI’s output.

I couldn’t verify the current version-specific docs here, so I would check profiling support against your installed Ink and React versions before relying on the React DevTools Profiler.
