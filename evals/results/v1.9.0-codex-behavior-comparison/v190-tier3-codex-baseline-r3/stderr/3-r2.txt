codex
Treat these as two layers of profiling: **framework work** and **the full path to terminal output**.

**For Textual, first isolate which operation is slow.** With 50k rows, initial population, sorting, and scrolling can have very different bottlenecks.

1. Reproduce each separately: load the table, scroll continuously, sort, then update a small set of cells. Keep terminal size and data fixed.
2. Capture a CPU profile during the slow interaction:
   ```bash
   py-spy record -o profile.svg -- python app.py
   ```
   Or use Python’s built-in profiler:
   ```bash
   python -m cProfile -o app.prof app.py
   python -m pstats app.prof
   ```
   In `pstats`, enter `sort cumulative`, then `stats 30`. Exit the app normally so the profile is saved.
3. Inspect where time accumulates:

   | Hot area | What to investigate |
   |---|---|
   | Your loading/formatting code | Parsing, repeated conversions, expensive cell renderables |
   | Row insertion or sizing | Automatic column-width measurement, content-dependent row heights |
   | Sorting/filtering | Repeated full-table operations on the UI thread |
   | Layout, rendering, Rich measurement | Frequent refreshes, complex cells, changing dimensions |
   | Terminal writes | Output volume, terminal emulator, remote connection |

Textual’s `DataTable` renders the visible region, so **50k stored rows do not mean 50k rows are painted every frame**. Loading, measuring, sorting, and invalidating data can still be expensive.

Time your own population code with `time.perf_counter()`, but remember that insertion may schedule layout and painting for later. That measurement alone does not tell you when the table becomes responsive. Once the profile identifies a suspect, compare one change at a time—for example, fixed column widths, simpler cell values, or fewer update batches. Moving blocking I/O off the UI thread helps responsiveness; it won’t fix expensive rendering.

**For Ink, don’t assume your existing React DevTools debugging connection supports profiling.** Component inspection and profiling are separate capabilities, and profiling support depends on the Ink/React renderer version and build. A working component tree is not evidence that the Profiler works.

For an end-to-end CPU profile, use Node directly:

```bash
node --cpu-prof dist/cli.js
```

Exit normally, then load the resulting `.cpuprofile` in Chrome DevTools’ Performance panel. Look for application computation, React reconciliation, Yoga layout, output generation, and terminal writes.

If your renderer/build supports React’s `<Profiler>`, use its `onRender` callback to measure component commit frequency and render duration. Those timings **do not include the complete terminal rendering pipeline**. Save measurements to a file or buffer them so logging doesn’t distort the result.

I couldn’t verify the latest Ink documentation from this environment, so I’d check your installed Ink and React versions before relying on a specific DevTools profiling capability.
