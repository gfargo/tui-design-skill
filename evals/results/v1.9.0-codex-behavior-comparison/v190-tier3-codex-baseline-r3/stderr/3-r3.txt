codex
For Textual, first separate **loading the rows, responding to input, and painting the terminal**. A 50k-row table can be slow in any of those places, and each needs a different fix.

1. **Time population separately.** Use `time.perf_counter()` around data preparation and `table.add_rows(...)`. This measures insertion, but deferred layout and painting may happen afterward.
2. **Profile a repeatable interaction.** Load the table, scroll for a few seconds, sort once, then exit. Start with Python’s built-in profiler:

   ```bash
   python -m cProfile -o table.prof app.py
   python -m pstats table.prof
   ```

   At the `pstats` prompt:

   ```text
   sort cumulative
   stats 30
   ```

   Look for time in your callbacks, sorting, Rich text measurement, table sizing, layout, and rendering. Cumulative time includes callees; high call counts can reveal repeated work.
3. **Compare controlled variants.** Try 5k versus 50k rows, fixed column widths versus automatic widths, and plain strings versus styled cells. Keep the terminal size and interaction sequence identical.
4. **Compare headless and terminal runs.** Textual’s `App.run_test()` with Pilot is useful for reproducing interactions without terminal output. If only the real-terminal run is slow, investigate output volume and terminal rendering. Headless timings alone don’t measure the full user experience.

Textual’s development console helps inspect events and logs, but it doesn’t replace a CPU profile. Avoid logging every cell or event while measuring. Also, DataTable renders the visible region; 50k stored rows doesn’t automatically mean 50k rows are painted each frame.

For Ink, **having React DevTools connected for inspection does not guarantee profiling support**. Ink’s documented DevTools integration has historically supported debugging without supporting the DevTools Profiler. Check your installed Ink version before relying on the “Record” tab; the connection itself isn’t evidence that render timings work.

Use Node’s CPU profiler to find where the process spends time:

```bash
node --cpu-prof dist/cli.js
```

Exit normally, then load the resulting `.cpuprofile` in Chrome DevTools’ **Performance** panel. This can expose React reconciliation, Yoga layout, text processing, terminal writes, and application logic.

If your Ink version exposes the `render()` option `onRender`, its `renderTime` measurement can also track Ink render costs. Aggregate those measurements or write them to a file—printing a log on every render can distort the result.

The key distinction: **React component work, Ink layout/output work, and terminal painting are separate costs.** A React profiler alone wouldn’t cover all three, even where supported.
