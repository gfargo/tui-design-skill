**Yes—with shell integration. Your Rust executable alone cannot change the calling shell’s directory.** `std::env::set_current_dir()` changes only your process’s working directory; spawning `sh -c 'cd …'` changes only that child shell.

The standard pattern, used by yazi and ranger, is:

1. A function in the user’s current shell launches your TUI.
2. Your TUI writes the selected absolute directory to a temporary file, via something like `--cwd-file`.
3. After the TUI exits, the function reads that file and runs the shell’s own `cd`.

For your own tool, define the file format as **one NUL-terminated path**. Here’s a Bash wrapper users can put in `~/.bashrc`:

```bash
pickcd() {
    local tmp dir rc
    tmp=$(mktemp) || return 1

    command mypicker --cwd-file "$tmp" "$@"
    rc=$?

    if (( rc == 0 )) && IFS= read -r -d '' dir < "$tmp"; then
        if [[ -n "$dir" ]]; then
            builtin cd -- "$dir" || rc=$?
        fi
    fi

    command rm -f -- "$tmp"
    return "$rc"
}
```

Your Rust side should:

- Write the absolute selected directory only on an accepted selection; leave the file empty on cancellation.
- Restore the terminal before returning to the shell.
- Write raw path bytes followed by `\0`. On Unix, use `OsStrExt::as_bytes()` rather than `to_string_lossy()` so non-UTF-8 filenames survive.

The quoted `"$dir"` and `cd --` handle spaces and leading dashes; NUL framing also preserves newlines in directory names. **Treat the result as data; don’t `eval` it.** Ship equivalent wrappers for Zsh, Fish, or PowerShell as needed.

Capturing stdout is another valid transport, provided all TUI rendering goes to stderr or `/dev/tty`. A dedicated cwd file is convenient for a full-screen file manager because it keeps the result separate from terminal output. Launching a new shell in the selected directory is possible too, but creates a nested shell—it doesn’t move the original one.
