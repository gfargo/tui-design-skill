**Make Nerd Font icons opt-in, and treat API timeouts as a stale-data state.** Users should retain a readable, usable app in both cases.

**Icons**

- Default to ordinary Unicode symbols with text labels; offer an ASCII mode.
- Provide an explicit setting such as `icons = "none" | "nerd-v3"`. Document that users must select a Nerd Font in their terminal.
- Don’t try to detect font support: terminals expose no reliable query for active Nerd Font coverage. `$TERM` and “is a TTY” don’t establish it.
- Pin the Nerd Font generation you support: v3 changed some codepoints.
- Centralize glyph choices and spacing. Measure terminal cells rather than string length, and test alignment with icons enabled and disabled. Keep actions understandable without their icons.

**API timeouts**

Keep the last successful data visible, preserve selection and scroll position, and show a persistent, textual freshness warning:

```text
Wide / 80×24
Resources                 STALE 42s | request timed out
> api-east   healthy
  api-west   healthy
Retrying in 8s                         r retry | l log

60-column split
Resources | STALE 42s
> api-east   healthy
  api-west   healthy
Request timed out; retry in 8s
r retry | l log
```

Here, `STALE 42s` means “last successful update was 42 seconds ago”; the displayed health values remain historical.

- **First load, no cached data:** show “Couldn’t load resources: request timed out” with retry and cancel controls. Don’t present an empty result as success.
- **Background refresh:** retain the rows; use a small delayed activity indicator if needed. Avoid a blocking dialog or a fresh toast on every failed poll.
- **Repeated failures:** retry with capped exponential backoff and jitter; expose `r retry now`. Keep only one request in flight so slow requests don’t accumulate.
- **Recovery:** replace the data, clear the stale warning, and resume normal polling. Preserve selection by stable item ID.
- **Partial failure:** mark only the affected source stale and keep successful sources usable.

In Ratatui, perform requests in a Tokio task and send results through a channel to the app’s update loop. Store data, last-success time, in-flight status, error, and retry deadline separately; rendering reads that state without doing network I/O.

Keep the presentation quiet: one shared freshness warning, no repeated warning icons on every row, and no extra border around the error. At 60 columns, move status onto another line before truncating the failure or recovery action. Verify timeout → repeated failure → recovery transitions, plus frames at 80×24 and 60 columns using `TestBackend`.
