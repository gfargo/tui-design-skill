**For Textual, profile the slow interaction before changing the table. For Ink, your connected React DevTools cannot profile renders.**

**Textual: find which phase costs time**

`DataTable` already virtualizes rendering, but inserting, measuring, sorting, or transforming 50k rows can still be expensive.

1. Reproduce loading, scrolling, sorting, and filtering separately, using the same dataset and terminal size.
2. Attach a sampling profiler while reproducing one slow operation:

   ```sh
   py-spy record -o profile.svg --pid <pid>
   ```

   Stop recording with Ctrl+C and open the SVG flame graph. Attaching may require elevated OS permissions. If a quiet recording contains almost nothing, retry with `--idle`; py-spy normally excludes idle threads.

3. Look for time in your data processing, row insertion, Rich formatting/measurement, layout, or rendering. Add `time.perf_counter()` measurements around suspect operations, recording results to a file or Textual’s dev console. Timing `add_rows()` measures insertion, not necessarily the deferred layout and paint afterward.
4. Change the measured bottleneck and repeat the same interaction.

Two traps matter here:

- **`add_rows()` loops over `add_row()`**; switching to it does not provide a bulk-insert speedup.
- An `async def` handler still blocks the UI while doing synchronous work. Move suitable blocking preparation into `@work(thread=True)` and return UI changes through `self.app.call_from_thread(...)`. Plain `@work` does not make CPU work nonblocking; keep table mutations on the UI thread.

`textual console` helps inspect logs, and `textual diagnose` reports the environment. Neither is a performance profiler, and Textual has no built-in FPS overlay.

**Ink: use Node’s CPU profiler**

Ink’s React DevTools integration supports component-tree and props inspection, but its reconciler does not enable the flags required for React Profiler recording.

Run your compiled CLI with:

```sh
node --cpu-prof ./dist/cli.js
```

Reproduce the slow interaction, then exit normally so Node writes the `.cpuprofile`. Load it into Chrome DevTools or speedscope.

Look for repeated component work, Yoga layout, painting/output, synchronous I/O, and timers or spinners driving constant updates. In particular, **clipping a long list does not virtualize it**: mount only the visible slice. Also check unnecessary parent-driven renders and whether append-only output belongs in `<Static>`.

For both projects, compare profiles under the same workload; CPU profiles explain busy execution, while elapsed-time measurements help reveal waiting and terminal-output delays.
