**Profile a repeatable slow interaction before changing the table.** For Ink, **your React DevTools connection supports inspection, but not render profiling.**

**Textual: find which phase is slow**

Separate initial loading, scrolling, sorting/filtering, and live updates. Use the same 50k-row dataset and terminal size for each run.

1. Attach a sampling profiler, then reproduce one slow action:

   ```sh
   py-spy record -o profile.svg --pid <pid>
   ```

   Stop recording after the reproduction and open the flame graph. Attaching may require elevated OS permissions. If a mostly idle capture shows little, retry with `--idle`; py-spy normally excludes idle threads.

2. Look for where CPU time accumulates:

   | Hot path | What to investigate |
   |---|---|
   | Parsing, fetching, formatting | Data preparation versus table insertion |
   | Sorting/filtering callbacks | Full-dataset work on every keystroke |
   | Rich rendering, cell measurement, layout | Expensive cell content, automatic sizing, repeated invalidation |
   | Your event handlers/watchers | Rebuilding the table or processing all rows on each update |

3. Time data preparation and table insertion separately with `time.perf_counter()`. Record to a file or Textual’s console. Insertion timing alone does **not** include the deferred layout and paint that follows.

`DataTable` already virtualizes rendering; 50k rows does not mean it paints 50k rows per frame. Loading, measuring, sorting, and updating those rows can still be costly. Optimize the measured hot path.

A synchronous CPU-heavy function inside `async def` still blocks the UI. For blocking work, use `@work(thread=True)` and send UI changes through `self.app.call_from_thread(...)`. Plain `@work` does not move CPU work off the event loop.

`textual console` helps with logs; `textual diagnose` reports the environment. Neither is a performance profiler, and Textual has no built-in FPS overlay.

**Ink: use a Node CPU profile**

Ink’s reconciler does not enable the flags React’s Profiler needs, so the existing DevTools connection is useful for component trees and props, not profiling.

Run the built CLI with:

```sh
node --cpu-prof ./dist/cli.js
```

Reproduce the slowdown, then exit normally so Node writes the `.cpuprofile`. Open it in Chrome DevTools’ Performance panel or speedscope.

Inspect React reconciliation, Yoga layout, text processing, and your application callbacks. Common culprits include unnecessary parent-driven renders, long lists whose children remain mounted despite being clipped, and continuously running spinners. For lists, mount only the visible slice; clipping alone still leaves layout and paint work for every child.

For both projects, repeat the same interaction after each change and compare latency as well as the CPU profile—terminal output delays may not appear as a CPU hotspot.
