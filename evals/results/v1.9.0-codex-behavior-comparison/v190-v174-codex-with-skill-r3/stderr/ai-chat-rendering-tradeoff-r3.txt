## Classify the product first

Choose the output contract before choosing a framework or layout:

| Product shape | Default contract |
|---|---|
| One-shot CLI | No live full-screen UI. Stable stdout for results, stderr for diagnostics, meaningful exit codes. Load `cli-basics.md`. |
| Summon–choose–exit tool | Prefer inline when shell context matters. Put interactive chrome on stderr or `/dev/tty` and the selected result on stdout. Use full-screen only when a large preview or working set needs stable space. |
| Full-screen session | Use the alternate screen and a stable spatial model. Treat terminal restoration, resize, suspend, and redraw behavior as product requirements. |

Then name the workflow shape—persistent panels, Miller columns, drill-down stack, dashboard, IDE-style panes, overlay, or tabs—and verify it against `visual-patterns.md`. Sketch the states and layout before writing code: initial, loading, empty, partial, success, error, disconnected, and too-small (`visual-patterns.md` → *States*). In a design answer, include an ASCII sketch of the layout at the floor size (60 columns) next to the wide one.

## Preserve these cross-cutting contracts

### Terminal lifecycle

- Use the alternate screen for full-screen sessions; keep bounded and one-shot workflows inline when possible.
- Prefer framework-managed terminal cleanup. Restore raw mode, screen buffer, cursor, and input modes on every exit path, including errors and panics. Do not invent custom signal handling when the framework already owns it.
- Re-layout from the current frame or window size on resize. Coalesce bursts only when layout work is expensive.
- Treat final shutdown and temporary handoff as different boundaries. For an editor, shell, or supported suspend, prefer the framework's handoff API: pause UI input, restore the shell-facing terminal, wait, re-enter modes, reload externally mutable data, and force a full redraw. Redrawing only repaints the current model; it does not refresh changed data. Do not final-unmount an app that must resume, and do not assume POSIX signals exist on Windows.
- Keep logs and debug output away from the screen the TUI owns. Use a file, framework console, or separate diagnostic stream.

### Rendering, data, and performance

- Never block the UI/event thread on disk, network, or subprocess work. Return results through commands, messages, tasks, channels, or framework events.
- Render on input, data, resize, or intentional ticks; do not redraw unchanged state in an unconditional loop.
- Measure terminal cell width, not bytes, code points, `len()`, or JavaScript string length. Test CJK, combining marks, and emoji.
- Virtualize collections that can grow beyond a few hundred rows. Truncate rather than wrap inside tables; reveal full values in a detail view.
- Keep panel positions stable unless the user explicitly changes the layout. Spatial memory is part of navigation.

### Meaning and access

- Define semantic style tokens rather than scattering color literals. Honor `NO_COLOR` in automatic color mode and preserve meaning in monochrome.
- Never use color alone. Pair it with text, shape, position, or symbols, and provide an ASCII fallback when Unicode support is uncertain.
- Make every action keyboard-reachable. Mouse support may accelerate an action but must not gate it.
- Offer familiar navigation aliases only where they do not conflict with text entry or a complete bounded prompt keymap. Preserve the expected reserved-key behavior: `Ctrl+C` cancels or quits, and `Ctrl+Z` suspends through the framework. Which other keys are reserved, and why raw mode frees `Ctrl+S`, is in `interaction-patterns.md` → *Reserved keys*.
- Match discoverability to complexity: complete inline controls for bounded prompts; contextual hints, help, and optionally a command palette for action-rich full-screen apps.
- Provide a plain `--no-tui` or equivalent mode when automation or serious accessibility needs require linear output; `visual-patterns.md` → *Accessibility* defines what it must contain.

## Apply two review reflexes unprompted

These catch the failures users rarely name. Apply both to every layout you design or review, even when the question is about something else.

### Run a clutter audit

Make “busy” countable. Report:

- border-nesting depth—more than one border between the terminal edge and content is usually too much;
- how many signals encode the same state—`[PASS]`, green, a checkmark, and a row marker is four;
- markers present on every row, which therefore mark nothing;
- the share of cells spent on chrome, labels, and repeated boilerplate instead of data.

Name the exact borders, markers, labels, or repeated fields to remove. Do not stop at “simplify it.” Use the full method in `visual-patterns.md` → *The clutter audit*.

### Pressure-test the floor

State what happens at 80×24 and in a 60-column tmux split: which pane wins, what hides, what truncates, what becomes drill-down, and when the truthful “terminal too small” state appears. Every multi-column design needs a single-pane fallback. Use the breakpoint ladder and minimum-size method in `visual-patterns.md` → *Responsive design*.

## Build and verification discipline

Keep business state independent enough to test without a terminal. In MVU or immediate-mode systems, feed synthetic events into update logic and assert state. In retained/widget systems, drive the smallest widget or app harness that owns the behavior.

Use a bottom-heavy test pyramid:

1. Unit-test state transitions, parsing, sorting, filtering, and command construction.
2. Snapshot or golden-test rendered frames at pinned terminal sizes and color profiles, including 80×24, 60 columns, and the hard minimum.
3. Use one or two PTY end-to-end flows for lifecycle and real-keyboard integration, not as the primary suite.

Verify at least:

- normal exit, interrupt, error, and panic cleanup;
- resize, too-small behavior, and suspend/resume where supported;
- empty, loading, partial, error, disconnected, and large-data states;
- keyboard reachability, focus visibility, and help accuracy;
- `NO_COLOR`, 16-color or monochrome, ASCII fallback, and non-TTY output;
- wide characters, combining marks, truncation, sorting, and virtualization;
- no stdout corruption and no blocking I/O in the event/render path.
- for one-shot CLIs, stdout, stderr, and the exit code in golden tests, with no TTY and under `NO_COLOR` (`cli-basics.md` → *Testing one-shot CLIs*).

Use the ecosystem reference's exact testing and debugging APIs. Never print diagnostics into an active raw-mode or alternate-screen UI.

## Ink (vadimdemedes/ink)

**Architectural model: React for the terminal.** A custom `react-reconciler` renderer that commits to terminal-native host nodes (`ink-root`, `ink-box`, `ink-text`), runs Yoga layout, paints into a screen buffer, and rewrites the live output in a single buffered terminal write. By default each frame replaces the whole live region; `incrementalRendering: true` updates only the changed lines ([readme](https://github.com/vadimdemedes/ink/blob/v8.0.0/readme.md#incrementalrendering)).

Current major: **Ink 8** (8.0.x, October 2026); runtime floors are in the table above.

```tsx check=typescript/ink-hello
import React, {useState} from 'react';
import {render, Text, Box, useInput, useApp} from 'ink';

const App = () => {
  const [n, setN] = useState(0);
  const {exit} = useApp();

  useInput((input, key) => {
    if (key.upArrow) setN(c => c + 1);
    if (key.downArrow) setN(c => c - 1);
    if (input === 'q') exit();
  });

  return (
    <Box borderStyle="round" padding={1}>
      <Text color="green">Counter: {n}</Text>
    </Box>
  );
};

render(<App />);
```

### Lifecycle and terminal handoff

Ink 7.1+ (unchanged in 8.0) distinguishes permanent unmounting from a resumable terminal suspension (`suspendTerminal` is not in 7.0 or Ink 6). Keep signal policy at the render boundary and temporary ownership changes inside `useApp()`.

| Boundary | Ink 7.1+ contract |
|---|---|
| Normal exit | Use `useApp().exit(...)` inside the tree or the render handle's `unmount()` outside it. At the top level, await `waitUntilExit()` before post-run output or process termination so pending terminal writes finish. |
| SIGINT / SIGTERM | `exitOnCtrlC` handles Ctrl+C bytes while stdin is raw; it is not a SIGTERM handler. If the host requires graceful signals, register them once at the process boundary, unmount, await `waitUntilExit()`, set the exit status, and remove listeners. Do not call `process.exit()` before cleanup flushes. To cancel work on the first Ctrl+C, see *Long-running work and Ctrl+C*. |
| Interactive child | Use `await suspendTerminal(async () => runChild())`. Ink pauses input and rendering, restores terminal modes, runs the callback even without an interactive TTY, and re-enters with a full redraw in `finally`. Reload child-mutated data afterward because redraw preserves the existing React state. For the manual form, always `await suspension.resume()` in `finally` or use `await using`. Do not unmount. |
| Foreground suspend | Ink has no separate high-level job-control action. If a Unix-only Ctrl+Z feature is necessary, perform SIGTSTP inside `suspendTerminal` and let its resume path re-enter and redraw; expose a different action on Windows. |

The tagged [`suspendTerminal` documentation](https://github.com/vadimdemedes/ink/blob/v8.0.0/readme.md#suspendterminalcallback) covers callback, manual, non-interactive, and nesting behavior. A second overlapping suspension is an error, so centralize ownership.

**Inline or alternate screen.** Inline is the default: the live region sits in the scrollback, and permanent lines go above it through `<Static>`, `useStdout().write()`, or the patched `console.*`. `render(<App />, {alternateScreen: true})` (Ink 7+) enters the alternate screen and restores the terminal on exit. It applies only in interactive mode (ignored in CI or with piped stdout), and teardown-time output is discarded, so print the final summary after `await waitUntilExit()`.

### Primitives

Ink ships only a handful of components — everything else composes from these:

- **`<Text>`** — only place strings can live. Props: `color`, `backgroundColor`, `bold`, `italic`, `underline`, `inverse`, `dimColor`, `wrap`, `strikethrough`. Strings as direct children of `<Box>` will throw — they must be wrapped.
- **`<Box>`** — flexbox container. Props: `padding`, `paddingX/Y/Top/Right/Bottom/Left`, `margin*`, `borderStyle`, `borderColor`, `borderTop`/`Bottom`/`Left`/`Right` (selective borders), `width`, `height`, `minWidth`/`maxWidth` (numbers only in Ink 8), `flexDirection`, `flexGrow`, `flexShrink`, `flexBasis`, `justifyContent`, `alignItems`, `gap`, `display: 'flex' | 'none'`, `overflow`/`overflowX`/`overflowY`. Ink 8 adds `contentOffsetX`/`contentOffsetY` for scrolling: give a fixed-height viewport `overflow="hidden"`, wrap the content in a `flexShrink={0}` box that carries any padding, and clamp the offset to `content.height - clientHeight` from `useBoxMetrics()`. That suits modest content; for long lists see *Lists, focus, and tables*.
- **`<Newline>`** — newline characters; only valid inside `<Text>` (use `gap` or margin between boxes). **`<Spacer>`** — flex-grow filler.
- **`<Static>`** — renders items permanently above the live UI; once rendered, never re-renders. Suited to log streaming.
- **`<Transform>`** — wraps children and transforms their rendered string. Used for gradients and OSC 8 hyperlinks.

### Layout

Yoga (Meta's open-source flexbox engine, same as React Native). No CSS, no className — props on `<Text>` and `<Box>`. Border styles come from `cli-boxes`: `single`, `double`, `round`, `bold`, `singleDouble`, `doubleSingle`, `classic`, or a custom `BoxStyle` object.

### Hooks

Ink-specific (items marked 7+ are not in Ink 6):
- **`useInput((input, key) => ...)`** — keyboard events. `key` is `{upArrow, downArrow, leftArrow, rightArrow, return, escape, tab, backspace, delete, ctrl, shift, meta, pageUp, pageDown, home, end}` (plus Kitty-protocol extras). Ink 8 drops mouse, focus, and cursor-position reports rather than passing them as typed text, so mouse support must parse raw stdin.
- **`useApp()`** — `{exit(errorOrResult?), waitUntilRenderFlush (7+), suspendTerminal (7.1+)}`. Pass an `Error` to `exit` to reject the render handle's `waitUntilExit()`; there is no separate error variant. Use `suspendTerminal` for a resumable interactive child, not final shutdown.
- **`useStdin()`** — `{stdin, setRawMode, isRawModeSupported}`. **`useStdout()`** / **`useStderr()`** — write outside the live UI; Ink 8 types the streams generically, so read the size from `useWindowSize()`, not `stdout.columns`.
- **`useFocus({autoFocus, isActive, id})`** — Tab-focusable component. **`useFocusManager()`** — `{focus(id), focusNext, focusPrevious, enableFocus, disableFocus, activeId (7+)}`.
- **`useWindowSize()`** (7+) — `{columns, rows}`, updates on resize. **`useCursor()`** — position the real terminal cursor (IME-friendly input).
- **`usePaste(callback)`** (7+) — bracketed-paste events, so pasted text arrives as one chunk instead of spraying through `useInput` character by character.
- **`useAnimation()`** (7+) — frame ticker; `isActive: false` stops it, and turning it back on resets the counters to 0 (it does not resume). **`useBoxMetrics()`** (7+) — measured box size; Ink 8 adds `clientWidth`/`clientHeight`, the size inside its borders.

Standard React hooks all work. For larger apps use **Zustand** (recommended), **Jotai**, or `useReducer` + Context.

### Lists, focus, and tables

- **Virtualize by slicing.** `contentOffsetY` only shifts and clips: Yoga still lays out and Ink still paints every child, so 20,000 rows cost 20,000 rows per frame. Mount only `items.slice(top, top + height)` in a fixed-height box.
- **Every mounted `useInput` fires on every key** unless its `isActive` is false. `useFocus` only tracks which component Tab selected; it mutes nothing. Gate each handler with `{isActive: isFocused}` (or a mode flag, so the list behind a dialog stops moving).
- **Tables keep one row to one line**, which the slice math assumes: give each cell a fixed-`width` `<Box>` and `<Text wrap="truncate-end">`. The default `wrap` grows the row.

```tsx check=typescript/ink-virtual-list
import React, {useState} from 'react';
import {Box, Text, useFocus, useInput} from 'ink';

const VirtualList = ({items, height, width}: {items: string[]; height: number; width: number}) => {
  const {isFocused} = useFocus();
  const [selected, setSelected] = useState(0);
  useInput((_input, key) => {
    if (key.downArrow) setSelected(i => Math.min(items.length - 1, i + 1));
    if (key.upArrow) setSelected(i => Math.max(0, i - 1));
  }, {isActive: isFocused});

  const top = Math.max(0, Math.min(selected - Math.floor(height / 2), items.length - height));
  return (
    <Box flexDirection="column" width={width} height={height}>
      {items.slice(top, top + height).map((item, i) => (
        <Text key={top + i} wrap="truncate-end" inverse={isFocused && top + i === selected}>{item}</Text>
      ))}
    </Box>
  );
};
```

### Long-running work and Ctrl+C

Ink renders, reads keys, and runs timers on one event loop. `execSync`, `spawnSync`, `readFileSync` on a big file, or a long CPU loop freezes the spinner and queues keystrokes until it returns. Use `execFile`/`spawn`, `fs/promises`, or a worker thread, plus an `AbortSignal`.

By default Ink quits on Ctrl+C before `useInput` sees it. For "first cancels, second quits", pass `exitOnCtrlC: false` and handle `key.ctrl && input === 'c'` in an always-active `useInput`: with no active input hook raw mode is off and Ctrl+C is SIGINT again.

```tsx check=typescript/ink-cancel
import React, {useEffect, useRef, useState} from 'react';
import {render, Text, useAnimation, useApp, useInput} from 'ink';
import {execFile} from 'node:child_process';

const Build = ({cmd, args}: {cmd: string; args: string[]}) => {
  const {exit} = useApp();
  const [status, setStatus] = useState('running');
  const abort = useRef(new AbortController());
  const {frame} = useAnimation({interval: 80, isActive: status === 'running'});
  useEffect(() => {
    execFile(cmd, args, {signal: abort.current.signal}, error => setStatus(error ? 'stopped' : 'done'));
  }, []);
  useInput((input, key) => {
    if (!key.ctrl || input !== 'c') return;
    if (status === 'running') abort.current.abort();  // first Ctrl+C cancels
    else {
      process.exitCode = 130;                         // second quits
      exit();
    }
  });

  return <Text>{status === 'running' ? `${'|/-\\'[frame % 4]} ${cmd}` : status}</Text>;
};

render(<Build cmd="npm" args={['run', 'build']} />, {exitOnCtrlC: false});
```

### ink-ui (vadimdemedes/ink-ui)

The companion library of themeable widgets:

- `<TextInput>`, `<EmailInput>`, `<PasswordInput>` — uncontrolled inputs: `defaultValue`, `onChange`, `onSubmit`, and no `value` prop (issue #20), so remount with a new `key` to clear one. Every input listens to every key unless `isDisabled`, and none integrates with `useFocus`: pass `isDisabled={!isFocused}`.
- `<Select>`, `<MultiSelect>`, `<ConfirmInput>` (y/n), `<ProgressBar>`, `<Badge>`, `<StatusMessage>`, `<Alert>`, and `<Spinner>` (use it inside Ink, not `ora`).

Theming via theme objects passed at the root. @inkjs/ui has had no release since 2.0.0 (May 2024) but works on Ink 8; fork or wrap any component you need to change.

### Testing — ink-testing-library

```tsx check=typescript/ink-testing-library
import {render} from 'ink-testing-library';

const tick = () => new Promise(resolve => setTimeout(resolve, 0));

const {lastFrame, rerender, stdin, frames, unmount} = render(<App />);
expect(lastFrame()).toContain('Counter: 0');  // frame includes the round border
stdin.write('\u001B[A');  // up arrow — see the input caveat below
await tick();             // input and re-render are asynchronous
expect(lastFrame()).toContain('Counter: 1');
unmount();
```

`renderToString()` (Ink 6.8+) renders synchronously for tests. **Staleness caveat.** ink-testing-library 4.0.0 was built against Ink 5 / React 18 (May 2024; unmaintained and still the latest release) but installs and works with Ink 6.8, 7.1, and 8. `stdin.write` drives `useInput` and `usePaste` as long as the test awaits after each write, because frames update asynchronously (the "stdin.write() does not trigger useInput" report reproduces only on Ink 5.0.1). Frames are text only because chalk sees a non-TTY stream (set `FORCE_COLOR=1` to assert styles). Add a few PTY-level tests (**node-pty** + `strip-ansi`) for real keyboard flows. Both packages are ESM-only; prefer vitest over Jest.

### Debugging

- **`console.log` is not lost.** The `patchConsole` render option defaults to `true`: Ink intercepts `console.*`, renders the message above the live output, and repaints. If console output *is* garbling the screen, something bypassed the patch: direct `process.stdout.write` or child-process stdio inherited straight to the terminal.
- **`render(<App />, {debug: true})`** renders every update as separate appended output instead of diffing in place, the best tool for "which frame went wrong".
- **React DevTools:** install the optional `react-devtools-core` peer, run your CLI with `DEV=true`, and launch `npx react-devtools` separately to inspect the live component tree. **Tree/props inspection only, not profiling:** Ink's reconciler sets none of the flags React's Profiler needs.
- **High-volume tracing** goes to stderr (`useStderr().write()`) or a file you `tail -f`, never stdout; Ink owns it.
- **Profiling:** `node --cpu-prof` is the real path; it writes a `.cpuprofile` on exit, loadable in Chrome DevTools' Performance panel or `speedscope`. Common Ink cost sinks: unmemoized components re-rendering on every parent update; `<Static>` misuse (static content left out of it, or changing content put in it); a mounted-but-hidden long list (see *Lists, focus, and tables*); and an always-animating leaf such as `ink-spinner` keeping the render cycle busy.

### Pastel — Next.js-style filesystem routing

`vadimdemedes/pastel` builds the command tree from the filesystem: each file under `commands/` is a command (`index.tsx` is `myapp`, `user/add.tsx` is `myapp user add`) exporting a default React component plus optional `args`/`options` Zod schemas. Pastel 4 calls Ink's `render()` without options, so `alternateScreen`, `kittyKeyboard`, `incrementalRendering`, and `concurrent` can't be set (issue #43); call `render()` directly when you need them.

### Strengths and weaknesses

Ink's strengths are the declarative React model and Yoga flexbox layout. Weaknesses:
- **Heavy startup**: roughly 150–250 ms to the first frame (measure with `hyperfine`); give `--version` and completion commands a fast path that bypasses Ink.
- **High-frequency re-renders used to flicker.** Ink 6.7+ ships synchronized updates, which largely fixed this. When streaming LLM tokens or tailing logs, still prefer `useDeferredValue` (fully functional only with `render(<App />, {concurrent: true})`) or manual debounce, and `<Static>` for append-only logs. Ink 8's `incrementalRendering: true` rewrites only the changed part of each line, and a lower `maxFps` (default 30) cuts churn further.
- **Screen-reader support is opt-in and partial.** Ink 6.2 added `aria-label` and `aria-hidden` (on `<Box>` and `<Text>`), `aria-role` and `aria-state` (on `<Box>`, from fixed lists), and a screen-reader renderer that turns on only through `render(..., {isScreenReaderEnabled: true})` or `INK_SCREEN_READER=true`. Nothing detects a screen reader; `useIsScreenReaderEnabled()` only reports that flag. The renderer prints linear text without borders or color and replaces children with their `aria-label`, but it still erases and rewrites the whole live region on every change. In that mode, move finished output into `<Static>`, keep the live part small, and stop per-tick spinners and timers. Design guidance: `visual-patterns.md` → *Accessibility*.

### Ink pitfalls

1. **`nodemon` breaks Inquirer/Ink arrow keys.** Use `nodemon --no-stdin` or `node --watch`.
2. **Ink 7 fixed Backspace reporting as `key.backspace`.** Old input handlers that check `key.delete` for Backspace silently break on upgrade—check `key.backspace`.
3. **Ink 8 upgrades break in three places:** percentage `minWidth`/`maxWidth` (numbers only now), `useStdout().stdout.columns` (no longer typed; use `useWindowSize()`), and `useInput` handlers that parsed mouse or focus reports (now dropped).

## Modern prompts: @clack/prompts

`@clack/prompts` has largely displaced Inquirer for new wizard-style CLIs. Stable at 1.x (bomb.sh/clack); used by **create-vite, `sv` (Svelte's CLI), and create-t3-app**. create-astro ships the same look through its own `@astrojs/cli-kit` rather than Clack.

```ts check=typescript/clack
import {intro, outro, text, confirm, select, spinner, isCancel, cancel} from '@clack/prompts';

intro('create-my-app');

const name = await text({
  message: 'Project name',
  validate: v => !v ? 'Required' : undefined,  // v is string | undefined
});
if (isCancel(name)) {
  cancel('Cancelled');
  process.exit(130);
}

const framework = await select({
  message: 'Pick a framework',
  options: [
    {value: 'react', label: 'React'},
    {value: 'vue', label: 'Vue'},
    {value: 'svelte', label: 'Svelte'},
  ],
});
if (isCancel(framework)) {
  cancel('Cancelled');
  process.exit(130);
}

const s = spinner();
s.start('Installing dependencies');
await install();
s.stop('Dependencies installed');

outro(`You're all set!`);
```

**Components:** `intro`/`outro`, `text`, `password`, `confirm`, `select`, `multiselect`, `autocomplete`, `path`, `date`, `spinner`, `progress`, `tasks`, `note`, `log.*`, `group`, and more. `validate` also accepts a Standard Schema validator (Zod, Valibot, ArkType) or an async function.

**`isCancel(value)`** is critical — it detects Ctrl+C per prompt and lets you clean up gracefully. Exit 130 on cancel, not 0, so `cli && next` stops; Clack's own `cancel()` example exits 1. Its look suits a `create-*` scaffolder.

## @inquirer/prompts

The modern modular rewrite of Inquirer — TypeScript-first packages that replaced the legacy monolithic `inquirer`. The workhorse for prompt-heavy CLIs:

```ts check=typescript/inquirer
import {input, select, confirm, password} from '@inquirer/prompts';

try {
  const name = await input({message: 'What is your name?'});
  const role = await select({
    message: 'Choose a role',
    choices: [
      {name: 'Admin', value: 'admin'},
      {name: 'User', value: 'user'},
    ],
  });
} catch (error) {
  if (error instanceof Error && error.name === 'ExitPromptError') process.exit(130);  // Ctrl+C
  throw error;
}
```

Ctrl+C rejects the prompt with `ExitPromptError`; uncaught, it prints a stack trace in the user's terminal. Catch it as above ([recipe](https://github.com/SBoudrias/Inquirer.js/blob/ea3130ebc609a6a3910b5397244044de7eda3d05/packages/prompts/README.md#handling-ctrlc-gracefully)).

It ships one package per prompt (`@inquirer/input`, `select`, `checkbox`, …). **Inquirer over Clack:** complex flows with conditional questions, validation chains, custom prompt types, i18n. **Clack over Inquirer:** minimal API and look, scaffolding a `create-*` tool.

## Color libraries

| Library | Size | Speed | API | Best for |
|---|---|---|---|---|
| **picocolors** | 7 KB | Fastest single-style | Functional only: `pc.red('hi')` | Tooling internals (PostCSS, SVGO, Stylelint, Browserslist, Babel, Prettier, Vite all use it) |
| **chalk** | ~56 KB (v6) | Slower; chainable | `chalk.red.bold('hi')` | End-user CLIs with frequent chaining; truecolor; familiar |

Color-disable behavior varies by library and version, so treat `NO_COLOR`, non-TTY output, and an explicit `--color` override as an application-level output policy and configure or bypass the library accordingly. chalk is ESM-only from v5 (see Runtime floors and ESM). For zero dependencies, `node:util` `styleText` (added in Node 20.12, stable since 22.13; honors `NO_COLOR`/TTY since 20.18/22.8; hex colors since 24.16/26.1) covers basic styling.

## Other utilities

- **ora** — single spinner (outside Ink; inside it use `<Spinner>` from `@inkjs/ui`). **cli-progress** — single and multi-bar progress with ETA (outside Ink).
- **listr2** — hierarchical animated task list with concurrency, retries, rollback. Renderers: `default` (live), `simple` (line-per-task, CI-friendly), `verbose`, `silent`, `test`. Used by Angular CLI and Electron Forge.
- **boxen** — text in boxes. **update-notifier** — checks the npm registry for newer versions and shows a boxed notice. **terminal-link** — OSC 8 hyperlinks with a plain-URL fallback. **string-width** — cell width for strings (CJK, emoji).

## Argument parsers

| Parser | Adoption | Style | Best for |
|---|---|---|---|
| **commander** | The most downloaded by a wide margin | Fluent API | The default (webpack-cli, Babel CLI, Svelte's `sv`); floors in Runtime floors and ESM |
| **yargs** | Very high | Fluent + middleware | Best validation; used by Jest and nyc |
| **citty** | Growing | TS-first, declarative | UnJS ecosystem (Nuxt, Nitro, unbuild) |
| **cac** | Niche | One ~20 KB file, no deps | Vite uses it; ESM-only since v7; use ≥ 7.0.1, which fixes a prototype-pollution bug with dotted option names |
| **oclif** | Plugin marketplace | Class-per-command | Heroku, Salesforce, Shopify CLI; heaviest startup of the group |
| **node:util.parseArgs** | stdlib | Argument parsing only | Stable since Node 20; zero-dep |

```ts check=typescript/commander
import {Command} from 'commander';

const program = new Command();
program
  .name('myapp')
  .description('CLI to do things')
  .version('1.0.0');

program.command('greet')
  .description('Say hello')
  .option('-n, --name <name>', 'who to greet', 'world')
  .action(({name}) => console.log(`Hello, ${name}!`));

program.parse();
```

With any `async` action, call `await program.parseAsync()`: `parse()` returns before the action settles, so a rejection escapes as an unhandled rejection. For an Ink action, `await` the render handle's `waitUntilExit()` inside it.

## OpenTUI (anomalyco/opentui)

The credible new entrant, built by Anomaly: TypeScript bindings over a Zig native core. Double-buffered rendering with alpha blending, scissor clipping, per-node mouse hit testing. Packages: `@opentui/core` (low-level), `@opentui/react` and `@opentui/solid` (React and SolidJS renderers), and `@opentui/three` (a Three.js WebGPU renderer that rasterizes 3D scenes into terminal cells).

Powers **opencode** (Anomaly's terminal coding agent). **Choose if** pushing past Ink's performance ceiling — animations, real-time streaming with low latency, or complex layouts where Yoga's CPU cost matters. **Trade-off:** v0.x churn (0.6 moved layout and painting into the native core, and 0.6 and 0.7 each broke custom renderables; 0.7 also dropped the screen-sized hit grid and reads renderable hooks from the class at construction), a smaller community, and a native binary in the install. `@opentui/core` 0.6+ declares `engines` of Bun ≥ 1.3.14 or Node ≥ 26.4. Read the [0.7.0 release notes](https://github.com/anomalyco/opentui/releases/tag/v0.7.0) before upgrading.

## blessed / terminal-kit

Retained-mode classics, pre-Ink era. **blessed** (ncurses in pure JS; last release 0.1.81, September 2015) is abandoned, and its fork **neo-blessed** is also unmaintained (last publish 0.2.0, June 2018). **terminal-kit** offers cursor control, screen buffers, input fields, menus, and half-block truecolor images (no Sixel). Choose them only for precise damage-region control or legacy code; prefer Ink for new TUI apps.

## Cross-library pitfalls

1. **Restore terminal state on exit.** Ink: `exit()` or `unmount()`, then await `waitUntilExit()`; blessed: `screen.destroy()`. Ink's Ctrl+C handling does not cover SIGTERM (see Lifecycle). ESM/CJS and Node floors: see Runtime floors and ESM.
2. **Detect non-TTY and CI** (`process.stdout.isTTY === false`, `process.env.CI`) and degrade to plain output; spinners and prompts must not run there. Raw mode needs `process.stdin.isTTY`; guard it.
3. **Cell width**: use `string-width` (Ink does), never `.length`.
4. **Frequently-invoked CLI startup**: lazy-load subcommand modules and give `--version`/`--help` a fast path.
5. **Don't mix raw-mode libraries** (Ink + ora, Ink + blessed → broken). Older `cmd.exe` lacks some ANSI; target Windows Terminal.
6. **Prompts and Ink draw on stdout by default.** For a summon–choose–exit tool whose result goes to stdout, redirect the chrome: Clack takes `output: process.stderr` on each call (`intro`, `cancel` and `spinner` too), Inquirer takes `{output: process.stderr}` as its second argument, and Ink takes `render(<App />, {stdout: process.stderr})`.

## Stack recommendations by project shape

| Project shape | Stack |
|---|---|
| Simple non-interactive CLI (~50 ms cold start, 19 packages, under 1 MB installed) | `commander + picocolors + ora` |
| Interactive setup wizard (`create-*` tool) | `@clack/prompts + picocolors + commander` |
| Complex CLI with tasks | `commander + @inquirer/prompts + listr2 + chalk + boxen + update-notifier` |
| Full TUI app | `ink + @inkjs/ui + zustand + commander + ink-testing-library` |
| Heroku-class plugin CLI | `oclif + ink + chalk + listr2` |
| Performance-critical / animated TUI | `@opentui/core` or `@opentui/react` |

## The seven canonical layouts in detail

Pick the layout from the user's loop, then sketch it at the floor size before writing code. The table is the decision; the thumbnails show each layout wide (left) and at its 60-column fallback (right), drawn in ASCII so they survive any terminal.

| Layout | Use when | Avoid when | 60-column fallback | Exemplars |
|---|---|---|---|---|
| **Persistent multi-panel** | Users watch several related views at once; data is read at a glance; numeric jumps (`1`–`5`) make sense | Each pane needs full attention, or the total would overwhelm a small terminal | Show the focused panel only, with the others as tabs or `1`–`5` jumps | lazygit (5 left panels plus one right), btop, htop (header, list, F-key footer) |
| **Miller columns** | Hierarchical data (filesystems, JSON, K8s trees) where parent context and a preview matter | Non-hierarchical data, or terminals under 80 columns | One pane (the middle column); the preview opens on demand | yazi (`[1, 4, 3]`), ranger, nnn, lf, broot |
| **Drill-down stack** | Many resource types to pivot between; each detail view deserves the full screen; command-mode navigation fits | Users must compare two things side by side, or the stack would pass three levels | Unchanged: one view at a time is the native shape | k9s, lazydocker, gh dash |
| **Widget dashboard** | Monitoring where users compose their own view and each widget updates on its own cadence | Static data, or users who want one curated experience | One widget at a time with a next-widget key | btop, bottom, glances, gtop |
| **IDE three-panel** | Compose, execute, inspect workflows with a navigator beside the work | Pure browsing with no composition step | The main panel only; the sidebar and output become toggles | Posting, Harlequin |
| **Overlay / popup** | Summon, choose, output, exit; shell-pipeline tools; replacing a built-in such as Ctrl+R | Long-running interactions, or anything that keeps state between runs | Unchanged: shrink the preview first | fzf, atuin, zoxide with fzf, gum |
| **Tabbed within a panel** | One panel needs several related views of the selected object | Unrelated tabs (use panels) or more than 5–6 tabs | Collapse the tab row to the active tab with a count and `[`/`]` | lazygit's branch tabs, lazydocker's right pane |

### Notes by layout

- **Multi-panel:** the focus cue must survive `NO_COLOR` (ranking in `interaction-patterns.md` → *Focus indicators*). Make the footer hint bar panel-aware (`c` does different things in lazygit's Files and Commits panels), and let numeric jumps work from any panel.
- **Miller columns:** the middle column is the widest because it is where the user works. The preview follows the selection live; debounce it when it is expensive.
- **Drill-down stack:** show the current address in the status bar (`cluster/namespace/pods/my-pod-7d9f`). `Esc` always backs up one level, so the user never feels trapped. Keep a stack of view-state objects: push saves the current view, pop restores it.
- **Widget dashboard:** define the config schema (TOML or YAML) early, because users will customize. bottom sets rows and column ratios in TOML, btop toggles boxes in `btop.conf`, glances reads INI, and gtop has no layout config. Make each widget independently scrollable or expandable. Drag-resize is rare (btop offers click-to-focus and scrolling, no drag-resize).
- **IDE three-panel:** make the sidebar collapsible, but `Ctrl+B` is tmux's default prefix, so keep an alternative. Cycle main-panel tabs with `[`/`]`, since `Ctrl+Tab` needs an enhanced keyboard protocol. helix is the counterexample: its file explorer is a picker, not a persistent sidebar.
- **Overlay:** buffer choice and the exit contract are in *Inline, alt-screen, or overlay* below. Startup time is part of the design because users summon these dozens of times a day; budgets are in `cli-basics.md` → *Startup time*.
- **Tabs:** mark the active tab with underline or reverse video, with the accent color as reinforcement. Label tabs with their jump keys (`Logs [1]`, `Stats [2]`), and cycle them in reading order.

## Inline, alt-screen, or overlay — where the UI lives

Before choosing a layout, choose a screen buffer. The **alternate screen** is a separate buffer with no scrollback; on exit the terminal restores whatever was there before. **Inline** rendering paints in the normal buffer, below the shell prompt, and scrolls with everything else.

**Default heuristic: alt screen for apps you *live in*; inline for tools you *summon*.** Editors, file managers, and dashboards — long-lived, navigational, full-screen — usually belong on the alt screen so they do not pollute scrollback. Prefer inline for bounded pickers, prompts, confirmations, and progress when preserving shell context matters. A picker with a large preview or unusually deep workflow may still earn a full-screen buffer; choose from the working set and exit contract, not the label alone.

All four frameworks support both modes. How each enters the alternate screen or stays inline, and how it prints permanent lines above an inline UI, is in its ecosystem reference: `ecosystem-go.md`, `ecosystem-rust.md` → *Inline viewport*, and `ecosystem-python.md` and `ecosystem-typescript.md` → *Lifecycle and terminal handoff*.

### The fzf model — bounded inline viewport

fzf itself defaults to full-screen mode. Its explicit `--height 40%` mode renders the finder below the cursor so previous commands remain visible; fzf's shell keybindings commonly opt into this bounded mode. The UI paints on `/dev/tty` (stderr as fallback) so stdout stays clean — that's why `vim $(fzf)` works. Treat height-capped inline rendering as a strong option for fzf-like tools, not as a fact about every picker or fzf's default.

### The exit contract — the receipt pattern

Inside `$(...)` or a pipe, stdout is not a TTY; anything the UI paints to stdout becomes part of the captured "result." So: **chrome to stderr or `/dev/tty`, answer to stdout.** gum runs its Bubble Tea UI with `tea.WithOutput(os.Stderr)` and prints the chosen value to stdout, stripping ANSI when stdout isn't a TTY — which is exactly why `CHOICE=$(gum choose a b c)` composes.

On exit, do one of two respectable things: erase the transient UI completely (fzf's default), or replace it with a one-line receipt that stays in scrollback — `✓ deployed api-server in 12s`. Textual's `inline_no_clear` and fzf's `--no-clear` are the deliberate leave-the-last-frame escape hatches. What you must not do is leave a dead, half-drawn UI behind.

### Choose by workflow

One-shot pick, confirm, or progress: prefer inline, erasing cleanly or leaving a concise receipt. Explore, monitor, or edit sessions: alt screen, restored on exit. Hybrids (fzf-like pickers; logs plus live status): inline with a height cap (`--height 40%`, `Viewport::Inline`).

## Borders — when, what, and why

### The Unicode block

The Unicode box-drawing block is U+2500–U+257F:
- **Single line**: `─ │ ┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼`
- **Heavy**: `━ ┃ ┏ ┓ ┗ ┛ ┣ ┫ ┳ ┻ ╋`
- **Double**: `═ ║ ╔ ╗ ╚ ╝ ╠ ╣ ╦ ╩ ╬`
- **Rounded**: `╭ ╮ ╰ ╯` (combined with single-line straights)

Nearly all of it is East Asian Ambiguous width, so every border cell doubles where the terminal or locale renders ambiguous characters wide. *ASCII fallback* below is the fallback, and *Localization* has the test.

### Choosing a style

Single-line is the default for most modern TUIs (lazygit, k9s, btop, htop); rounded corners are the Charm look (Bubble Tea apps, gum, glow). Reserve heavy for the focused panel or a "hot" warning state. Double reads as "DOS", so avoid it unless going retro.

### When to use borders

Draw a border only where it does work: a dynamic pane needs a visible boundary, adjacent panels need separation, or focus must show with a cue that survives `NO_COLOR` (ranking: `interaction-patterns.md` → *Focus indicators*). Skip it for static content (htop has no internal borders), when density matters more than structure, or when the pane is implicitly bounded. Whitespace is usually separator enough (see *The clutter audit* below).

### The background-leak problem

A terminal cell has one foreground and one background. A border cell draws the line in the foreground, but its background shows behind it, so a panel whose background differs from its parent's gets a visible "step" at the border. Use the same background for panel and borders, or one-eighth block characters (`▏▕▔▁`) as borders, as Textual does for themed apps; they are ambiguous-width too, with the same ASCII fallback.

### ASCII fallback

For legacy SSH, Windows conhost, `TERM=dumb`, or any system where Unicode might be unreliable:
- Single-line `─│┌┐└┘├┤┬┴┼` → `-|+++++++++`; rounded `╭╮╰╯` → `+`
- Heavy → `=|+++` (or just bold the ASCII)

Detect it from the first non-empty variable among `$LC_ALL`, `$LC_CTYPE`, and `$LANG` (does it name UTF-8?), and via terminal capability queries. The ASCII set also sidesteps ambiguous-width box drawing; see *Localization*. Provide a config option (`--ascii`, `MYAPP_ASCII=1`) for explicit override.

## Color in depth

### The three tiers

Design in three layers: monochrome, 16 ANSI, then 256/truecolor. Use truecolor only when the terminal advertises it (`COLORTERM=truecolor` or `24bit`, or your framework's color-profile detection); `COLORTERM` often doesn't survive ssh or sudo, so let users force a tier (detection details: `terminal-protocols.md` → *Modes and sequences* and *Notes that change a decision*). SKILL.md → *Meaning and access* sets the token and `NO_COLOR` rules this section builds on. The depth worth adding here: the user's terminal theme is sacred. The 16 ANSI colors are *theme variables* — the user's `red` might be `#ef5350` (Material), `#dc322f` (Solarized), or `#f38ba8` (Catppuccin). You design in terms of "red means error," not "use #ff0000 for errors."

### Semantic tokens

Define a vocabulary by *function*, not appearance:

```
status.success    → green
status.warning    → yellow
status.error      → red
status.info       → blue or cyan

text.primary      → default fg
text.muted        → dim or gray
text.emphasis     → bold + accent

bg.base           → default bg
bg.surface        → slightly elevated
bg.overlay        → modal/popup bg

accent.primary    → brand color
accent.secondary  → complementary

border.default    → muted
border.focus      → accent.primary (plus a non-color cue)

git.staged/added  → green
git.modified      → yellow
git.untracked     → red or cyan
git.deleted       → red (foreground)
```

Then map tokens to palette colors. **Lipgloss v2's `LightDark`** (`AdaptiveColor` in v1/compat), **Textual's CSS variables**, and **Ratatui's palette indirection** all implement this.

This indirection earns its keep when adding themes (four Catppuccin flavors are one config file, not four code changes) or supporting light/dark modes.

### Conventional meanings

- **Green** — success, added, online, OK.
- **Red** — error, deleted, danger, offline.
- **Yellow** — warning, modified, pending, in-progress.
- **Cyan / Blue** — info, paths, links, hints.
- **Magenta** — special, highlights, attention without alarm.
- **Dim / gray** — secondary, disabled, metadata, timestamps.
- **Bold (any color)** — title, primary content, emphasis.

Stick to conventions. A green error message confuses everyone.

### Color and accessibility

About 8% of males have red-green color vision deficiency, so don't rely on color alone. Pair it with **letters** (lazygit's `M`/`A`/`D`/`??` file status), **symbols** (delta's `+`/`-` prefixes work in monochrome), or **position** (errors at the end of output, success in a separate column). Safe pairs for CVD are blue + orange, blue + yellow, and any high-contrast neutral pair. Avoid red + green as the only distinction; if you must use them, add letters or symbols.

### Honor `NO_COLOR`

[no-color.org](https://no-color.org) is an informal standard proposed in 2017. Respect it: when `NO_COLOR` is present with a non-empty value, suppress automatic color output. An explicit user choice such as `--color=always` may override that default if the tool documents the precedence.

Library behavior varies: some detect it automatically, while others need an optional capability feature or an application-level gate (`owo-colors` consults the environment only through its `supports-colors` feature and `if_supports_color`). Make `NO_COLOR` part of the app's semantic color policy instead of assuming a styling dependency enforces it.

Provide tool-specific `MYAPP_NO_COLOR` and `MYAPP_FORCE_COLOR` for finer control. Keep precedence consistent with the policy in `references/cli-basics.md` → *Color*.

## Typography in monospace

You can't change font size. Typography signals are limited but useful:

| Attribute | Use for | Notes |
|---|---|---|
| **Bold** | Titles, current selection, primary content, focused panel name | Universal support |
| **Dim** | Metadata, timestamps, disabled items, secondary text | Universal support |
| **Italic** | Light emphasis | Poorly supported; never the only signal |
| **Underline** | OSC 8 hyperlinks, shortcut hints | Wide support; meaningful |
| **Reverse video** | Cursor row, current selection | Works on every terminal back to VT100 |
| **Strikethrough** | Cancelled / deleted items | Limited support |
| **Blink** | Don't | Some modern terminals render it (WezTerm, kitty 0.43+); distracting and an accessibility hazard |

**Reverse video is the canonical "current selection" signal.** It's the most reliable and most readable. Use it for the highlighted row in lists, the current cell in tables, the cursor position.

**Bold** the focused panel's title; which cues carry focus, and in what order, is in `interaction-patterns.md` → *Focus indicators*.

### Visual hierarchy

Since you can't change font size, hierarchy comes from:

1. **Position** — top/left reads first; status bar at bottom.
2. **Weight and color** — bold + accent for headlines; dim for secondary; reverse video for the current selection.
3. **Indentation and connectors** — `├─ └─` for trees (ASCII fallback `|-` and `` `- ``); consistent indent units (2 cells is standard).
4. **Whitespace** — blank rows for separation; pads around important content.
5. **Bullets / symbols** — `▸` expandable, `▾` expanded, `◉` active, `◦` inactive, `∙` static bullet. These are narrow-class; their ambiguous-width lookalikes (`▶ ▼ ● ○ •`) are the ones to avoid (see *Localization*).
6. **Borders** — a heavier border weight marks the focused panel.

Spend signals by the budget in *The clutter audit*: at most one color cue plus one non-color cue per state. The current selection: reverse video alone. The focused panel: a heavier border or marked title, plus the accent color. A warning: yellow plus a `!` prefix.

## Density: pack vs pad

You have a fixed grid. Two strategies:

**Pack (high density)** — htop, btop, k9s. For data scanned at a glance, updated in real time, and read horizontally across rows. Use tight one-line records, compact dim headers, abbreviations and units (`GiB`, `1.2k`, `99.9%`), and sparklines or mini-bars.

**Pad (low density)** — gum/huh forms, glow, Posting. For prose, forms, and single decisions. Use generous vertical spacing, one field per line with labels above for narrow terminals, a single column, and lots of margin around modals.

Use density to communicate hierarchy: dense data tables in the main panel, padded settings/forms in modals, dense status bars at the bottom.

**Spacing defaults.** One blank row between groups, 1 cell of inner padding inside a bordered panel, a 2-cell gutter between table columns, and modals no wider than 60–80% of the terminal (fixed to content below that, never edge to edge).

### The clutter audit — making "feels busy" countable

"It feels noisy" is a real signal but useless until you convert it into specific offenders. When a layout feels cluttered, **count — don't squint** — and report the count, not a vibe:

- **Border-nesting depth.** Trace any corner from the terminal edge inward. More than *one* border between the edge and the content is too many. A border wrapping content that's already inside a bordered panel separates nothing and shows no focus — delete it. Boxes-inside-boxes is the single most common cause of "busy," and an outer full-screen frame is almost always redundant (the terminal edge already frames the app).
- **Signals per piece of state.** Count how many things encode the same fact. `[PASS]` + green + `✅` + a `▸` row prefix is *four* signals for one status. **The budget is at most one color cue plus one non-color cue** (green plus a word, letter, or symbol); cut the rest. This is the one rule other sections point to.
- **Always-on markers.** A glyph that appears on 100% of rows (a `▸` on every line) marks nothing — it's texture, not information. Reserve markers for the exception: the selected row, the failed item.
- **Chrome-to-data ratio.** Add up the cells spent on borders, titles, padding, labels, and repeated boilerplate (a full ISO date on every log line when only the time changes) versus cells showing actual data. A high chrome ratio *is* the cluttered feeling.
- **The removal test.** For each decorative element ask: "if I delete this, do I lose information?" If no, delete it. Whitespace is not empty space — it's the cheapest separator you have, and a single blank row routinely out-reads a heavy border.

Run this pass on any layout, yours or someone else's. "Three concentric borders, status encoded four ways, a marker on every row" tells the user exactly what to cut; "simplify it" tells them nothing.

A worked example. Before (the PASS and FAIL tags are green and red):

```
+--------------------------------------+
| +----------------------------------+ |
| | > [PASS] (ok)  build        2.1s | |
| | > [PASS] (ok)  lint         0.8s | |
| | > [FAIL] (!!)  test         4.5s | |
| +----------------------------------+ |
+--------------------------------------+
```

The audit reports: border-nesting depth 2; three signals for one status (tag, `(ok)` or `(!!)`, color); a `>` marker on 3 of 3 rows; and 189 of 226 non-blank cells (84%) spent on chrome. After (FAIL in red):

```
 Task    Status  Time
 build   PASS    2.1s
 lint    PASS    0.8s
 test    FAIL    4.5s
```

Depth 0, two signals on the failure (the word and red) and none on passes, no always-on marker, and 14 of 51 non-blank cells (27%) on the header labels. The selected row gets reverse video alone.

## Responsive design — breakpoints and the floor

A terminal layout is not designed for one size. The same app runs on a 220-column ultrawide, an 80×24 SSH session, a 60-column tmux split, and a 13-inch laptop. **A layout that only works at the author's window size is unfinished** — and the author rarely notices, because they only ever see their own terminal. Pressure-test every layout at the floor, and raise it in any review even when the user only asked about something else: it's the most-missed issue in TUI design.

### The breakpoint ladder

Decide behavior per width band, widest to narrowest. Exact thresholds depend on content, but the shape is universal:

- **Wide (120+ cols)** — the full multi-panel layout; you can afford a side panel or preview alongside the primary view.
- **Standard (80–119)** — the baseline most users see. Often: one primary view full-width, with details/logs on drill-in (Enter / a key) rather than permanently side-by-side.
- **Narrow (60–79)** — collapse to a single column. Stack panels vertically or hide all but the primary. Multi-column layouts (Miller columns, 2×N grids) **must** fold to one pane here. (lazygit's `--screen-mode full` is a related single-panel mode — but it's a user-selectable escape hatch, not automatic responsive behavior.)
- **Below the application-specific minimum** — don't render garbage or panic. Show the too-small state (see *States*), naming the dimensions the app actually requires, until the user resizes. Do not claim an 80-column requirement if the single-pane layout intentionally supports 60 columns.

### One app at three widths

A sidebar, a list, and a detail pane, drawn at half scale. Defaults: the sidebar takes 20–30% of the width, clamped to 20–40 columns; the list never goes under 30 columns; the detail pane takes the rest and needs at least 30. A pane below its minimum folds away instead of shrinking: detail first, then the sidebar.

```
120 columns: sidebar 30, list 40, detail 50
+---------------+--------------------+-------------------------+
| sidebar       | list               | detail                  |
+---------------+--------------------+-------------------------+

80 columns: sidebar becomes a toggle; list 40, detail 40
+--------------------+--------------------+
| list               | detail             |
+--------------------+--------------------+

60 columns: one pane; Enter opens the detail, Esc returns
+------------------------------+
| list                         |
+------------------------------+
```

Below the whole layout's minimum, show the too-small state from *States*.

This is why a **drill-down model degrades better than a fixed grid**: when only one primary thing is ever on screen, narrowing just shrinks it; a fixed 2×2 grid has nowhere to go and turns to mush. If you find yourself unable to make a grid responsive, that's often a sign the layout should have been drill-down in the first place.

### Mechanics

- **Lay out in relative units, never absolute positions:** percentages (Textual `width: 30%`), ratios (Ratatui `Ratio(num, den)`), `Min`/`Max`/`Fill` constraints (Ratatui), `fr` units (Textual `1fr`/`3fr`), flex (Ink/Yoga). Derive geometry from the current frame or latest known window dimensions, and invalidate cached rectangles whenever those dimensions change.
- **Decide what's load-bearing.** When width runs out, what hides *first*? Usually: preview pane → secondary columns → low-priority table columns. Keep the primary view and the controls needed to operate it; a dedicated footer can collapse if those controls remain discoverable elsewhere. **Detail-on-Enter** is the escape hatch — it lets you hide columns/fields at narrow widths without losing access to the data.
- **Truncate, don't wrap, in cells**; reserve a cell for the ellipsis. Truncate paths at the start or middle so the filename survives; tail-truncate prose and IDs.
- **Handle the framework's resize event** and re-layout from the current frame/window size. On POSIX this usually begins with `SIGWINCH`; Windows and higher-level frameworks expose different events. Coalesce rapid events only when layout work is expensive so resizing still feels immediate.
- **Use 80×24 as a compatibility test baseline, not a universal hard minimum.** Define a smaller application-specific minimum from the content that must remain usable and test both sizes. `tmux split-window -h` is a free narrow-terminal test rig.

When reviewing a layout, state the degradation plan concretely: "at 80×24 the preview drops and you get parent│current; at 60 columns it's a single pane; below the tested minimum, show a message naming that minimum." **A review that doesn't name what happens at the floor hasn't finished.**

## Tables and lists

### Alignment rules

- **Numerics: right-aligned.** Easy to scan magnitudes.
- **Text: left-aligned.** Standard.
- **Dates: fixed-width ISO-8601** (`2026-04-28 14:30`). Sortable; doesn't shift on locale.
- **Status / categorical: left-aligned**, like text.

### Truncation

When content exceeds column width:

- **Start truncation** (`…/share/file.txt`) — for paths, so the filename you're looking at survives.
- **Middle truncation** (`/usr/…/file.txt`) — for paths when the root is also useful context.
- **Tail truncation** (`Connection refused whi…`) — for prose, names, and IDs, where the beginning carries the meaning.
- **Wrap** — only for prose. Never wrap in cells of dense tables.

Reserve a cell for the ellipsis `…`, which is ambiguous-width (see *Localization*), or three for the ASCII `...`. Don't truncate so aggressively that nothing remains: `... ` is useless.

### Sort indicators

Show which column is currently sorted: `▴` ascending, `▾` descending. Place after the column header: `Size ▾`. The larger `▲▼` are ambiguous-width. Click (or key) to toggle and cycle.

Filter behavior (response time, match count, highlighting, smart case) is defined in `interaction-patterns.md` → *Search and filter*.

### Wide tables on narrow terminals

Three approaches:

1. **Hide low-priority columns.** Define column priority; drop them as width shrinks.
2. **Horizontal scroll.** htop scrolls the process table left and right with the arrow keys when columns overflow.
3. **Detail-on-Enter.** Pressing Enter on a row opens a side panel or modal showing all fields. The highest-leverage option: show fewer columns, and the user is one keypress from full detail.

### Virtualization

**Always virtualize** lists that might exceed a few hundred items.

- **k9s** (thousands of pods) and **Toolong** (multi-GB logs) virtualize.
- **Textual `DataTable`**, **Ratatui `List` + `ListState`**, and **Bubbles `list`** virtualize or offset efficiently.
- **Ink** needs an explicitly windowed slice or viewport for a changing collection. `<Static>` is only for finalized append-only history; it does not virtualize selectable, filtered, or otherwise mutable rows.

The naive "render all rows, scroll viewport" approach degrades horribly at 10k+ items.

### Emoji and aligned columns

Emoji whose base character is East Asian Wide (`✅ ❌ ⭐`, plus most pictographs) take 2 cells everywhere. Emoji built from a narrow base plus a variation selector or joiner (`⚠️` is U+26A0 + U+FE0F, `✔️`, `❤️`, ZWJ families) take 1 or 2 depending on the terminal and the width library, so a column that contains them can misalign by a cell per row. For status columns use narrow text symbols (`✓ ✗ !`) or words; if you want emoji, choose Wide-base ones, measure with a grapheme-aware width library, and test on the terminals you support (see *Localization* for the width classes).

### Diff views

Choose by width: **unified** below about 120 columns, **side-by-side** at 120 or more, where each side keeps at least 55 columns plus a 2-cell gutter. Mark lines with a `+` or `-` in the first column (color only reinforces it), keep a line-number gutter, and highlight changed words inside a changed line. Navigate by hunk with `]`/`[` (or `n`/`N`). Don't wrap in side-by-side; truncate and scroll horizontally.

## Localization

Terminal layouts assume a fixed number of cells per string, so translated text breaks them in ways a GUI would absorb.

- **Budget for growth.** Translations run longer than English, and short strings grow most. IBM's globalization guidelines allow 100–200% extra space for strings up to 10 characters and 30% past 70 ([IBM](https://public.dhe.ibm.com/systems/power/docs/systemi/v5r2/en_US/rbagsmstp3.pdf), p. 16), and Microsoft's pseudo-localization lengthens text by 40% ([Microsoft](https://learn.microsoft.com/en-us/globalization/methodology/pseudolocalization)). Footer hints, column headers, and button labels are exactly those short strings. Size columns from the rendered text rather than the English labels, and let labels truncate before data does, with the full text in help.
- **Test with a pseudo-locale.** Before any translation exists, run the UI with every string lengthened by about half and wrapped in markers, as Windows' `qps-ploc`, Android's `en-XA`, and ICU's `en_XA` do, then pressure-test the floor from *Responsive design*. A 60-column split with long labels is where layouts fail. General catalog tools such as gettext's `en@boldquot` and Translate Toolkit's `podebug` produce the strings.
- **Right-to-left text.** Most terminals don't implement bidi. kitty, Alacritty, Ghostty, and Windows Terminal show Arabic and Hebrew in logical order, left to right; VTE (GNOME Terminal) and Konsole reorder lines by default, and WezTerm and iTerm2 only experimentally. The [terminal-wg recommendation](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html) has full-screen apps turn off the terminal's reordering (`CSI 8 l` on entry, `CSI 8 h` on exit), which leaves visual order to the app. Either way, keep right-to-left strings in their own field or line, never mix directions inside one cell, and don't promise correct shaping.
- **Ambiguous-width characters.** Unicode's East Asian Ambiguous class ([UAX #11](https://www.unicode.org/reports/tr11/tr11-46.html)) is narrow by default and wide only in East Asian legacy contexts, and terminals expose the choice as a setting: iTerm2, VTE, and Windows Terminal 1.25+. Nearly all box drawing, including the rounded corners, is ambiguous, and so are the block elements (`▀` through `▏`, plus `▒ ▓ ▔ ▕`, so every progress-bar block), the triangles `▲ ▶ ▼ ◀`, the shapes `● ○ ■ □ ◆ ★`, `…`, `·`, `•`, and the arrows `←↑→↓`. When the app and the terminal disagree, borders and markers misalign. go-runewidth switches to wide under any `ja`, `ko`, or `zh` locale, while most other width libraries default to narrow. Test with the terminal's ambiguous-wide setting on, prefer narrow-class markers where they fit (`▸ ▾ ▴ ◉ ◦ ⋅ ✓ ✗ ⋯` and the Braille spinner frames), and keep the ASCII border set from *ASCII fallback* and the ASCII bar from *Determinate progress bars* one switch away. Check a glyph against [EastAsianWidth.txt](https://www.unicode.org/Public/18.0.0/ucd/EastAsianWidth.txt); class `A` is ambiguous, `N` or `Na` is not.
- **Numbers, dates, and units.** Format human output with the user's locale, because separators, grouping, and even digits differ: 1234567.891 is `1 234 567,891` in French and `12,34,567.891` in Indian English. Use the platform's locale library (`Intl`, Babel, `golang.org/x/text/message`, ICU4X) rather than hand-built strings. Keep machine output (`--json`, `--plain`) locale-independent: under a comma-decimal locale, POSIX `printf` both prints and parses numbers with commas, so pin `LC_NUMERIC=C` for anything a script will read. Fixed-width ISO-8601 dates remain the right choice inside tables.
- **Locale detection.** Read `LC_ALL`, then the category variable (`LC_CTYPE` for encoding, `LC_NUMERIC` and `LC_TIME` for formats), then `LANG`, skipping empty values ([POSIX](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html)). `C.UTF-8` is a glibc name rather than a POSIX one, and CI may run in either the C locale or a full one (GitHub's macOS runners set `LC_ALL=en_US.UTF-8`), so tests should pin the locale they expect.

## Status bars, headers, footers

### A common full-screen four-section layout

Header (persistent context: app, dataset, mode), then the main area (the panels), then a status/mode line (ephemeral feedback), then a footer hint bar (contextual shortcuts). Some apps merge status and footer into one line, and some skip the header. Complex full-screen apps benefit from persistent context around the work area; bounded inline tools often need neither a header nor a dedicated footer.

### Header content

- App name, plus the current dataset or context: branch name (lazygit), cluster + namespace (k9s), file path (bat/glow).
- Mode indicator (NORMAL / INSERT in editors).
- Right-aligned: time, host, version, sparingly and only if meaningful.

### Status / mode line

- Ephemeral feedback: "Saved", "3 files changed", "Connecting...".
- Success and info messages fade after 3–5 seconds or give way to the idle state. Keep errors and warnings until the user dismisses them, then move them to a message log the user can reopen (a `:messages` command or a key): a message that vanishes unread can't be acted on.
- **Toasts and the message log.** Show a transient message in the status line, or as a toast at the bottom-right just above the footer so it never covers the row being acted on, with at most two visible. Every message, errors included, is also written to a log the user can reopen (`:messages` or a key): newest last, with a timestamp and kind, capped around 200 entries for the session.
- The current mode, for modal apps (label and cursor shape: `interaction-patterns.md` → *Keybinding philosophies and modal vs modeless*).
- Lead each message with a symbol or label word (`✓ Saved`, `! Low disk space`, `✗ Save failed`) so the kind survives `NO_COLOR`, with green, yellow, or red as the one reinforcement. A message that already starts with a label (`Error:`) needs no symbol too; error wording follows `cli-basics.md` → *Error messages*.

### Footer hint bar

Lay hints out as `key action ⋅ key action ⋅ key action`, with `⋅` (U+22C5; the middle dot `·` is ambiguous-width) or `|` as the separator; htop's `F1Help F2Setup F3Search …` strip is the classic form. Put the most frequent action first and `?` last, and show one rendered line per width:

```
80 columns:  q quit ⋅ / filter ⋅ enter open ⋅ space select ⋅ d delete ⋅ ? help
40 columns:  q quit ⋅ / filter ⋅ ? help
```

Drop hints from the right of the least frequent until the line fits, keeping `?` so the full list stays one key away. Which shortcuts to show and how to generate them from your keymap: `interaction-patterns.md` → *Layer 1: Always-visible footer hints*.

## Modals and dialogs

- **Width:** 60–80% of the terminal, at most about 80 columns for prose, at least 30. Center it horizontally and place it slightly above vertical center.
- **One modal at a time.** A second request replaces the first or queues behind it; `Esc` closes one modal per press (`interaction-patterns.md` → *Esc, q, and Ctrl+C*). The modal traps focus.
- **Clear the cells behind it** (draw a blank background) so underlying text doesn't bleed through, and give it its own border and a title.
- **Modality must not rest on dimming.** Dim the background with the faint attribute where supported, but dimming is an attribute, not a color, and some terminals ignore it. The border, the title, and the changed footer hints say "you are in a dialog" under `NO_COLOR` and without faint.

## Progress indicators

### Spinners

The de facto modern default for indeterminate work: **Braille spinners**.

```
⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏
```

Ten frames at ~80ms per frame (cli-spinners' `dots`) give a smooth rotation.

**Rules:**
- Show only after ~100–200ms — instant work shouldn't flash a spinner.
- Stop with a final state symbol: `✓` (success), `✗` (failure), or just disappear.
- Suppress entirely on non-TTY. CI logs shouldn't have spinners.
- In plain, screen-reader, or reduced-motion mode, print one static line instead (see *Accessibility*).

### Determinate progress bars

Block characters for sub-cell precision:
```
▏▎▍▌▋▊▉█
```

These give 8 sub-positions per cell.

```
[████████▎             ] 41%
```

The block elements are East Asian Ambiguous width: where the terminal renders ambiguous characters wide, each cell doubles and the bar overflows its row. Keep the blocks as the default, but offer the ASCII bar (`[#####     ] 50%`) behind the same switch as the ASCII borders, and always print the percent so the bar is never the only signal.

Show: percent, current/total counts where meaningful, ETA for long operations.

### Multi-progress

Parallel tasks each get their own bar (`package-b [████████▎           ]  41%`, with `100% ✓` on finished rows). indicatif `MultiProgress`, rich `Progress` (multiple tasks), and listr2 `concurrent` mode support this out of the box; Bubbles ships only a single `progress` component — compose multiple bars by hand.

### Pulse / fade

Ambient indication of background work without commanding attention: lazygit's auto-fetch shows only a small spinner and status message instead of a blocking dialog.

## States

Every screen passes through the same states, and each one needs a design before the happy path is done: initial, loading, empty, partial, success, error, disconnected or stale, and too small. Every state names what happened, offers the next action, and keeps its meaning under `NO_COLOR` (a symbol or label word, never color alone).

```
Initial      Welcome to myapp.
             n new request   i import   ? help

Loading      Pods (staging)                    loading... 3s   Esc cancel
             api-7d  1/1  4d                   <- old rows stay visible

Empty        No pods in namespace "staging".
             n change namespace   c create one

Partial      Pods (2 of 3 clusters)            ! prod-eu unreachable   r retry
             api-7d  1/1  4d

Success      ✓ Saved notes.txt                 fades after 3-5 s

Error        ✗ Cannot connect to 10.0.0.4:6443 (connection refused)
             r retry   l view log   Esc dismiss

Stale        Pods (staging)          STALE 2m   reconnecting (3)   r retry now
             api-7d  1/1  4d         <- dimmed, last known good

Too small    terminal too small: need 48x12
             resize the window, or press q to quit
```

- **Initial.** The first launch, before the user has done anything. Render the frame at once and show where to start; a blank screen reads as a hang.
- **Loading.** Draw the layout immediately and show the delayed spinner from *Progress indicators* inside the content area. Add elapsed time once a wait passes a second or two, and let `Esc` cancel the request. There is no TUI convention for an automatic give-up time, so prefer elapsed time and cancel over picking one. When refreshing, keep the last rows visible.
- **Empty.** Never just "No data." Name the scope that is empty and the next action: Posting's empty collection reads "Collection is empty. Press ctrl+s to save the current request."
- **Partial.** Show what loaded and mark each source that failed, inline, with a count (`2 of 3`) and a retry key. Do not blank the screen for one failed source or hide the failure.
- **Success.** Confirm in the status line (3–5 seconds, per *Status bars*); a long operation also leaves a receipt in scrollback or the message log.
- **Error.** Say what failed and how to recover, with the retry or escape key beside it. It stays until dismissed, then moves to the message log.
- **Disconnected or stale.** Keep the last-known-good view visible, dimmed, with a `STALE` or `reconnecting` marker and the age instead of blanking the screen. k9s's retry and backoff settings (`apiServerTimeout`, `maxConnRetry`) treat connection loss as a designed-for case. Never let a transient failure rewrite persistent config: btop has an open bug where a temporarily unavailable GPU permanently rewrites the user's saved widget layout instead of hiding the metric until it returns.
- **Too small.** Name the dimensions the layout needs, and keep `q` and `Ctrl+C` working. Don't render a broken frame; the threshold comes from *Responsive design*.

## Theming systems

Most production TUIs support themes: define semantic tokens (`status.error`, `text.muted`), map them to palette colors in one file per theme (TOML/YAML/CSS), and allow selection via config, env var, or runtime command.

### Configuration formats

No format is the TUI standard. Common ones: TOML (bottom, helix, starship, alacritty 0.13+), YAML (lazygit, lazydocker, k9s), TCSS (Textual, live-reloads), and flag files or git config (bat's config is a list of CLI flags; fzf reads `FZF_DEFAULT_OPTS` or `FZF_DEFAULT_OPTS_FILE`; delta lives under `[delta]` in `.gitconfig`). Matching the tool your users already configure, as when mirroring lazygit, is a good reason to use its format; otherwise choose the one that suits your own settings.

### Community palettes for themeable, broadly distributed apps

If theming is part of the product, ship popular palettes (Catppuccin, Dracula, Nord, Gruvbox, Tokyo Night, Rose Pine, Solarized) or document how to import them; the base16 spec underlies many. Users of highly themeable apps expect plug-and-play. Small single-purpose tools still need semantic colors and light/dark safety, but do not need to bundle every palette.

### Icons and Nerd Fonts — there is no detection, only opt-in

No terminal emulator exposes "a Nerd Font is installed and active" as a queryable signal (not kitty, WezTerm, iTerm2, Alacritty, Windows Terminal, or Ghostty): the protocol has no font capability query, and font-fallback chains can substitute per glyph anyway. Even `has-nerd-font`, which guesses from the terminal's configured font name, still needs a `NERD_FONT=1` override. **Don't invent a detection scheme — gate icons behind an explicit opt-in instead**, the way real tools do:

- **eza** — `--icons=WHEN` (`always` / `automatic` / `never`); `automatic` gates on stdout being a TTY, not on font presence.
- **lazygit** — `gui.nerdFontsVersion: '2' | '3' | ""`; empty (the default) means no icons at all.
- **yazi** — icons are default-on in the shipped theme; users without a Nerd Font override the icon tables in `theme.toml`.

**Pin the codepoint generation, not just "Nerd Font on/off."** Nerd Fonts v3 moved Material Design Icons' codepoints (`F500–FD46` → `F0001+`), a documented breaking change, which is why lazygit's config asks for `'2'` or `'3'` explicitly.

The fallback ladder is Nerd Font glyphs → plain Unicode symbols → ASCII. starship ships all three rungs as named presets (`nerd-font-symbols` / `no-nerd-font` / `plain-text-symbols`), but most tools are binary (icons on or off), so don't imply every icon-capable tool implements all three.

### Light/dark detection

- OSC `]11;?` query — many terminals respond with their background color; others never answer, so bound the wait. Mode 2031 reports later theme switches where supported. The query, timeout, and sentinel details are in `terminal-protocols.md` → *Modes and sequences* and *Notes that change a decision*.
- `$COLORFGBG` env var — set by some terminals (rxvt-derivatives).
- Lipgloss v2's `LightDark` (`AdaptiveColor` in v1/compat) and Textual's runtime theme switching abstract this.

If you support both light and dark, default to "auto" and let users override with `--theme dark`.

## Accessibility

Be honest about the medium. Screen readers announce what changed on screen. NVDA finds new text in a terminal by diffing its contents, and Windows Terminal reports text as it is written ([NVDA user guide](https://download.nvaccess.org/releases/2026.2/documentation/userGuide.html#DiffAlgo), [Windows Terminal accessibility notes](https://github.com/microsoft/terminal/blob/e90f9a534cae047fccddacc1ee813a82929662d5/doc/terminal-a11y-2023.md)). A full-screen UI repaints constantly, so a spinner frame, a re-highlighted menu row, or a redrawn panel is heard as new text, and the layout itself carries no structure a listener can navigate. No TUI framework fixes that. The dependable answer is a linear mode offered alongside the full-screen UI.

### What works for screen-reader users

These rules come from Sampath, Merrick, and Macvean's study of blind developers using CLIs ([CHI '21](https://doi.org/10.1145/3411764.3445544)) and from the screen-reader modes that current agent CLIs ship:

- **Append; don't repaint.** Report a state change as a new line (`Saved notes.txt`) instead of redrawing a status bar, and keep output in scrollback rather than on the alternate screen.
- **Say it in words.** End every command with a status line, because silent success leaves users guessing. Make progress an occasional line (`Uploaded 3 of 10`), not spinner frames or a bar, which are read out character by character.
- **Flatten structure.** Turn table rows into labelled `Header: value` lines or offer `--format csv|json`; aligned columns force users to memorize column order. Drop borders, box drawing, and ASCII art, which are heard as symbol noise.
- **Number the choices.** An arrow-key menu is re-read whenever the highlight moves; print a numbered list and read a typed answer.
- **Label lines.** Prefix output kinds (`error:`, `warning:`, speaker names in a chat) so a listener knows what a line is before hearing it. For `error:`/`warning:`, follow the one rule in `cli-basics.md` → *Error messages*.
- **Write errors to be spoken.** Say what failed and what to do next, without regexes or symbol-dense jargon.
- **Keep the cursor on the focus.** Screen readers and magnifiers follow the terminal cursor, which full-screen apps usually hide. Hide it only while a frame is painting, then re-show it on the focused field or row (at minimum in the accessible mode), or return it to the prompt after printing.

[Claude Code's screen-reader mode](https://code.claude.com/docs/en/accessibility) is the most complete published example: flat text without box drawing, `Header: value` tables, numbered menus, labelled lines, no fullscreen, and the terminal bell when it needs input.

### The plain-mode contract

`SKILL.md` requires a `--no-tui`-style mode when automation or accessibility needs linear output. Treat it as part of the product, not a degraded fallback. It must meet these terms:

- It reaches every action the TUI offers; nothing is TUI-only.
- It follows the rules above and the stream contract in `cli-basics.md` → *Stdin / stdout / stderr discipline*. Results go to stdout; prompts and progress go to stderr.
- Meaning never depends on color, column position, or layout.
- Every prompt has a flag or config equivalent, so the mode can run unattended.
- Users turn it on once, through a flag, an environment variable, or a persistent setting, and it starts automatically when stdout is not a terminal. Don't count on detecting a screen reader. Ink, Gemini CLI, and Claude Code all require an explicit opt-in. gh's `GH_ACCESSIBLE_PROMPTER` and `GH_SPINNER_DISABLED`, with matching config keys, are the model.

### Framework support

None of these makes a full-screen app accessible by itself. Check the ecosystem reference before relying on a feature:

| Stack | What exists | Details |
|---|---|---|
| Huh (Go) | Accessible mode: plain line-by-line prompts with numbered choices and no full-screen redraw. The app switches it on, and Huh does so itself only for `TERM=dumb` | `ecosystem-go.md` → *Huh* |
| Bubble Tea, Bubbles | Nothing screen-reader-specific. Build the linear mode yourself and use Huh's accessible mode for prompts, as gh does | `ecosystem-go.md` → *Huh* |
| Ink | `aria-*` props and an opt-in screen-reader renderer that prints linear text without borders or color; the live region is still rewritten on every change | `ecosystem-typescript.md` → *Strengths and weaknesses* |
| Textual | No screen-reader support, and `textual serve` adds none. Built-in animations honor a reduced-motion level | `ecosystem-python.md` → *Dev tools* |
| Ratatui | Nothing in the library; accessibility is an open tracking issue | `ecosystem-rust.md` → *Pitfalls* |

### Motion

- Treat animation as decoration with an off switch, and default it off in plain and screen-reader modes. No cross-tool reduced-motion variable exists, so name yours and document it, as gh (`GH_SPINNER_DISABLED`) and Textual (`TEXTUAL_ANIMATIONS=none`) do.
- With motion off, print one static line (`Working...`) and then the final status, rather than a frozen spinner frame.
- Never blink text (see *Typography in monospace*), and don't animate content the user is reading.

### Keyboard, focus, and color

- Every action is keyboard-reachable (`SKILL.md`), and focus shows through at least one cue besides color; the ranking is in `interaction-patterns.md` → *Focus indicators*.
- Color rules live in *Color and accessibility* and *Honor `NO_COLOR`* above. Keep a 16-color theme: those colors follow the user's terminal palette, including high-contrast palettes, while truecolor values override it.

## Common visual pitfalls

1. **Hardcoded colors** that clash with user themes. Use semantic tokens.
2. **Decorative borders** that don't earn their keep.
3. **Color-only signaling**, or **emoji as the only signal** (some terminals render boxes). Pair with letters or symbols.
4. **Misaligned tables** when text contains CJK or emoji. Use `unicode_width` / `string-width`.
5. **Over-bolding.** Bold loses meaning when half the screen is bold.
6. **Inconsistent capitalization** in headers (mix of "Branch", "branch", "BRANCH").
7. **Light-mode-only colors** (low contrast on dark, or vice versa).
8. **Tiny status bar** that hides important state under the fold.
9. **No visual focus indication** — users tab around guessing where they are.

112-### Notes by layout
113-
114-- **Multi-panel:** the focus cue must survive `NO_COLOR` (ranking in `interaction-patterns.md` → *Focus indicators*). Make the footer hint bar panel-aware (`c` does different things in lazygit's Files and Commits panels), and let numeric jumps work from any panel.

124:## Inline, alt-screen, or overlay — where the UI lives
125-
126:Before choosing a layout, choose a screen buffer. The **alternate screen** is a separate buffer with no scrollback; on exit the terminal restores whatever was there before. **Inline** rendering paints in the normal buffer, below the shell prompt, and scrolls with everything else.
127-
128:**Default heuristic: alt screen for apps you *live in*; inline for tools you *summon*.** Editors, file managers, and dashboards — long-lived, navigational, full-screen — usually belong on the alt screen so they do not pollute scrollback. Prefer inline for bounded pickers, prompts, confirmations, and progress when preserving shell context matters. A picker with a large preview or unusually deep workflow may still earn a full-screen buffer; choose from the working set and exit contract, not the label alone.
129-
130:All four frameworks support both modes. How each enters the alternate screen or stays inline, and how it prints permanent lines above an inline UI, is in its ecosystem reference: `ecosystem-go.md`, `ecosystem-rust.md` → *Inline viewport*, and `ecosystem-python.md` and `ecosystem-typescript.md` → *Lifecycle and terminal handoff*.
131-
132:### The fzf model — bounded inline viewport
133-
134:fzf itself defaults to full-screen mode. Its explicit `--height 40%` mode renders the finder below the cursor so previous commands remain visible; fzf's shell keybindings commonly opt into this bounded mode. The UI paints on `/dev/tty` (stderr as fallback) so stdout stays clean — that's why `vim $(fzf)` works. Treat height-capped inline rendering as a strong option for fzf-like tools, not as a fact about every picker or fzf's default.
135-
136-### The exit contract — the receipt pattern
137-
138-Inside `$(...)` or a pipe, stdout is not a TTY; anything the UI paints to stdout becomes part of the captured "result." So: **chrome to stderr or `/dev/tty`, answer to stdout.** gum runs its Bubble Tea UI with `tea.WithOutput(os.Stderr)` and prints the chosen value to stdout, stripping ANSI when stdout isn't a TTY — which is exactly why `CHOICE=$(gum choose a b c)` composes.
139-
140:On exit, do one of two respectable things: erase the transient UI completely (fzf's default), or replace it with a one-line receipt that stays in scrollback — `✓ deployed api-server in 12s`. Textual's `inline_no_clear` and fzf's `--no-clear` are the deliberate leave-the-last-frame escape hatches. What you must not do is leave a dead, half-drawn UI behind.
141-
142-### Choose by workflow
143-
144:One-shot pick, confirm, or progress: prefer inline, erasing cleanly or leaving a concise receipt. Explore, monitor, or edit sessions: alt screen, restored on exit. Hybrids (fzf-like pickers; logs plus live status): inline with a height cap (`--height 40%`, `Viewport::Inline`).

148-## Borders — when, what, and why
149-
150-### The Unicode block
151-
152-The Unicode box-drawing block is U+2500–U+257F:
153-- **Single line**: `─ │ ┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼`
154-- **Heavy**: `━ ┃ ┏ ┓ ┗ ┛ ┣ ┫ ┳ ┻ ╋`
155-- **Double**: `═ ║ ╔ ╗ ╚ ╝ ╠ ╣ ╦ ╩ ╬`
156-- **Rounded**: `╭ ╮ ╰ ╯` (combined with single-line straights)
157-
158-Nearly all of it is East Asian Ambiguous width, so every border cell doubles where the terminal or locale renders ambiguous characters wide. *ASCII fallback* below is the fallback, and *Localization* has the test.
159-
160-### Choosing a style
161-
162-Single-line is the default for most modern TUIs (lazygit, k9s, btop, htop); rounded corners are the Charm look (Bubble Tea apps, gum, glow). Reserve heavy for the focused panel or a "hot" warning state. Double reads as "DOS", so avoid it unless going retro.
163-
164-### When to use borders
165-
166-Draw a border only where it does work: a dynamic pane needs a visible boundary, adjacent panels need separation, or focus must show with a cue that survives `NO_COLOR` (ranking: `interaction-patterns.md` → *Focus indicators*). Skip it for static content (htop has no internal borders), when density matters more than structure, or when the pane is implicitly bounded. Whitespace is usually separator enough (see *The clutter audit* below).
167-
168-### The background-leak problem
169-
170-A terminal cell has one foreground and one background. A border cell draws the line in the foreground, but its background shows behind it, so a panel whose background differs from its parent's gets a visible "step" at the border. Use the same background for panel and borders, or one-eighth block characters (`▏▕▔▁`) as borders, as Textual does for themed apps; they are ambiguous-width too, with the same ASCII fallback.
171-
172-### ASCII fallback
173-
174-For legacy SSH, Windows conhost, `TERM=dumb`, or any system where Unicode might be unreliable:
175-- Single-line `─│┌┐└┘├┤┬┴┼` → `-|+++++++++`; rounded `╭╮╰╯` → `+`
176-- Heavy → `=|+++` (or just bold the ASCII)
177-
178-Detect it from the first non-empty variable among `$LC_ALL`, `$LC_CTYPE`, and `$LANG` (does it name UTF-8?), and via terminal capability queries. The ASCII set also sidesteps ambiguous-width box drawing; see *Localization*. Provide a config option (`--ascii`, `MYAPP_ASCII=1`) for explicit override.

182-## Color in depth
183-
184-### The three tiers
185-
186-Design in three layers: monochrome, 16 ANSI, then 256/truecolor. Use truecolor only when the terminal advertises it (`COLORTERM=truecolor` or `24bit`, or your framework's color-profile detection); `COLORTERM` often doesn't survive ssh or sudo, so let users force a tier (detection details: `terminal-protocols.md` → *Modes and sequences* and *Notes that change a decision*). SKILL.md → *Meaning and access* sets the token and `NO_COLOR` rules this section builds on. The depth worth adding here: the user's terminal theme is sacred. The 16 ANSI colors are *theme variables* — the user's `red` might be `#ef5350` (Material), `#dc322f` (Solarized), or `#f38ba8` (Catppuccin). You design in terms of "red means error," not "use #ff0000 for errors."

292-
293:### The clutter audit — making "feels busy" countable
294-
295-"It feels noisy" is a real signal but useless until you convert it into specific offenders. When a layout feels cluttered, **count — don't squint** — and report the count, not a vibe:
296-
297-- **Border-nesting depth.** Trace any corner from the terminal edge inward. More than *one* border between the edge and the content is too many. A border wrapping content that's already inside a bordered panel separates nothing and shows no focus — delete it. Boxes-inside-boxes is the single most common cause of "busy," and an outer full-screen frame is almost always redundant (the terminal edge already frames the app).
298-- **Signals per piece of state.** Count how many things encode the same fact. `[PASS]` + green + `✅` + a `▸` row prefix is *four* signals for one status. **The budget is at most one color cue plus one non-color cue** (green plus a word, letter, or symbol); cut the rest. This is the one rule other sections point to.
299-- **Always-on markers.** A glyph that appears on 100% of rows (a `▸` on every line) marks nothing — it's texture, not information. Reserve markers for the exception: the selected row, the failed item.
300-- **Chrome-to-data ratio.** Add up the cells spent on borders, titles, padding, labels, and repeated boilerplate (a full ISO date on every log line when only the time changes) versus cells showing actual data. A high chrome ratio *is* the cluttered feeling.
301-- **The removal test.** For each decorative element ask: "if I delete this, do I lose information?" If no, delete it. Whitespace is not empty space — it's the cheapest separator you have, and a single blank row routinely out-reads a heavy border.
302-
303-Run this pass on any layout, yours or someone else's. "Three concentric borders, status encoded four ways, a marker on every row" tells the user exactly what to cut; "simplify it" tells them nothing.

330:## Responsive design — breakpoints and the floor
331-
332-A terminal layout is not designed for one size. The same app runs on a 220-column ultrawide, an 80×24 SSH session, a 60-column tmux split, and a 13-inch laptop. **A layout that only works at the author's window size is unfinished** — and the author rarely notices, because they only ever see their own terminal. Pressure-test every layout at the floor, and raise it in any review even when the user only asked about something else: it's the most-missed issue in TUI design.
333-
334-### The breakpoint ladder
335-
336-Decide behavior per width band, widest to narrowest. Exact thresholds depend on content, but the shape is universal:
337-
338-- **Wide (120+ cols)** — the full multi-panel layout; you can afford a side panel or preview alongside the primary view.
339-- **Standard (80–119)** — the baseline most users see. Often: one primary view full-width, with details/logs on drill-in (Enter / a key) rather than permanently side-by-side.
340-- **Narrow (60–79)** — collapse to a single column. Stack panels vertically or hide all but the primary. Multi-column layouts (Miller columns, 2×N grids) **must** fold to one pane here. (lazygit's `--screen-mode full` is a related single-panel mode — but it's a user-selectable escape hatch, not automatic responsive behavior.)
341-- **Below the application-specific minimum** — don't render garbage or panic. Show the too-small state (see *States*), naming the dimensions the app actually requires, until the user resizes. Do not claim an 80-column requirement if the single-pane layout intentionally supports 60 columns.
342-
343-### One app at three widths
344-
345-A sidebar, a list, and a detail pane, drawn at half scale. Defaults: the sidebar takes 20–30% of the width, clamped to 20–40 columns; the list never goes under 30 columns; the detail pane takes the rest and needs at least 30. A pane below its minimum folds away instead of shrinking: detail first, then the sidebar.
346-
347-```
348-120 columns: sidebar 30, list 40, detail 50
349-+---------------+--------------------+-------------------------+
350-| sidebar       | list               | detail                  |
351-+---------------+--------------------+-------------------------+
352-
353-80 columns: sidebar becomes a toggle; list 40, detail 40
354-+--------------------+--------------------+
355-| list               | detail             |
356-+--------------------+--------------------+
357-
358-60 columns: one pane; Enter opens the detail, Esc returns
359-+------------------------------+
360-| list                         |
361-+------------------------------+
362-```
363-
364-Below the whole layout's minimum, show the too-small state from *States*.
365-
366-This is why a **drill-down model degrades better than a fixed grid**: when only one primary thing is ever on screen, narrowing just shrinks it; a fixed 2×2 grid has nowhere to go and turns to mush. If you find yourself unable to make a grid responsive, that's often a sign the layout should have been drill-down in the first place.
367-
368-### Mechanics
369-
370-- **Lay out in relative units, never absolute positions:** percentages (Textual `width: 30%`), ratios (Ratatui `Ratio(num, den)`), `Min`/`Max`/`Fill` constraints (Ratatui), `fr` units (Textual `1fr`/`3fr`), flex (Ink/Yoga). Derive geometry from the current frame or latest known window dimensions, and invalidate cached rectangles whenever those dimensions change.
371-- **Decide what's load-bearing.** When width runs out, what hides *first*? Usually: preview pane → secondary columns → low-priority table columns. Keep the primary view and the controls needed to operate it; a dedicated footer can collapse if those controls remain discoverable elsewhere. **Detail-on-Enter** is the escape hatch — it lets you hide columns/fields at narrow widths without losing access to the data.
372-- **Truncate, don't wrap, in cells**; reserve a cell for the ellipsis. Truncate paths at the start or middle so the filename survives; tail-truncate prose and IDs.
373-- **Handle the framework's resize event** and re-layout from the current frame/window size. On POSIX this usually begins with `SIGWINCH`; Windows and higher-level frameworks expose different events. Coalesce rapid events only when layout work is expensive so resizing still feels immediate.
374-- **Use 80×24 as a compatibility test baseline, not a universal hard minimum.** Define a smaller application-specific minimum from the content that must remain usable and test both sizes. `tmux split-window -h` is a free narrow-terminal test rig.
375-
376-When reviewing a layout, state the degradation plan concretely: "at 80×24 the preview drops and you get parent│current; at 60 columns it's a single pane; below the tested minimum, show a message naming that minimum." **A review that doesn't name what happens at the floor hasn't finished.**

381-
382-### Alignment rules
383-
384-- **Numerics: right-aligned.** Easy to scan magnitudes.
385-- **Text: left-aligned.** Standard.
386-- **Dates: fixed-width ISO-8601** (`2026-04-28 14:30`). Sortable; doesn't shift on locale.
387-- **Status / categorical: left-aligned**, like text.
388-
389-### Truncation
390-
391-When content exceeds column width:
392-
393-- **Start truncation** (`…/share/file.txt`) — for paths, so the filename you're looking at survives.
394-- **Middle truncation** (`/usr/…/file.txt`) — for paths when the root is also useful context.
395-- **Tail truncation** (`Connection refused whi…`) — for prose, names, and IDs, where the beginning carries the meaning.

450-### A common full-screen four-section layout
451-
452:Header (persistent context: app, dataset, mode), then the main area (the panels), then a status/mode line (ephemeral feedback), then a footer hint bar (contextual shortcuts). Some apps merge status and footer into one line, and some skip the header. Complex full-screen apps benefit from persistent context around the work area; bounded inline tools often need neither a header nor a dedicated footer.
453-
454-### Header content
455-
456-- App name, plus the current dataset or context: branch name (lazygit), cluster + namespace (k9s), file path (bat/glow).
457-- Mode indicator (NORMAL / INSERT in editors).
458-- Right-aligned: time, host, version, sparingly and only if meaningful.
459-
460-### Status / mode line
461-
462-- Ephemeral feedback: "Saved", "3 files changed", "Connecting...".
463-- Success and info messages fade after 3–5 seconds or give way to the idle state. Keep errors and warnings until the user dismisses them, then move them to a message log the user can reopen (a `:messages` command or a key): a message that vanishes unread can't be acted on.
464-- **Toasts and the message log.** Show a transient message in the status line, or as a toast at the bottom-right just above the footer so it never covers the row being acted on, with at most two visible. Every message, errors included, is also written to a log the user can reopen (`:messages` or a key): newest last, with a timestamp and kind, capped around 200 entries for the session.
465-- The current mode, for modal apps (label and cursor shape: `interaction-patterns.md` → *Keybinding philosophies and modal vs modeless*).
466-- Lead each message with a symbol or label word (`✓ Saved`, `! Low disk space`, `✗ Save failed`) so the kind survives `NO_COLOR`, with green, yellow, or red as the one reinforcement. A message that already starts with a label (`Error:`) needs no symbol too; error wording follows `cli-basics.md` → *Error messages*.
467-
468-### Footer hint bar
469-
470-Lay hints out as `key action ⋅ key action ⋅ key action`, with `⋅` (U+22C5; the middle dot `·` is ambiguous-width) or `|` as the separator; htop's `F1Help F2Setup F3Search …` strip is the classic form. Put the most frequent action first and `?` last, and show one rendered line per width:
471-
472-```
473-80 columns:  q quit ⋅ / filter ⋅ enter open ⋅ space select ⋅ d delete ⋅ ? help
474-40 columns:  q quit ⋅ / filter ⋅ ? help
475-```
476-
477-Drop hints from the right of the least frequent until the line fits, keeping `?` so the full list stays one key away. Which shortcuts to show and how to generate them from your keymap: `interaction-patterns.md` → *Layer 1: Always-visible footer hints*.

481-## Modals and dialogs
482-
483-- **Width:** 60–80% of the terminal, at most about 80 columns for prose, at least 30. Center it horizontally and place it slightly above vertical center.
484-- **One modal at a time.** A second request replaces the first or queues behind it; `Esc` closes one modal per press (`interaction-patterns.md` → *Esc, q, and Ctrl+C*). The modal traps focus.
485-- **Clear the cells behind it** (draw a blank background) so underlying text doesn't bleed through, and give it its own border and a title.
486-- **Modality must not rest on dimming.** Dim the background with the faint attribute where supported, but dimming is an attribute, not a color, and some terminals ignore it. The border, the title, and the changed footer hints say "you are in a dialog" under `NO_COLOR` and without faint.

509-
510-Block characters for sub-cell precision:
511-```
512-▏▎▍▌▋▊▉█

564-- **Initial.** The first launch, before the user has done anything. Render the frame at once and show where to start; a blank screen reads as a hang.
565-- **Loading.** Draw the layout immediately and show the delayed spinner from *Progress indicators* inside the content area. Add elapsed time once a wait passes a second or two, and let `Esc` cancel the request. There is no TUI convention for an automatic give-up time, so prefer elapsed time and cancel over picking one. When refreshing, keep the last rows visible.
566-- **Empty.** Never just "No data." Name the scope that is empty and the next action: Posting's empty collection reads "Collection is empty. Press ctrl+s to save the current request."
567:- **Partial.** Show what loaded and mark each source that failed, inline, with a count (`2 of 3`) and a retry key. Do not blank the screen for one failed source or hide the failure.
568-- **Success.** Confirm in the status line (3–5 seconds, per *Status bars*); a long operation also leaves a receipt in scrollback or the message log.
569-- **Error.** Say what failed and how to recover, with the retry or escape key beside it. It stays until dismissed, then moves to the message log.
570-- **Disconnected or stale.** Keep the last-known-good view visible, dimmed, with a `STALE` or `reconnecting` marker and the age instead of blanking the screen. k9s's retry and backoff settings (`apiServerTimeout`, `maxConnRetry`) treat connection loss as a designed-for case. Never let a transient failure rewrite persistent config: btop has an open bug where a temporarily unavailable GPU permanently rewrites the user's saved widget layout instead of hiding the metric until it returns.
571-- **Too small.** Name the dimensions the layout needs, and keep `q` and `Ctrl+C` working. Don't render a broken frame; the threshold comes from *Responsive design*.

575-## Theming systems
576-
577-Most production TUIs support themes: define semantic tokens (`status.error`, `text.muted`), map them to palette colors in one file per theme (TOML/YAML/CSS), and allow selection via config, env var, or runtime command.
578-
579-### Configuration formats
580-
581-No format is the TUI standard. Common ones: TOML (bottom, helix, starship, alacritty 0.13+), YAML (lazygit, lazydocker, k9s), TCSS (Textual, live-reloads), and flag files or git config (bat's config is a list of CLI flags; fzf reads `FZF_DEFAULT_OPTS` or `FZF_DEFAULT_OPTS_FILE`; delta lives under `[delta]` in `.gitconfig`). Matching the tool your users already configure, as when mirroring lazygit, is a good reason to use its format; otherwise choose the one that suits your own settings.
582-
583-### Community palettes for themeable, broadly distributed apps
584-
585-If theming is part of the product, ship popular palettes (Catppuccin, Dracula, Nord, Gruvbox, Tokyo Night, Rose Pine, Solarized) or document how to import them; the base16 spec underlies many. Users of highly themeable apps expect plug-and-play. Small single-purpose tools still need semantic colors and light/dark safety, but do not need to bundle every palette.
586-
587-### Icons and Nerd Fonts — there is no detection, only opt-in
588-
589-No terminal emulator exposes "a Nerd Font is installed and active" as a queryable signal (not kitty, WezTerm, iTerm2, Alacritty, Windows Terminal, or Ghostty): the protocol has no font capability query, and font-fallback chains can substitute per glyph anyway. Even `has-nerd-font`, which guesses from the terminal's configured font name, still needs a `NERD_FONT=1` override. **Don't invent a detection scheme — gate icons behind an explicit opt-in instead**, the way real tools do:
590-
591-- **eza** — `--icons=WHEN` (`always` / `automatic` / `never`); `automatic` gates on stdout being a TTY, not on font presence.
592-- **lazygit** — `gui.nerdFontsVersion: '2' | '3' | ""`; empty (the default) means no icons at all.
593-- **yazi** — icons are default-on in the shipped theme; users without a Nerd Font override the icon tables in `theme.toml`.
594-
595-**Pin the codepoint generation, not just "Nerd Font on/off."** Nerd Fonts v3 moved Material Design Icons' codepoints (`F500–FD46` → `F0001+`), a documented breaking change, which is why lazygit's config asks for `'2'` or `'3'` explicitly.
596-
597-The fallback ladder is Nerd Font glyphs → plain Unicode symbols → ASCII. starship ships all three rungs as named presets (`nerd-font-symbols` / `no-nerd-font` / `plain-text-symbols`), but most tools are binary (icons on or off), so don't imply every icon-capable tool implements all three.
598-
599-### Light/dark detection
600-
601-- OSC `]11;?` query — many terminals respond with their background color; others never answer, so bound the wait. Mode 2031 reports later theme switches where supported. The query, timeout, and sentinel details are in `terminal-protocols.md` → *Modes and sequences* and *Notes that change a decision*.
602-- `$COLORFGBG` env var — set by some terminals (rxvt-derivatives).
603-- Lipgloss v2's `LightDark` (`AdaptiveColor` in v1/compat) and Textual's runtime theme switching abstract this.
604-
605-If you support both light and dark, default to "auto" and let users override with `--theme dark`.

609-## Accessibility
610-
611-Be honest about the medium. Screen readers announce what changed on screen. NVDA finds new text in a terminal by diffing its contents, and Windows Terminal reports text as it is written ([NVDA user guide](https://download.nvaccess.org/releases/2026.2/documentation/userGuide.html#DiffAlgo), [Windows Terminal accessibility notes](https://github.com/microsoft/terminal/blob/e90f9a534cae047fccddacc1ee813a82929662d5/doc/terminal-a11y-2023.md)). A full-screen UI repaints constantly, so a spinner frame, a re-highlighted menu row, or a redrawn panel is heard as new text, and the layout itself carries no structure a listener can navigate. No TUI framework fixes that. The dependable answer is a linear mode offered alongside the full-screen UI.
612-
613-### What works for screen-reader users
614-
615-These rules come from Sampath, Merrick, and Macvean's study of blind developers using CLIs ([CHI '21](https://doi.org/10.1145/3411764.3445544)) and from the screen-reader modes that current agent CLIs ship:
616-
617-- **Append; don't repaint.** Report a state change as a new line (`Saved notes.txt`) instead of redrawing a status bar, and keep output in scrollback rather than on the alternate screen.
618-- **Say it in words.** End every command with a status line, because silent success leaves users guessing. Make progress an occasional line (`Uploaded 3 of 10`), not spinner frames or a bar, which are read out character by character.
619-- **Flatten structure.** Turn table rows into labelled `Header: value` lines or offer `--format csv|json`; aligned columns force users to memorize column order. Drop borders, box drawing, and ASCII art, which are heard as symbol noise.
620-- **Number the choices.** An arrow-key menu is re-read whenever the highlight moves; print a numbered list and read a typed answer.
621-- **Label lines.** Prefix output kinds (`error:`, `warning:`, speaker names in a chat) so a listener knows what a line is before hearing it. For `error:`/`warning:`, follow the one rule in `cli-basics.md` → *Error messages*.
622-- **Write errors to be spoken.** Say what failed and what to do next, without regexes or symbol-dense jargon.
623-- **Keep the cursor on the focus.** Screen readers and magnifiers follow the terminal cursor, which full-screen apps usually hide. Hide it only while a frame is painting, then re-show it on the focused field or row (at minimum in the accessible mode), or return it to the prompt after printing.
624-
625-[Claude Code's screen-reader mode](https://code.claude.com/docs/en/accessibility) is the most complete published example: flat text without box drawing, `Header: value` tables, numbered menus, labelled lines, no fullscreen, and the terminal bell when it needs input.
626-
627-### The plain-mode contract
628-
629-`SKILL.md` requires a `--no-tui`-style mode when automation or accessibility needs linear output. Treat it as part of the product, not a degraded fallback. It must meet these terms:
630-
631-- It reaches every action the TUI offers; nothing is TUI-only.
632-- It follows the rules above and the stream contract in `cli-basics.md` → *Stdin / stdout / stderr discipline*. Results go to stdout; prompts and progress go to stderr.

codex
**Start inline if your main loop is “ask → read → follow up.” Choose the alternate screen if browsing and manipulating conversation history is central.** Streaming alone doesn’t require either buffer.

| Consideration | Inline + `<Static>` | Alternate screen |
|---|---|---|
| History | Native terminal scrollback, selection, search | You implement scrolling, search, and copying |
| After exit | Transcript remains visible | Previous shell screen returns |
| Earlier messages | Printed content is immutable | Can reflow, edit, collapse, or branch |
| Layout | Small live region beneath history | Stable composer, panes, overlays |
| Main risk | A growing streaming answer overwhelms the live region | Taking responsibility for the whole terminal experience |

For the straightforward chat client you described, I’d choose **inline, with completed content in `<Static>` and the unfinished response in ordinary live components**.

The critical detail: **don’t put a changing response into `<Static>`.** Once an item is printed, updates won’t repaint it.

Use this rendering model:

```text
<Static>  completed messages / finalized blocks
Live      unfinished response tail
Live      request status + composer
```

Batch token updates—roughly every 30–50 ms is a reasonable starting point. Keep the live region within the available terminal height. For long answers, commit finalized paragraphs or code blocks into `<Static>` and retain only the unfinished tail. Markdown makes this trickier: later tokens can change formatting, so define conservative commit boundaries and never revise already printed blocks.

Keep the conversation in your application’s data model, independently of what has been printed. Terminal scrollback is a viewing surface, not durable conversation storage.

A minimal layout, with the same single-column structure across widths:

```text
Wide terminal                         60-column split
You: Explain this function.            You: Explain this function.

Assistant:                            Assistant:
Completed explanation...              Completed explanation...
                                      wraps to available width.
[unfinished response tail]
                                      [unfinished response tail]
Streaming | Ctrl+C cancel             Streaming | Ctrl+C cancel
> follow-up draft                     > follow-up draft
```

At **80×24**, cap the composer and streaming tail so the controls remain visible. At **60 columns**, wrap prose, omit optional model/token metadata, and offer long code through a pager or export. Declare and test a smaller minimum—for example, 40×10—below which you show a resize message while preserving cancellation.

The clutter budget here is small: **zero borders, one speaker label per turn, no marker on every line, and one status/hint row**. That row consumes about 4% of a 24-row terminal.

Switch to the alternate screen when you need a pinned composer while independently scrolling history, message selection, branching, collapsible tool output, or persistent side panels. In Ink 7+, that’s supported through `render(<App />, {alternateScreen: true})`; it still requires your own history viewport and navigation.

For either choice, preserve partial text on cancellation or connection failure, provide a retry action, and ship a linear plain mode with answers on stdout and diagnostics on stderr. **Choose based on who should own history navigation: the terminal or your application.**
