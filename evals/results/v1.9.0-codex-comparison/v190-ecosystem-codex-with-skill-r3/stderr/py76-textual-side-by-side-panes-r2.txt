## Classify the product first

Choose the output contract before choosing a framework or layout:

| Product shape | Default contract |
|---|---|
| One-shot CLI | No live full-screen UI. Stable stdout for results, stderr for diagnostics, meaningful exit codes. Load `cli-basics.md`. |
| Summon–choose–exit tool | Prefer inline when shell context matters. Put interactive chrome on stderr or `/dev/tty` and the selected result on stdout. Use full-screen only when a large preview or working set needs stable space. |
| Full-screen session | Use the alternate screen and a stable spatial model. Treat terminal restoration, resize, suspend, and redraw behavior as product requirements. |

Then name the workflow shape—persistent panels, Miller columns, drill-down stack, dashboard, IDE-style panes, overlay, or tabs—and verify it against `visual-patterns.md`. Sketch the states and layout before writing code: initial, loading, empty, partial, success, error, disconnected, and too-small (`visual-patterns.md` → *States*). In a design answer, include an ASCII sketch of the layout at the floor size (60 columns) next to the wide one.

## Preserve these cross-cutting contracts

### Terminal lifecycle

- Use the alternate screen for full-screen sessions; keep bounded and one-shot workflows inline when possible.
- Prefer framework-managed terminal cleanup. Restore raw mode, screen buffer, cursor, and input modes on every exit path, including errors and panics. Do not invent custom signal handling when the framework already owns it.
- Re-layout from the current frame or window size on resize. Coalesce bursts only when layout work is expensive.
- Treat final shutdown and temporary handoff as different boundaries. For an editor, shell, or supported suspend, prefer the framework's handoff API: pause UI input, restore the shell-facing terminal, wait, re-enter modes, reload externally mutable data, and force a full redraw. Redrawing only repaints the current model; it does not refresh changed data. Do not final-unmount an app that must resume, and do not assume POSIX signals exist on Windows.
- Keep logs and debug output away from the screen the TUI owns. Use a file, framework console, or separate diagnostic stream.

### Rendering, data, and performance

- Never block the UI/event thread on disk, network, or subprocess work. Return results through commands, messages, tasks, channels, or framework events.
- Render on input, data, resize, or intentional ticks; do not redraw unchanged state in an unconditional loop.
- Measure terminal cell width, not bytes, code points, `len()`, or JavaScript string length. Test CJK, combining marks, and emoji.
- Virtualize collections that can grow beyond a few hundred rows. Truncate rather than wrap inside tables; reveal full values in a detail view.
- Keep panel positions stable unless the user explicitly changes the layout. Spatial memory is part of navigation.

### Meaning and access

- Define semantic style tokens rather than scattering color literals. Honor `NO_COLOR` in automatic color mode and preserve meaning in monochrome.
- Never use color alone. Pair it with text, shape, position, or symbols, and provide an ASCII fallback when Unicode support is uncertain.
- Make every action keyboard-reachable. Mouse support may accelerate an action but must not gate it.
- Offer familiar navigation aliases only where they do not conflict with text entry or a complete bounded prompt keymap. Preserve the expected reserved-key behavior: `Ctrl+C` cancels or quits, and `Ctrl+Z` suspends through the framework. Which other keys are reserved, and why raw mode frees `Ctrl+S`, is in `interaction-patterns.md` → *Reserved keys*.
- Match discoverability to complexity: complete inline controls for bounded prompts; contextual hints, help, and optionally a command palette for action-rich full-screen apps.
- Provide a plain `--no-tui` or equivalent mode when automation or serious accessibility needs require linear output; `visual-patterns.md` → *Accessibility* defines what it must contain.

## Apply two review reflexes unprompted

These catch the failures users rarely name. Apply both to every layout you design or review, even when the question is about something else.

### Run a clutter audit

Make “busy” countable. Report:

- border-nesting depth—more than one border between the terminal edge and content is usually too much;
- how many signals encode the same state—`[PASS]`, green, a checkmark, and a row marker is four;
- markers present on every row, which therefore mark nothing;
- the share of cells spent on chrome, labels, and repeated boilerplate instead of data.

Name the exact borders, markers, labels, or repeated fields to remove. Do not stop at “simplify it.” Use the full method in `visual-patterns.md` → *The clutter audit*.

### Pressure-test the floor

State what happens at 80×24 and in a 60-column tmux split: which pane wins, what hides, what truncates, what becomes drill-down, and when the truthful “terminal too small” state appears. Every multi-column design needs a single-pane fallback. Use the breakpoint ladder and minimum-size method in `visual-patterns.md` → *Responsive design*.

## Build and verification discipline

Keep business state independent enough to test without a terminal. In MVU or immediate-mode systems, feed synthetic events into update logic and assert state. In retained/widget systems, drive the smallest widget or app harness that owns the behavior.

Use a bottom-heavy test pyramid:

1. Unit-test state transitions, parsing, sorting, filtering, and command construction.
2. Snapshot or golden-test rendered frames at pinned terminal sizes and color profiles, including 80×24, 60 columns, and the hard minimum.
3. Use one or two PTY end-to-end flows for lifecycle and real-keyboard integration, not as the primary suite.

Verify at least:

- normal exit, interrupt, error, and panic cleanup;
- resize, too-small behavior, and suspend/resume where supported;
- empty, loading, partial, error, disconnected, and large-data states;
- keyboard reachability, focus visibility, and help accuracy;
- `NO_COLOR`, 16-color or monochrome, ASCII fallback, and non-TTY output;
- wide characters, combining marks, truncation, sorting, and virtualization;
- no stdout corruption and no blocking I/O in the event/render path.
- for one-shot CLIs, stdout, stderr, and the exit code in golden tests, with no TTY and under `NO_COLOR` (`cli-basics.md` → *Testing one-shot CLIs*).

Use the ecosystem reference's exact testing and debugging APIs. Never print diagnostics into an active raw-mode or alternate-screen UI.

## Textual (Textualize/textual)

**Architectural model: reactive, async-first, message-passing.** App subclass + Widgets in a DOM-like tree (App → Screen → Widgets) + TCSS for layout/style + reactive attributes for state + Messages/Events for communication, all on asyncio.

**Status:** Textualize the company wound down in mid-2025, and Will McGugan maintains Textual and Rich as open source. Textual shipped five major versions (4.0 through 8.0) since the May 2025 announcement, with 8.x current as of mid-2026 (Textual 8.2.8, Rich 15.0.0); releases have slowed. The majors carried breaking renames (`Static.renderable` → `Static.content` in 6.0, `Select.BLANK` → `Select.NULL` in 8.0), so pin your major and read the changelog when upgrading. Harlequin, Dolphie and Posting 2.x track Textual 8.2 (see `exemplar-apps.md`); Toolong, elia and frogmouth are pinned to pre-1.0 Textual, so use them as design references only.

```python check=python/hello-app
from textual.app import App, ComposeResult
from textual.widgets import Header, Footer, Button, Label

class HelloApp(App):
    CSS = "#greeting { padding: 1 2; }"  # or CSS_PATH = "hello.tcss"; that file must exist
    BINDINGS = [
        ("q", "quit", "Quit"),
        ("d", "toggle_dark", "Toggle dark mode"),
    ]

    def compose(self) -> ComposeResult:
        yield Header()
        yield Label("Hello, world!", id="greeting")
        yield Button("Click me", id="go", variant="success")
        yield Footer()

    def on_button_pressed(self, event: Button.Pressed) -> None:
        self.query_one("#greeting", Label).update("Button pressed!")

    def action_toggle_dark(self) -> None:
        self.theme = "textual-light" if self.theme == "textual-dark" else "textual-dark"

if __name__ == "__main__":
    HelloApp().run()
```

`compose()` defines the widget tree (called once on mount). `BINDINGS` declares key bindings declaratively — they auto-render in the `Footer` widget. `action_*` methods are invoked by binding actions. `on_*` methods handle events from child widgets.

### Lifecycle and terminal handoff

| Boundary | Textual 8 contract |
|---|---|
| Normal exit | Call `self.exit(result, return_code=...)`; the run lifecycle shuts the driver down in a `finally` path. `return_code` is application metadata, so call `sys.exit(app.return_code)` after `app.run()` when the process must expose it. |
| SIGTERM | Textual installs no SIGTERM handler. On Unix, have the running event loop call `exit` (recipe below); never restore the terminal from a `signal.signal` handler. SIGKILL cannot be cleaned up. |
| Interactive child | Run an argv-based subprocess inside `with self.suspend():`. Textual pauses input/output, restores the child-facing terminal, and resumes plus refreshes afterward. Reload any data the child could have changed; layout refresh does not reread it. Handle `SuspendNotSupported` with a non-terminal alternative because Textual Web cannot hand a local terminal to a child. |
| Foreground suspend | Bind or invoke `suspend_process`; Textual sends SIGTSTP and resumes application mode on Unix. It is intentionally a no-op on Windows and Textual Web. Subscribe to `app_resume_signal` to reload externally mutable data when needed. |

SIGTERM recipe: the loop runs the callback, so `exit` takes the normal shutdown path and the driver restores the terminal. `add_signal_handler` raises `NotImplementedError` on Windows, so skip it there. 143 is 128 plus SIGTERM.

```python check=python/sigterm
import asyncio
import signal
from textual.app import App

class Service(App):
    def on_mount(self) -> None:
        asyncio.get_running_loop().add_signal_handler(
            signal.SIGTERM, lambda: self.exit(return_code=143))
```

[`App.suspend()`](https://textual.textualize.io/guide/app/#suspend-context-manager) lends the terminal to code inside a context manager; `suspend_process` is Unix job control. Neither is a final-exit substitute.

**Ctrl+C is not quit in Textual.** `ctrl+q` is bound to `quit`; `ctrl+c` is bound to `help_quit`, which only shows a toast naming the key that quits, and `Input` and `TextArea` use it to copy ([`app.py`](https://github.com/Textualize/textual/blob/v8.2.8/src/textual/app.py), `BINDINGS` and `action_help_quit`). To keep the "Ctrl+C cancels or quits" contract, rebind it with a priority binding so it fires even while a text field has focus, at the cost of copy there:

```python check=python/ctrl-c-quit
from textual.app import App
from textual.binding import Binding

class QuitOnCtrlC(App):
    BINDINGS = [Binding("ctrl+c", "quit", "Quit", show=False, priority=True)]
```

**Inline mode:** `app.run(inline=True)` (since 0.55) renders below the prompt instead of on the alternate screen. Set its height with CSS on `Screen`, as in `Screen { &:inline { height: 50vh; } }`. Inline mode is not supported on Windows.

### Widgets

- **Input:** `Input`, `MaskedInput`, `TextArea` (multi-line, optional tree-sitter syntax highlighting — the `syntax` extras require Python 3.10+ since Textual 5.0), `Button`, `Switch`, `Checkbox`, `RadioButton`, `RadioSet`, `Select`, `OptionList`.
- **Data and display:** `DataTable` (cell/row/column cursors, sortable, virtualized — handles thousands of rows), `Tree`, `DirectoryTree`, `ListView` + `ListItem`, `Markdown`, `RichLog`, `ProgressBar`, `Sparkline`.

Use `DataTable` for any tabular display. Add columns with `add_columns`, rows with `add_rows`, configure cursor type (`cell`/`row`/`column`/`none`), enable `zebra_stripes`, hook into `on_data_table_row_selected`.

### Layout — TCSS

Layout is CSS:

```css check=python/textual-layout
Screen {
    layout: horizontal;
}

#sidebar {
    width: 30;
    border: tall $accent;
}

#main {
    width: 1fr;
    layout: vertical;
}

DataTable {
    height: 1fr;
}

.error {
    color: $error;
    text-style: bold;
}
```

Concepts:
- **`layout`** — `vertical | horizontal | grid`. A `Screen` stacks its children vertically, so side-by-side panes need `layout: horizontal` on the Screen (as above) or a `Horizontal` parent.
- **Containers**: `Vertical`, `Horizontal` and `Grid` expand (`width` and `height: 1fr`); `VerticalGroup`, `HorizontalGroup` and `ItemGrid` are `height: auto`, so use a group for a toolbar or form row that hugs its content. Also `VerticalScroll`, `Center`, `Middle`.
- **Sizing**: cells (`width: 30`), percentages (`width: 50%`), `auto`, fractional units (`width: 1fr`); `overflow-x: auto` adds scrollbars. **Grid**: `grid-size: 3 4`, `grid-columns`, `grid-rows`, `column-span`. **Docking**: `dock: top | right | bottom | left` for sticky edges, as `Header` and `Footer` do.

**Selectors**: type (`Button { ... }` matches subclasses too, e.g. your `MyButton(Button)`, unlike web CSS; use a class selector for exact targeting), id (`#dialog`), class (`.error`), pseudo (`:focus`, `:hover`, `:disabled`, `:dark`, `:light`). Nesting works. **Theme variables** (`$primary`, `$panel`, `$text`, `$accent`, `$error`, etc.) — semantic tokens that change with the active theme.

### Events and messages

Handle events with `on_<widget>_<message>` methods (as in the hello app) or the **`@on` decorator with a CSS selector**, preferred when you have many widgets of one type:
```python check=python/on-decorator
from textual import on

@on(Button.Pressed, "#submit")
def handle_submit(self) -> None:
    ...

@on(Button.Pressed, ".danger")
def handle_danger(self, event: Button.Pressed) -> None:
    ...
```

Messages bubble up the DOM. Call `event.stop()` to halt propagation. The idiom: **"attributes down, messages up"** — parents set state on children via attributes; children notify parents via messages.

### Reactive state

```python check=python/reactive
from textual.reactive import reactive, var
from textual.widget import Widget

class Counter(Widget):
    count: reactive[int] = reactive(0)
    label: reactive[str] = reactive("")
    history: reactive[list[int]] = reactive(list)  # callable default: one list per widget
    cursor = var(0)  # watchers fire, but no repaint

    def watch_count(self, old: int, new: int) -> None:
        # called automatically when count changes; repaint is already automatic
        self.log(f"count {old} -> {new}")

    def validate_count(self, value: int) -> int:
        # called before assignment; can clamp or transform
        return max(0, min(10, value))

    def compute_label(self) -> str:
        # derived, read-only reactive; recomputed when count changes
        return f"Count: {self.count}"

    def render(self) -> str:
        return self.label

    def remember(self) -> None:
        self.history.append(self.count)  # in-place edits are invisible to Textual...
        self.mutate_reactive(Counter.history)  # ...so fire watchers and repaint by hand
```

`compute_<name>` only runs for a declared reactive of that name (`label` here), and that reactive becomes read-only. Don't name one `display` — that's Widget's built-in visibility property. Execution order on assignment: **validate → assign → watch → compute**. Modifiers on `reactive(...)`: `init=False` (no watcher on initial assignment), `always_update=True` (fire even when the value didn't change), `layout=True` (re-layout, not just re-render), `bindings=True` (re-evaluate `BINDINGS`), `recompose=True` (re-run `compose()`; the manual route is `await self.remove_children()` + `await self.mount(...)`).

Textual detects assignment, not mutation: after `append` or `d[k] = v`, call `self.mutate_reactive(Cls.attr)`. Use `var` for state that needs watchers but no repaint or relayout (cursor index, cache). To hide a dependent widget, react in `watch_<name>` and set `widget.display = False` (removes it from layout) or `.visible = False` (hides it without reflowing).

### Async and workers

Handlers can be `async def`. The `@work` decorator turns methods into background workers:

```python check=python/workers
import httpx
from textual import work
from textual.widgets import Static
from textual.worker import Worker, WorkerState, get_current_worker

@work(exclusive=True)
async def fetch_data(self, url: str) -> None:
    async with httpx.AsyncClient() as client:
        response = await client.get(url)
        response.raise_for_status()
    self.query_one("#result", Static).update(response.text)

# For blocking code:
@work(thread=True)
def compute_heavy(self) -> None:
    result = expensive_sync_thing()
    self.app.call_from_thread(self.update_result, result)

@work(thread=True, exclusive=True, group="search", exit_on_error=False)
def search(self, query: str) -> None:
    worker = get_current_worker()
    for page in range(20):
        rows = slow_fetch(query, page)
        if worker.is_cancelled:  # a newer search replaced this one
            return
        self.app.call_from_thread(self.show_rows, rows)

def on_worker_state_changed(self, event: Worker.StateChanged) -> None:
    if event.state is WorkerState.ERROR:
        self.notify(str(event.worker.error), severity="error")
```

`call_from_thread(fn, *args)` is required when modifying UI from a thread (vs an asyncio task). It exists only on `App`, so a Screen or Widget worker calls `self.app.call_from_thread(...)`; `self.call_from_thread` there raises `AttributeError`. `post_message` is also thread-safe. `set_interval(secs, callable)` schedules periodic UI updates without blocking.

**Cancellation:** `exclusive=True` cancels earlier workers in the same `group` on the same widget. An async worker stops at its next `await`; a thread worker cannot be interrupted, since cancelling only flips its state to `CANCELLED`, so poll `get_current_worker().is_cancelled` and return before touching the UI. `exit_on_error=False` keeps a failing worker from quitting the app; handle `ERROR` in `on_worker_state_changed` (sent to the widget that started the worker, not bubbled).

**Streaming LLM output:** don't re-render the whole reply per token. `Markdown.get_stream()` batches fragments when the widget can't keep up (about 20 appends a second), and `anchor()` on the scroll container holds the view on the tail until the user scrolls up. Call `stream.stop()` in `finally` to flush queued text.

```python check=python/markdown-stream
@work(exclusive=True)
async def stream_reply(self, chunks) -> None:
    self.query_one(VerticalScroll).anchor()
    stream = Markdown.get_stream(self.query_one(Markdown))
    try:
        async for chunk in chunks:
            await stream.write(chunk)
    finally:
        await stream.stop()
```

```python check=python/modal
from textual import on, work
from textual.app import ComposeResult
from textual.screen import ModalScreen
from textual.widgets import Button, Label

class ConfirmDialog(ModalScreen[bool]):
    def compose(self) -> ComposeResult:
        yield Label("Are you sure?")
        yield Button("Yes", id="yes", variant="error")
        yield Button("No", id="no")

    @on(Button.Pressed, "#yes")
    def confirm(self) -> None:
        self.dismiss(True)

    @on(Button.Pressed, "#no")
    def cancel(self) -> None:
        self.dismiss(False)

# In your app: a callback works from any handler, no worker needed
def action_delete(self) -> None:
    self.push_screen(ConfirmDialog(), self.after_confirm)

async def after_confirm(self, confirmed: bool | None) -> None:
    if confirmed:
        await self.do_delete()

# Or wait inline, which only works inside a worker:
@work
async def action_delete_inline(self) -> None:
    if await self.push_screen_wait(ConfirmDialog()):
        await self.do_delete()
```

Results come back via `dismiss(value)`; the callback receives it (`None` for a bare `dismiss()`). `push_screen_wait` returns it inline but needs the `@work` decorator; from a plain handler it raises `NoActiveWorker`.

### Testing — Pilot + pytest-textual-snapshot

Pilot drives the app headlessly from pytest:

```python check=python/pilot-test
import pytest
from textual.widgets import Label

@pytest.mark.asyncio  # or asyncio_mode = "auto"
async def test_button_click():
    app = HelloApp()  # the example app above
    async with app.run_test(size=(80, 24)) as pilot:
        await pilot.click("#go")
        await pilot.pause()
        assert app.query_one("#greeting", Label).content == "Button pressed!"
```

For SVG snapshots, call `snap_compare("path/to/app.py", press=["tab", "enter", "a"])` in a test; snapshots live under `__snapshots__/` and failures generate an HTML diff page.

Gotchas worth knowing:

- **Async tests need `pytest-asyncio`.** Its default strict mode fails an unmarked `async def` test ("async def functions are not natively supported"). Set `asyncio_mode = "auto"` under `[tool.pytest.ini_options]`, as Textual's own suite does, or mark each test `@pytest.mark.asyncio`.
- **Pin `pytest>=8.4,<9` for snapshot suites.** pytest-textual-snapshot's last release, 1.1.0 (January 2025), pins `syrupy==4.8.0`, which requires `pytest<9`; pytest-asyncio 1.4 needs pytest 8.4 or later. On pytest 9, pip silently picks 1.0.0, which writes `.raw` snapshots instead of `.svg`.
- **`run_test()` runs headless at `size=(80, 24)` and disables notifications and tooltips by default.** A test asserting on a `notify()` toast will silently see nothing — pass `notifications=True` (and `tooltips=True` if relevant) to `run_test`.
- **There's no `App.messages` capture API.** Assert posted messages via a recorder handler on a test App subclass (an `@on(SomeWidget.Changed)` handler appending events to a list — Textual's own test suite does this), or via the `message_hook` parameter of `run_test`, which sees every message in the app. Messages bubble asynchronously, so always `await pilot.pause()` before asserting.
### Debugging

Textual redirects `sys.stdout` and `sys.stderr` while the app runs, so `print()` is captured and sent to `textual console` instead of the screen. What corrupts the display is a write that bypasses the redirect: `sys.__stdout__`, file descriptor 1 (C extensions, `os.write(1, ...)`), and child processes that inherit the terminal. To see output, `pip install textual-dev` (the `textual` CLI lives in that separate package):

- **`textual console`** receives logs and `print()`/`self.log(...)` output in another terminal; start the app with **`textual run --dev myapp.py`**, which also hot-reloads TCSS on save.
- **`textual keys`** — interactive key inspector; press keys to see exactly what events Textual receives, useful for tracking down "why doesn't my binding fire" bugs.

**Profiling:** neither the dev console nor `textual diagnose` (an environment report) measures performance, and there is no built-in FPS overlay. For a "what's slow" answer, attach `py-spy` to the running process (`py-spy record -o profile.svg --pid <pid>`); it needs no code changes, though attaching usually needs `sudo`, and Python 3.15+ has the stdlib `python -m profiling.sampling attach <pid>`. `py-spy` excludes idle threads by default and Textual's main loop mostly awaits, so pass `--idle` if a run over a quiet window shows almost nothing. Heavy synchronous work inside an `async def` handler with no `await` blocks the whole UI; offload it to `@work(thread=True)`, not just `@work`.

### Dev tools

**`textual serve app.py`** serves the app over HTTP/WebSocket in a browser tab with no code changes, so the same codebase runs in a terminal, over SSH, or in a browser. Prefer `textual serve` (self-hosted; works with Textual 8.2) over **textual-web**, the hosted service, which has had no release since 0.8.0 in August 2024.

**Accessibility:** `textual serve` is not an accessibility path. Its browser client paints the terminal grid with xterm.js on a canvas, with xterm's screen-reader mode off, so a screen reader gets no more than it would in a terminal. Textual itself has no screen-reader support; the roadmap item is still open. For reduced motion, `TEXTUAL_ANIMATIONS=none` (or setting `App.animation_level` to `"none"`) makes built-in animations jump to their end state and the loading indicator static; custom timers and spinners must check `app.animation_level` themselves. Design guidance: `visual-patterns.md` → *Accessibility*.

### Pitfalls

1. **Reactives in `__init__` fire watchers before mount** → `NoMatches` errors when watchers try to query DOM. Init in `on_mount` or use the `self.set_reactive(MyClass.attr, value)` method to bypass validators and watchers.
2. **Don't bypass Textual's stdout capture** (see Debugging). `print()` is safe, but `sys.__stdout__`, fd 1 and inherited child-process output corrupt the screen; run children inside `self.suspend()`.
3. **Inside Textual, use `ProgressBar` widget**, not Rich's `Live`/`Progress` — they fight each other for the screen.
4. **`can_focus = True`** on custom widgets that should receive key events. Without this, key events bypass them.
5. **`DataTable.add_rows()` is not a bulk-insert optimization.** It is a plain loop over `add_row()`, paying the same per-row cost, so switching to it won't speed up a slow bulk insert.

## Rich (Textualize/rich)

Immediate-mode output formatting — no input handling, no event loop. The de facto Python library for pretty CLI output; it honors `NO_COLOR`.

```python check=python/rich
from rich.console import Console
from rich.table import Table
from rich.panel import Panel
from rich.progress import track

console = Console()
err = Console(stderr=True)  # diagnostics and progress stay off stdout

# Markup syntax (like BBCode)
err.print("[bold red]error:[/] file not found")

# Tables
table = Table(title="Users")
table.add_column("Name", style="cyan")
table.add_column("Email", style="green")
table.add_row("Alice", "alice@example.com")
console.print(table)

# Panels
console.print(Panel.fit("Hello, world!", title="Greeting", border_style="blue"))

# Progress
for item in track(items, description="Processing...", console=err):
    do_work(item)
```

**`from rich.traceback import install; install()`** replaces the default traceback with a syntax-highlighted one with source context. (There is no `rich.install()`; the sibling `rich.pretty.install()` only pretty-prints REPL results.)

**Use Rich vs Textual:** Rich is for tools that *print and exit*. Textual is for apps the user *lives inside*. Rich + Click/Typer is the standard for modern Python CLI tools; pip vendors Rich for its own output, and Textual, Harlequin, and most new Typer-based tools build on it. (Poetry uses cleo and Sphinx does not depend on Rich.)

## prompt_toolkit

**Prompt-style** — single-line input with completion, history, syntax highlighting:

```python check=python/prompt-toolkit
from prompt_toolkit import prompt
from prompt_toolkit.completion import WordCompleter

cmd_completer = WordCompleter(["help", "list", "quit"])
text = prompt("> ", completer=cmd_completer)
```

**Full-screen Application** — HSplit/VSplit/FloatContainer + UIControl + KeyBindings. Powers IPython, ptpython, all the DBCLI tools (mycli, pgcli, litecli), pyvim, pymux.

For one-off prompts inside CLI tools, use **questionary** (built on prompt_toolkit) — much simpler API:

```python check=python/questionary
import sys
import questionary

answer = questionary.text("What's your name?").ask()
if answer is None:  # .ask() turns Ctrl-C into None
    sys.exit(130)
choice = questionary.select(
    "Pick a color",
    choices=["red", "green", "blue"],
).unsafe_ask()  # raises KeyboardInterrupt instead
```

`.ask()` catches Ctrl-C, prints "Cancelled by user" to stdout, and returns `None`; check for `None` and exit 130. `kbi_msg=""` still prints a blank line, so when stdout carries the result, call `.unsafe_ask()` and catch `KeyboardInterrupt`. prompt_toolkit draws prompts on stdout by default, even when stdout is piped, so when stdout carries the result pass `output=create_output(stdout=sys.stderr)` (from `prompt_toolkit.output`). For a single select without questionary, prompt_toolkit 3.0.52+ has a built-in `choice()`.

## Argument parsing: argparse vs Click vs Typer

**argparse** — stdlib, no dependency. Verbose but capable. Since Python 3.14 it colorizes help and can suggest fixes for mistyped choices and subcommands (`suggest_on_error`, on by default in 3.15).

**Click** — decorator-based, very popular:
```python check=python/click
import click

@click.command()
@click.option("--name", default="world", help="Who to greet")
@click.option("--count", default=1, type=int)
def hello(name: str, count: int) -> None:
    """Say hello."""
    for _ in range(count):
        click.echo(f"Hello, {name}!")
```

**Typer** — type-hint-driven (FastAPI's author):
```python check=python/typer
import typer

app = typer.Typer()

@app.command()
def hello(name: str = "world", count: int = 1) -> None:
    """Say hello."""
    for _ in range(count):
        typer.echo(f"Hello, {name}!")

if __name__ == "__main__":
    app()
```

**Recommendation: use Typer for new projects.** Type hints give you free validation, documentation, and shell completion. Since 0.26 (May 2026) Typer vendors Click instead of depending on it, so Click plug-ins and extracting the underlying Click app are no longer supported; use Click directly if you need them. **Cyclopts** (Python 3.11+) is the Click-free alternative with a similar type-hint API.

**Trogon** (last release 0.6.0, October 2024; unmaintained) generates a Textual form UI for a **Click** CLI: `from trogon import tui`, then `@tui()` above your Click group. On Click 8.3+ it pre-fills options that have no default with the literal text `Sentinel.UNSET`, and its Typer integration fails on Typer 0.26+; pin `typer<0.26` or write that CLI in Click.

281-## Density: pack vs pad
282-
283-You have a fixed grid. Two strategies:
284-
285-**Pack (high density)** — htop, btop, k9s. For data scanned at a glance, updated in real time, and read horizontally across rows. Use tight one-line records, compact dim headers, abbreviations and units (`GiB`, `1.2k`, `99.9%`), and sparklines or mini-bars.
286-
287-**Pad (low density)** — gum/huh forms, glow, Posting. For prose, forms, and single decisions. Use generous vertical spacing, one field per line with labels above for narrow terminals, a single column, and lots of margin around modals.
288-
289-Use density to communicate hierarchy: dense data tables in the main panel, padded settings/forms in modals, dense status bars at the bottom.
290-
291-**Spacing defaults.** One blank row between groups, 1 cell of inner padding inside a bordered panel, a 2-cell gutter between table columns, and modals no wider than 60–80% of the terminal (fixed to content below that, never edge to edge).
292-
293:### The clutter audit — making "feels busy" countable
294-
295-"It feels noisy" is a real signal but useless until you convert it into specific offenders. When a layout feels cluttered, **count — don't squint** — and report the count, not a vibe:
296-
297-- **Border-nesting depth.** Trace any corner from the terminal edge inward. More than *one* border between the edge and the content is too many. A border wrapping content that's already inside a bordered panel separates nothing and shows no focus — delete it. Boxes-inside-boxes is the single most common cause of "busy," and an outer full-screen frame is almost always redundant (the terminal edge already frames the app).
298-- **Signals per piece of state.** Count how many things encode the same fact. `[PASS]` + green + `✅` + a `▸` row prefix is *four* signals for one status. **The budget is at most one color cue plus one non-color cue** (green plus a word, letter, or symbol); cut the rest. This is the one rule other sections point to.
299-- **Always-on markers.** A glyph that appears on 100% of rows (a `▸` on every line) marks nothing — it's texture, not information. Reserve markers for the exception: the selected row, the failed item.
300-- **Chrome-to-data ratio.** Add up the cells spent on borders, titles, padding, labels, and repeated boilerplate (a full ISO date on every log line when only the time changes) versus cells showing actual data. A high chrome ratio *is* the cluttered feeling.
301-- **The removal test.** For each decorative element ask: "if I delete this, do I lose information?" If no, delete it. Whitespace is not empty space — it's the cheapest separator you have, and a single blank row routinely out-reads a heavy border.
302-
303-Run this pass on any layout, yours or someone else's. "Three concentric borders, status encoded four ways, a marker on every row" tells the user exactly what to cut; "simplify it" tells them nothing.

330:## Responsive design — breakpoints and the floor
331-
332-A terminal layout is not designed for one size. The same app runs on a 220-column ultrawide, an 80×24 SSH session, a 60-column tmux split, and a 13-inch laptop. **A layout that only works at the author's window size is unfinished** — and the author rarely notices, because they only ever see their own terminal. Pressure-test every layout at the floor, and raise it in any review even when the user only asked about something else: it's the most-missed issue in TUI design.
333-
334-### The breakpoint ladder
335-
336-Decide behavior per width band, widest to narrowest. Exact thresholds depend on content, but the shape is universal:
337-
338-- **Wide (120+ cols)** — the full multi-panel layout; you can afford a side panel or preview alongside the primary view.
339-- **Standard (80–119)** — the baseline most users see. Often: one primary view full-width, with details/logs on drill-in (Enter / a key) rather than permanently side-by-side.
340-- **Narrow (60–79)** — collapse to a single column. Stack panels vertically or hide all but the primary. Multi-column layouts (Miller columns, 2×N grids) **must** fold to one pane here. (lazygit's `--screen-mode full` is a related single-panel mode — but it's a user-selectable escape hatch, not automatic responsive behavior.)
341-- **Below the application-specific minimum** — don't render garbage or panic. Show the too-small state (see *States*), naming the dimensions the app actually requires, until the user resizes. Do not claim an 80-column requirement if the single-pane layout intentionally supports 60 columns.
342-
343-### One app at three widths
344-
345-A sidebar, a list, and a detail pane, drawn at half scale. Defaults: the sidebar takes 20–30% of the width, clamped to 20–40 columns; the list never goes under 30 columns; the detail pane takes the rest and needs at least 30. A pane below its minimum folds away instead of shrinking: detail first, then the sidebar.

350-| sidebar       | list               | detail                  |
351-+---------------+--------------------+-------------------------+

354-+--------------------+--------------------+

356-+--------------------+--------------------+

440:- **Test with a pseudo-locale.** Before any translation exists, run the UI with every string lengthened by about half and wrapped in markers, as Windows' `qps-ploc`, Android's `en-XA`, and ICU's `en_XA` do, then pressure-test the floor from *Responsive design*. A 60-column split with long labels is where layouts fail. General catalog tools such as gettext's `en@boldquot` and Translate Toolkit's `podebug` produce the strings.
441-- **Right-to-left text.** Most terminals don't implement bidi. kitty, Alacritty, Ghostty, and Windows Terminal show Arabic and Hebrew in logical order, left to right; VTE (GNOME Terminal) and Konsole reorder lines by default, and WezTerm and iTerm2 only experimentally. The [terminal-wg recommendation](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html) has full-screen apps turn off the terminal's reordering (`CSI 8 l` on entry, `CSI 8 h` on exit), which leaves visual order to the app. Either way, keep right-to-left strings in their own field or line, never mix directions inside one cell, and don't promise correct shaping.
442-- **Ambiguous-width characters.** Unicode's East Asian Ambiguous class ([UAX #11](https://www.unicode.org/reports/tr11/tr11-46.html)) is narrow by default and wide only in East Asian legacy contexts, and terminals expose the choice as a setting: iTerm2, VTE, and Windows Terminal 1.25+. Nearly all box drawing, including the rounded corners, is ambiguous, and so are the block elements (`▀` through `▏`, plus `▒ ▓ ▔ ▕`, so every progress-bar block), the triangles `▲ ▶ ▼ ◀`, the shapes `● ○ ■ □ ◆ ★`, `…`, `·`, `•`, and the arrows `←↑→↓`. When the app and the terminal disagree, borders and markers misalign. go-runewidth switches to wide under any `ja`, `ko`, or `zh` locale, while most other width libraries default to narrow. Test with the terminal's ambiguous-wide setting on, prefer narrow-class markers where they fit (`▸ ▾ ▴ ◉ ◦ ⋅ ✓ ✗ ⋯` and the Braille spinner frames), and keep the ASCII border set from *ASCII fallback* and the ASCII bar from *Determinate progress bars* one switch away. Check a glyph against [EastAsianWidth.txt](https://www.unicode.org/Public/18.0.0/ucd/EastAsianWidth.txt); class `A` is ambiguous, `N` or `Na` is not.
443-- **Numbers, dates, and units.** Format human output with the user's locale, because separators, grouping, and even digits differ: 1234567.891 is `1 234 567,891` in French and `12,34,567.891` in Indian English. Use the platform's locale library (`Intl`, Babel, `golang.org/x/text/message`, ICU4X) rather than hand-built strings. Keep machine output (`--json`, `--plain`) locale-independent: under a comma-decimal locale, POSIX `printf` both prints and parses numbers with commas, so pin `LC_NUMERIC=C` for anything a script will read. Fixed-width ISO-8601 dates remain the right choice inside tables.
444-- **Locale detection.** Read `LC_ALL`, then the category variable (`LC_CTYPE` for encoding, `LC_NUMERIC` and `LC_TIME` for formats), then `LANG`, skipping empty values ([POSIX](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html)). `C.UTF-8` is a glibc name rather than a POSIX one, and CI may run in either the C locale or a full one (GitHub's macOS runners set `LC_ALL=en_US.UTF-8`), so tests should pin the locale they expect.

575-## Theming systems
576-
577-Most production TUIs support themes: define semantic tokens (`status.error`, `text.muted`), map them to palette colors in one file per theme (TOML/YAML/CSS), and allow selection via config, env var, or runtime command.
578-
579-### Configuration formats
580-
581-No format is the TUI standard. Common ones: TOML (bottom, helix, starship, alacritty 0.13+), YAML (lazygit, lazydocker, k9s), TCSS (Textual, live-reloads), and flag files or git config (bat's config is a list of CLI flags; fzf reads `FZF_DEFAULT_OPTS` or `FZF_DEFAULT_OPTS_FILE`; delta lives under `[delta]` in `.gitconfig`). Matching the tool your users already configure, as when mirroring lazygit, is a good reason to use its format; otherwise choose the one that suits your own settings.
582-
583-### Community palettes for themeable, broadly distributed apps
584-
585-If theming is part of the product, ship popular palettes (Catppuccin, Dracula, Nord, Gruvbox, Tokyo Night, Rose Pine, Solarized) or document how to import them; the base16 spec underlies many. Users of highly themeable apps expect plug-and-play. Small single-purpose tools still need semantic colors and light/dark safety, but do not need to bundle every palette.
586-
587-### Icons and Nerd Fonts — there is no detection, only opt-in
588-
589-No terminal emulator exposes "a Nerd Font is installed and active" as a queryable signal (not kitty, WezTerm, iTerm2, Alacritty, Windows Terminal, or Ghostty): the protocol has no font capability query, and font-fallback chains can substitute per glyph anyway. Even `has-nerd-font`, which guesses from the terminal's configured font name, still needs a `NERD_FONT=1` override. **Don't invent a detection scheme — gate icons behind an explicit opt-in instead**, the way real tools do:
590-
591-- **eza** — `--icons=WHEN` (`always` / `automatic` / `never`); `automatic` gates on stdout being a TTY, not on font presence.
592-- **lazygit** — `gui.nerdFontsVersion: '2' | '3' | ""`; empty (the default) means no icons at all.
593-- **yazi** — icons are default-on in the shipped theme; users without a Nerd Font override the icon tables in `theme.toml`.
594-
595-**Pin the codepoint generation, not just "Nerd Font on/off."** Nerd Fonts v3 moved Material Design Icons' codepoints (`F500–FD46` → `F0001+`), a documented breaking change, which is why lazygit's config asks for `'2'` or `'3'` explicitly.
596-
597-The fallback ladder is Nerd Font glyphs → plain Unicode symbols → ASCII. starship ships all three rungs as named presets (`nerd-font-symbols` / `no-nerd-font` / `plain-text-symbols`), but most tools are binary (icons on or off), so don't imply every icon-capable tool implements all three.
598-
599-### Light/dark detection
600-
601-- OSC `]11;?` query — many terminals respond with their background color; others never answer, so bound the wait. Mode 2031 reports later theme switches where supported. The query, timeout, and sentinel details are in `terminal-protocols.md` → *Modes and sequences* and *Notes that change a decision*.
602-- `$COLORFGBG` env var — set by some terminals (rxvt-derivatives).
603-- Lipgloss v2's `LightDark` (`AdaptiveColor` in v1/compat) and Textual's runtime theme switching abstract this.
604-
605-If you support both light and dark, default to "auto" and let users override with `--theme dark`.

codex
**The parent controls where siblings go; each container controls its own children.** Width alone doesn’t create columns.

Widgets yielded directly from `App.compose()` become children of the default `Screen`, whose layout is vertical. Your two `Vertical`s therefore stack. Their `Vertical` type only determines how widgets *inside each pane* are arranged.

For your existing structure, the smallest fix is:

```css
Screen {
    layout: horizontal;
}

#sidebar {
    width: 30;
}

#main {
    width: 1fr;
}
```

`30` means terminal columns; `1fr` takes the remaining available width.

If you also have a toolbar above both panes, use a horizontal wrapper for just the panes:

```python
from textual.app import App, ComposeResult
from textual.containers import Horizontal, HorizontalGroup, Vertical
from textual.widgets import Label


class Example(App):
    CSS = """
    Screen { layout: vertical; }
    #toolbar { height: auto; }
    #panes { height: 1fr; }
    #sidebar { width: 30; }
    #main { width: 1fr; }
    """

    def compose(self) -> ComposeResult:
        with HorizontalGroup(id="toolbar"):
            yield Label("Toolbar")

        with Horizontal(id="panes"):
            with Vertical(id="sidebar"):
                yield Label("Sidebar")
            with Vertical(id="main"):
                yield Label("Main")


Example().run()
```

The toolbar behavior comes from **different default sizing**, despite both containers arranging children horizontally:

| Container | Default sizing | Typical purpose |
|---|---|---|
| `Horizontal` | Expands in width and height (`1fr`) | Main pane area |
| `HorizontalGroup` | Expands in width, content-height (`height: auto`) | Toolbar or form row |

A `HorizontalGroup` containing one-line content naturally becomes one row; it isn’t capped at one row. A `Horizontal` requests available height, so it can occupy the whole screen. Use a group—or `height: auto`—for a toolbar. Use an expanding container for the workspace. If you require exactly one row, set `height: 1` and ensure the controls fit.

For resizing, keep the main pane usable:

```text
80 columns                  60-column fallback
Toolbar                     Toolbar
Sidebar (30) | Main (50)     Main; sidebar opens on demand
```

Those widths assume no extra spacing. At 80×24, keep the toolbar content-height and let the pane area take the remaining rows. In a 60-column split, hide the sidebar behind a keyboard toggle if the main pane needs more than 30 columns. The example adds no borders or repeated markers; avoid adding nested borders that consume the remaining space.
