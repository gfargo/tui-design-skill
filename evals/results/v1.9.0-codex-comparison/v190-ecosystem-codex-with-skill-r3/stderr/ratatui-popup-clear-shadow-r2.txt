## Classify the product first

Choose the output contract before choosing a framework or layout:

| Product shape | Default contract |
|---|---|
| One-shot CLI | No live full-screen UI. Stable stdout for results, stderr for diagnostics, meaningful exit codes. Load `cli-basics.md`. |
| Summon–choose–exit tool | Prefer inline when shell context matters. Put interactive chrome on stderr or `/dev/tty` and the selected result on stdout. Use full-screen only when a large preview or working set needs stable space. |
| Full-screen session | Use the alternate screen and a stable spatial model. Treat terminal restoration, resize, suspend, and redraw behavior as product requirements. |

Then name the workflow shape—persistent panels, Miller columns, drill-down stack, dashboard, IDE-style panes, overlay, or tabs—and verify it against `visual-patterns.md`. Sketch the states and layout before writing code: initial, loading, empty, partial, success, error, disconnected, and too-small (`visual-patterns.md` → *States*). In a design answer, include an ASCII sketch of the layout at the floor size (60 columns) next to the wide one.

## Preserve these cross-cutting contracts

### Terminal lifecycle

- Use the alternate screen for full-screen sessions; keep bounded and one-shot workflows inline when possible.
- Prefer framework-managed terminal cleanup. Restore raw mode, screen buffer, cursor, and input modes on every exit path, including errors and panics. Do not invent custom signal handling when the framework already owns it.
- Re-layout from the current frame or window size on resize. Coalesce bursts only when layout work is expensive.
- Treat final shutdown and temporary handoff as different boundaries. For an editor, shell, or supported suspend, prefer the framework's handoff API: pause UI input, restore the shell-facing terminal, wait, re-enter modes, reload externally mutable data, and force a full redraw. Redrawing only repaints the current model; it does not refresh changed data. Do not final-unmount an app that must resume, and do not assume POSIX signals exist on Windows.
- Keep logs and debug output away from the screen the TUI owns. Use a file, framework console, or separate diagnostic stream.

### Rendering, data, and performance

- Never block the UI/event thread on disk, network, or subprocess work. Return results through commands, messages, tasks, channels, or framework events.
- Render on input, data, resize, or intentional ticks; do not redraw unchanged state in an unconditional loop.
- Measure terminal cell width, not bytes, code points, `len()`, or JavaScript string length. Test CJK, combining marks, and emoji.
- Virtualize collections that can grow beyond a few hundred rows. Truncate rather than wrap inside tables; reveal full values in a detail view.
- Keep panel positions stable unless the user explicitly changes the layout. Spatial memory is part of navigation.

### Meaning and access

- Define semantic style tokens rather than scattering color literals. Honor `NO_COLOR` in automatic color mode and preserve meaning in monochrome.
- Never use color alone. Pair it with text, shape, position, or symbols, and provide an ASCII fallback when Unicode support is uncertain.
- Make every action keyboard-reachable. Mouse support may accelerate an action but must not gate it.
- Offer familiar navigation aliases only where they do not conflict with text entry or a complete bounded prompt keymap. Preserve the expected reserved-key behavior: `Ctrl+C` cancels or quits, and `Ctrl+Z` suspends through the framework. Which other keys are reserved, and why raw mode frees `Ctrl+S`, is in `interaction-patterns.md` → *Reserved keys*.
- Match discoverability to complexity: complete inline controls for bounded prompts; contextual hints, help, and optionally a command palette for action-rich full-screen apps.
- Provide a plain `--no-tui` or equivalent mode when automation or serious accessibility needs require linear output; `visual-patterns.md` → *Accessibility* defines what it must contain.

## Apply two review reflexes unprompted

These catch the failures users rarely name. Apply both to every layout you design or review, even when the question is about something else.

### Run a clutter audit

Make “busy” countable. Report:

- border-nesting depth—more than one border between the terminal edge and content is usually too much;
- how many signals encode the same state—`[PASS]`, green, a checkmark, and a row marker is four;
- markers present on every row, which therefore mark nothing;
- the share of cells spent on chrome, labels, and repeated boilerplate instead of data.

Name the exact borders, markers, labels, or repeated fields to remove. Do not stop at “simplify it.” Use the full method in `visual-patterns.md` → *The clutter audit*.

### Pressure-test the floor

State what happens at 80×24 and in a 60-column tmux split: which pane wins, what hides, what truncates, what becomes drill-down, and when the truthful “terminal too small” state appears. Every multi-column design needs a single-pane fallback. Use the breakpoint ladder and minimum-size method in `visual-patterns.md` → *Responsive design*.

## Build and verification discipline

Keep business state independent enough to test without a terminal. In MVU or immediate-mode systems, feed synthetic events into update logic and assert state. In retained/widget systems, drive the smallest widget or app harness that owns the behavior.

Use a bottom-heavy test pyramid:

1. Unit-test state transitions, parsing, sorting, filtering, and command construction.
2. Snapshot or golden-test rendered frames at pinned terminal sizes and color profiles, including 80×24, 60 columns, and the hard minimum.
3. Use one or two PTY end-to-end flows for lifecycle and real-keyboard integration, not as the primary suite.

Verify at least:

- normal exit, interrupt, error, and panic cleanup;
- resize, too-small behavior, and suspend/resume where supported;
- empty, loading, partial, error, disconnected, and large-data states;
- keyboard reachability, focus visibility, and help accuracy;
- `NO_COLOR`, 16-color or monochrome, ASCII fallback, and non-TTY output;
- wide characters, combining marks, truncation, sorting, and virtualization;
- no stdout corruption and no blocking I/O in the event/render path.
- for one-shot CLIs, stdout, stderr, and the exit code in golden tests, with no TTY and under `NO_COLOR` (`cli-basics.md` → *Testing one-shot CLIs*).

Use the ecosystem reference's exact testing and debugging APIs. Never print diagnostics into an active raw-mode or alternate-screen UI.

## Ratatui (ratatui/ratatui)

**Architectural model: immediate-mode rendering.** Every frame, the application redraws the entire UI from current state. The library handles diffing between intermediate buffers and emits only changed cells — "a video codec for text."

The mental model is **"UI = f(state)"**. You manage app state, the event loop, and timing yourself. Ratatui handles the rendering math.

**Canonical app structure:**

```rust check=rust/canonical
use ratatui::{prelude::*, widgets::*, DefaultTerminal};
use ratatui::crossterm::event::{self, Event, KeyCode, KeyEventKind, KeyModifiers};
use color_eyre::Result;

fn main() -> Result<()> {
    color_eyre::install()?;            // install reporting before Ratatui wraps the hook
    ratatui::run(|terminal| App::default().run(terminal))
}

#[derive(Default)]
struct App {
    counter: i32,
    should_quit: bool,
}

impl App {
    fn run(&mut self, terminal: &mut DefaultTerminal) -> Result<()> {
        while !self.should_quit {
            terminal.draw(|frame| self.draw(frame))?;
            self.handle_events()?;
        }
        Ok(())
    }

    fn draw(&self, frame: &mut Frame) {
        frame.render_widget(
            Paragraph::new(format!("Counter: {}", self.counter))
                .block(Block::bordered().title("Demo")),
            frame.area(),
        );
    }

    fn handle_events(&mut self) -> Result<()> {
        if let Event::Key(key) = event::read()? {
            if key.kind == KeyEventKind::Press {
                match key.code {
                    KeyCode::Char('q') | KeyCode::Esc => self.should_quit = true,
                    // raw mode delivers Ctrl+C as a key event, not SIGINT
                    KeyCode::Char('c') if key.modifiers.contains(KeyModifiers::CONTROL) => {
                        self.should_quit = true
                    }
                    KeyCode::Char('+') | KeyCode::Right => self.counter += 1,
                    KeyCode::Char('-') | KeyCode::Left => self.counter -= 1,
                    _ => {} // Ctrl+Z lands here and is silently ignored; see Foreground suspend
                }
            }
        }
        Ok(())
    }
}
```

`ratatui::run()` calls `init()`, runs your closure, then `restore()`. `init()` enables raw mode, enters the alt screen, builds a `Terminal<CrosstermBackend>`, and installs a panic hook that restores the terminal before delegating to the hook already installed, so install reporting hooks such as `color_eyre` **before** it. Use `init()` / `restore()` yourself only when you need code between setup and teardown. `restore()` undoes only raw mode and the alternate screen; mouse capture, bracketed paste, and keyboard-enhancement flags stay on (see [Lifecycle](#lifecycle-and-terminal-handoff)).

### Lifecycle and terminal handoff

Ratatui owns rendering and terminal setup, but not the application event loop, subprocesses, or general process-signal policy. Prefer the managed API and make every external lifecycle event converge on the loop boundary. A bad exit leaves the user in raw mode on the alt screen with no cursor, so install any reporting hook (`color_eyre`) first and let `run()` / `init()` wrap it.

| Boundary | Ratatui 0.30 contract |
|---|---|
| Normal exit | Prefer `ratatui::run(...)`; it initializes, runs the closure, and restores afterward. With `init()` / `restore()`, retain the loop result, restore, then return the result so errors cannot skip cleanup. `restore()` covers only raw mode and the alternate screen; tear down any extra modes first (see *Extra modes* below). |
| SIGTERM | Ratatui does not turn process signals into application events. Use the runtime or a signal integration to send a quit event or cancellation into the loop, then let the closure return through managed cleanup. Default SIGTERM and SIGKILL do not unwind Rust cleanup code. |
| Interactive child | Stop the input reader first (a still-running reader steals the child's keystrokes and terminal capability responses), restore, run and wait for the child, reinitialize, clear, and redraw. Keep the child's result; if child and reentry both fail, report both instead of letting `?` discard one. See the snippet below. |
| Foreground suspend | Ratatui and Crossterm have no suspend support, and in raw mode Ctrl+Z is just a key event, so you must bind it yourself. On Unix, use the same temporary-handoff sequence, send SIGTSTP only after restoration, then reinitialize and redraw after SIGCONT (snippet below). Windows has no job control: offer a drop-to-shell handoff (the editor sequence, running the user's shell) instead. |

**Extra modes are yours to undo.** [`try_restore`](https://github.com/ratatui/ratatui/blob/ratatui-v0.30.2/ratatui/src/init.rs) disables raw mode and leaves the alternate screen, nothing else, and the panic hook only calls `restore()`. Mouse capture, bracketed paste, and Kitty keyboard-enhancement flags stay on after a normal exit or a panic unless you disable them. Pop the keyboard flags while still on the alternate screen, because terminals keep separate [keyboard-mode stacks](https://sw.kovidgoyal.net/kitty/keyboard-protocol/) for the main and alternate screens. So disable extras first, then let `restore()` run, including from a hook that wraps Ratatui's:

```rust check=rust/extra-modes
use std::io::stdout;
use std::sync::atomic::{AtomicBool, Ordering};
use ratatui::crossterm::{
    event::{
        DisableBracketedPaste, DisableMouseCapture, EnableBracketedPaste, EnableMouseCapture,
        KeyboardEnhancementFlags, PopKeyboardEnhancementFlags, PushKeyboardEnhancementFlags,
    },
    execute,
    terminal::supports_keyboard_enhancement,
};

static KITTY_PUSHED: AtomicBool = AtomicBool::new(false);

fn enable_extra_modes() -> std::io::Result<()> {
    execute!(stdout(), EnableMouseCapture, EnableBracketedPaste)?;
    if supports_keyboard_enhancement()? {
        execute!(stdout(), PushKeyboardEnhancementFlags(
            KeyboardEnhancementFlags::DISAMBIGUATE_ESCAPE_CODES))?;
        KITTY_PUSHED.store(true, Ordering::Relaxed);
    }
    Ok(())
}

/// Best effort and idempotent: safe from the panic hook and the normal path.
fn disable_extra_modes() {
    if KITTY_PUSHED.swap(false, Ordering::Relaxed) {
        let _ = execute!(stdout(), PopKeyboardEnhancementFlags);
    }
    let _ = execute!(stdout(), DisableBracketedPaste, DisableMouseCapture);
}

fn main() -> color_eyre::Result<()> {
    color_eyre::install()?;
    ratatui::run(|terminal| {
        let ratatui_hook = std::panic::take_hook(); // the hook run() installed
        std::panic::set_hook(Box::new(move |info| {
            disable_extra_modes();                  // still on the alt screen
            ratatui_hook(info);                     // restore(), then the reporting hook
        }));
        let result = enable_extra_modes()
            .map_err(Into::into)
            .and_then(|()| App::default().run(terminal));
        disable_extra_modes();                      // before run() calls restore()
        result
    })
}
```

**Manual setup.** If you construct `Terminal` and configure Crossterm raw/alternate-screen state yourself, you own normal and panic cleanup; wrap the existing reporting hook:

```rust check=rust/panic-hook
color_eyre::install()?;
let report_hook = std::panic::take_hook();
std::panic::set_hook(Box::new(move |info| {
    ratatui::restore();
    report_hook(info);
}));
```

Do not add that `restore()` wrapper on top of `ratatui::run()` or `ratatui::init()`; those managed APIs already install it. A hook that only undoes extra modes and then delegates to the existing hook, as above, is the exception. The fallible helpers are not transactional: `try_init()` can return after an earlier setup step changed terminal state, and `try_restore()` stops at its first teardown error. If the caller requires fallible setup or teardown, handle an error with independent best-effort cleanup attempts (disable raw mode, leave the alternate screen, disable mouse/paste modes, show the cursor) rather than assuming one returned `Err` rolled everything back. `ratatui::restore()` performs the default Crossterm teardown—custom backends must run their matching backend-specific teardown instead. Whichever path you choose, inject setup/teardown failures and verify normal exit, returned errors, and panics in a PTY.

**Child handoff,** following Ratatui's official [external-editor recipe](https://ratatui.rs/recipes/apps/spawn-vim/):

```rust check=rust/editor-handoff
use std::{io::stdout, process::{Command, ExitStatus}};
use ratatui::crossterm::{execute, terminal::{enable_raw_mode, EnterAlternateScreen}};
use color_eyre::eyre::eyre;

fn run_editor(terminal: &mut DefaultTerminal, app: &mut App) -> Result<ExitStatus> {
    app.input.stop();                                    // async apps: cancel the EventStream task
    ratatui::restore();
    let child = Command::new("vim").arg(&app.path).status(); // keep it; no `?` yet
    let reentry = enable_raw_mode()
        .and_then(|()| execute!(stdout(), EnterAlternateScreen))
        .and_then(|()| terminal.clear());                // next draw repaints every cell
    app.input.start();
    app.reload();                                        // the child may have changed state
    match (child, reentry) {
        (Ok(status), Ok(())) => { terminal.draw(|f| app.draw(f))?; Ok(status) }
        (child, reentry) => Err(eyre!("child: {child:?}; reentry: {reentry:?}")),
    }
}
```

Reentry steps are not transactional (see the fallible-helper warning above), and a successful redraw proves only that the renderer recovered. If the app enabled extra modes, call `disable_extra_modes()` before `ratatui::restore()` (otherwise they stay on while the child runs) and `enable_extra_modes()` after reentry; both are defined under *Extra modes* above.

The suspend path is the same sequence with SIGTSTP in place of the child. Bind `KeyCode::Char('z')` with `KeyModifiers::CONTROL` to set a flag, then call this from the loop. Add `signal-hook` for `raise`; Ratatui's `component` template [does the same](https://github.com/ratatui/templates/blob/5903368da4cfce85144f8efc7070f9c175a8f203/component/template/src/tui.rs) for Ctrl+Z:

```rust check=rust/suspend
#[cfg(unix)]
fn suspend(terminal: &mut DefaultTerminal) -> Result<()> {
    disable_extra_modes();
    ratatui::restore();
    signal_hook::low_level::raise(signal_hook::consts::SIGTSTP)?; // returns after `fg` (SIGCONT)
    enable_raw_mode()?;
    execute!(stdout(), EnterAlternateScreen)?;
    enable_extra_modes()?;
    terminal.clear()?;                                            // next draw repaints every cell
    Ok(())
}
```

### Inline viewport

For tools you summon (pickers, prompts, progress), keep the shell visible. `run()` and `init()` always take the alt screen; `ratatui::init_with_options` enables raw mode and the panic hook but not the alt screen, and `Viewport::Inline(n)` reserves `n` rows below the prompt. Draw into `frame.area()`, not `Rect::new(0, 0, ..)`: the viewport starts wherever the cursor was.

- **Permanent lines** (logs, results) go through `Terminal::insert_before(height, draw_fn)`: they push the viewport down, then scroll into scrollback. Enable Ratatui's `scrolling-regions` feature so it does not clear and redraw the viewport.
- **Exit:** the last frame stays on screen with the cursor at the end of its last cell, so later shell output joins that line. To keep the result, `println!()` after `restore()`. To remove a transient UI, `Terminal::clear()` alone is not enough: it restores the old cursor, so return to the viewport origin as below.

```rust check=rust/inline
use ratatui::{backend::Backend, text::Line, widgets::Widget, Terminal, TerminalOptions, Viewport};

fn main() -> std::io::Result<()> {
    let options = TerminalOptions { viewport: Viewport::Inline(3) };
    let mut terminal = ratatui::init_with_options(options); // no alt screen
    let result = run(&mut terminal);
    let _ = erase_inline(&mut terminal); // omit to keep the last frame, then println!()
    ratatui::restore();
    result
}

/// Permanent output above the live UI.
fn log_above<B: Backend>(terminal: &mut Terminal<B>, text: &str) -> Result<(), B::Error> {
    terminal.insert_before(1, |buf| Line::from(text).render(buf.area, buf))
}

/// Erase a transient UI and leave the cursor where it began.
fn erase_inline<B: Backend>(terminal: &mut Terminal<B>) -> Result<(), B::Error> {
    let origin = terminal.get_frame().area().as_position();
    terminal.clear()?;
    terminal.set_cursor_position(origin)
}
```

### Widgets

**Built-in:** `Block` (borders, title, padding; the container for almost everything), `Paragraph` (wrap, alignment, scroll), `List` / `ListState` and `Table` / `TableState` (selectable, virtualized), `Tabs`, `Chart`, `BarChart`, `Gauge` / `LineGauge`, `Sparkline`, `Canvas` (Braille sub-cell drawing for maps and plots), `Scrollbar`, `Calendar`, `Clear`, and `Fill` (one repeated symbol and style, 0.30.1+).

**Custom widgets** implement the `Widget` trait (one-shot) or `StatefulWidget` (with associated state). Both are zero-cost — they're just `(area, buf)` consumers.

**Popups.** Take the rect from `area.centered(horizontal, vertical)` (`Rect::centered`, 0.30.0+; `centered_horizontally` / `centered_vertically` for one axis) and render `Clear` into it before the popup, or the text underneath shows through every cell the popup leaves blank. `Block::shadow` (0.30.1+) paints an offset drop shadow over the cells beside the block, outside the `Clear`ed rect:

```rust check=rust/popup
use ratatui::layout::{Constraint, Offset};
use ratatui::widgets::{Block, Clear, Paragraph, Shadow};
use ratatui::{style::Stylize, Frame};

fn draw_popup(frame: &mut Frame, message: &str) {
    let area = frame.area().centered(Constraint::Percentage(60), Constraint::Length(5));
    frame.render_widget(Clear, area);
    let shadow = Shadow::dark_shade().black().on_dark_gray().offset(Offset::new(2, 1));
    let block = Block::bordered().title("Confirm").shadow(shadow);
    frame.render_widget(Paragraph::new(message).block(block), area);
}
```

**Text-input cursor.** The terminal's real cursor stays hidden unless you call `frame.set_cursor_position((x, y))` during that draw, in screen coordinates (start from `inner.x`, not 0). Call it only while the input has focus: it follows the user's cursor-shape and blink settings, and IME popups and screen readers track it. Compute `x` in cells, not bytes or chars:

```rust check=rust/input-cursor
use ratatui::{buffer::CellWidth, layout::Rect, widgets::{Block, Paragraph}, Frame};

/// `cursor` is a byte offset on a char boundary of `text`.
fn draw_input(frame: &mut Frame, area: Rect, text: &str, cursor: usize) {
    let block = Block::bordered().title("Search");
    let inner = block.inner(area);
    frame.render_widget(Paragraph::new(text).block(block), area);
    let x = (inner.x + text[..cursor].cell_width()).min(inner.right().saturating_sub(1));
    frame.set_cursor_position((x, inner.y));
}
```

### Layout

Constraint-based using Cassowary (the same algorithm as iOS Auto Layout):

```rust check=rust/layout
use ratatui::layout::{Layout, Constraint};

let [header, body, status] = Layout::vertical([
    Constraint::Length(3),    // 3 rows for header
    Constraint::Min(0),       // body fills remaining
    Constraint::Length(1),    // 1 row for status
]).areas(frame.area());

let [sidebar, main] = Layout::horizontal([
    Constraint::Percentage(30),
    Constraint::Percentage(70),
]).areas(body);
```

Constraints: `Length(n)` exact, `Min(n)` / `Max(n)` bounds, `Percentage(p)`, `Ratio(num, den)`, and `Fill(weight)` (proportional; prefer over `Percentage` for simple ratios). Ratatui caches split results (`layout-cache`), so re-splitting an area is cheap.

### Styling

```rust check=rust/styling
use ratatui::style::{Color, Modifier, Style, Stylize};

// Direct API
let style = Style::default()
    .fg(Color::Yellow)
    .bg(Color::Black)
    .add_modifier(Modifier::BOLD);

// Stylize extension trait (preferred for brevity)
let span = "Hello".bold().yellow().on_black();
```

**Colors:** 16 ANSI named colors (`Color::Red`, `Color::LightRed`, …), `Color::Indexed(u8)` for 256-color, `Color::Rgb(r, g, b)` for truecolor. `ratatui::crossterm::style::available_color_count()` reads only `COLORTERM`/`TERM`, so use it to gate truecolor or 256-color features, not to honor `NO_COLOR`: Crossterm already drops foreground, background, and underline color codes when `NO_COLOR` is non-empty ([`colored.rs`](https://docs.rs/crossterm/0.29.0/src/crossterm/style/types/colored.rs.html)); `style::force_color_output(true)` overrides it. Bold, reverse, and other attributes are still emitted, so keep state distinguishable without color. Avoid the `SLOW_BLINK`, `RAPID_BLINK`, and `CROSSED_OUT` modifiers; terminals support them poorly.

## Backends: Crossterm vs Termion vs Termwiz

- **Crossterm** — default, cross-platform (Linux/macOS/Windows), pure Rust, MIT. Use this unless you have a specific reason not to.
- **Termion** — Unix-only, older, smaller. Choose only if you want Unix-only and minimal dependencies.
- **Termwiz** — terminal library from the WezTerm project. It can encode Sixel, iTerm2, and kitty images, but Ratatui's termwiz backend doesn't expose them; for images use `ratatui-image`, which works with Crossterm.
- **Termina** — `termina` feature (`TerminaBackend`, Ratatui 0.30.2+), built on the Helix editor's terminal library, which sits between Crossterm and Termwiz and targets newer VT extensions such as the kitty keyboard protocol. Import it as `ratatui::termina` (like `ratatui::crossterm`, not a separate dependency). `ratatui::init()` is Crossterm-only, so set up raw mode and cleanup through Termina yourself. Newer and less proven than Crossterm; choose it only when you need what it exposes.

**Crossterm version conflicts** are a foot-gun: two semver-incompatible Crossterm majors cause separate event queues and broken raw-mode tracking. Run `cargo tree -p crossterm` and verify only one version. Crossterm 0.29 (April 2025) is the current stable; 0.28 is the legacy pin. Ratatui 0.30 has per-version feature flags (`crossterm_0_28`, `crossterm_0_29`) so widget-library authors can pin a Crossterm without forcing it on apps; the default is 0.29, and if both end up enabled `crossterm_0_29` takes precedence. In app code, import Crossterm through the re-export (`use ratatui::crossterm`) rather than a separate dependency, so you get the exact version Ratatui uses.

## State management patterns

**1. Monolithic App struct** (simplest, used in most examples):

```rust check=rust/app-struct
struct App {
    items: Vec<Item>,
    list_state: ListState,
    input: String,
    mode: Mode,
    // ...
}
```

**2. Elm Architecture** (Model + Message + update + view; testable update logic when state is complex):

```rust check=rust/elm
enum Msg { Increment, Decrement, Quit }

fn update(model: &mut Model, msg: Msg) -> Option<Cmd> { todo!() }
fn view(model: &Model, frame: &mut Frame) { /* ... */ }
```

**3. Component pattern** — each component implements an `init`/`handle_events`/`update`/`draw` interface and communicates via `mpsc::UnboundedSender<Action>`. The official `component` template in `ratatui/templates` uses this with Tokio. Best for larger apps; **tui-realm** (crate `tuirealm`) formalizes it as a framework (components, subscriptions, message-based events).

## Async with Tokio

The standard pattern: a cancellable task reads Crossterm's `EventStream` into an `mpsc` channel; the main loop `select!`s over that channel and a tick interval, and draws only after an event or a tick that changed visible state (diffing keeps terminal output minimal, but an unconditional draw still rebuilds the widget tree every tick). `EventStream` needs Crossterm's `event-stream` feature, which Ratatui does not enable: add `crossterm = { version = "0.29", features = ["event-stream"] }` matching Ratatui's Crossterm version so Cargo unifies them, and keep importing through `ratatui::crossterm`.

```rust check=rust/async-input
use std::time::Duration;
use futures::StreamExt;
use ratatui::crossterm::event::{Event, EventStream};
use tokio::{sync::mpsc, task::JoinHandle};
use tokio_util::sync::CancellationToken;

fn spawn_input(tx: mpsc::UnboundedSender<Event>, stop: CancellationToken) -> JoinHandle<()> {
    tokio::spawn(async move {
        let mut events = EventStream::new();
        loop {
            tokio::select! {
                _ = stop.cancelled() => break,
                next = events.next() => match next {
                    Some(Ok(event)) => { let _ = tx.send(event); }
                    _ => break,
                },
            }
        }
    })
}

// Main loop
let (tx, mut rx) = mpsc::unbounded_channel();
let stop = CancellationToken::new();
let input = spawn_input(tx, stop.clone());
let mut tick = tokio::time::interval(Duration::from_millis(250));
let mut dirty = true;
while !app.should_quit {
    if std::mem::take(&mut dirty) {
        terminal.draw(|f| app.draw(f))?;
    }
    tokio::select! {
        event = rx.recv() => match event {
            Some(event) => { app.handle(event); dirty = true; }
            None => break, // reader ended (EOF or error); stop instead of ticking with no input
        },
        _ = tick.tick() => dirty = app.on_tick(), // true only if the tick changed something visible
    }
}
stop.cancel();
input.await?;
```

Cancel and await the reader before `ratatui::restore()` or a child handoff (see [Lifecycle](#lifecycle-and-terminal-handoff)), then spawn a fresh reader with a new token. Sync-only apps need no Tokio: `event::poll(Duration::from_millis(250))`, then `event::read()`.

## Testing

`TestBackend` lets you assert against rendered output:

```rust check=rust/test-backend
use ratatui::{backend::TestBackend, Terminal};

let backend = TestBackend::new(20, 5);
let mut terminal = Terminal::new(backend)?;
terminal.draw(|f| app.draw(f))?;
terminal.backend().assert_buffer_lines([
    "┌Demo──────────────┐",
    "│Counter: 0        │",
    "│                  │",
    "│                  │",
    "└──────────────────┘",
]);
```

Pair with **`insta`** for snapshot testing — `insta::assert_snapshot!(terminal.backend())`, reviewed via `cargo insta review` (the officially documented recipe), with one caveat: **snapshots capture text only — color and style are not asserted.** When color matters (selected-row highlight, error styling), compare `Buffer`s instead: build the expected buffer with `Buffer::with_lines(...)`, apply `set_style` to the regions you care about, and `assert_eq!` against the backend's buffer, as the official counter-app tutorial does.

For the lifecycle layer TestBackend can't reach (event loop, key handling, raw-mode setup and teardown, exit code), the same official recipe now shows a PTY end-to-end test with `termlens`: spawn `env!("CARGO_BIN_EXE_<app>")` at a fixed size, wait for visible text, send keys, and snapshot `terminal.screen()` with insta. Keep it to one or two flows, and pin termlens's version because the crate is new (2026).

**Test at multiple sizes.** Resize bugs live at the edges, so render at 80×24, 60 columns, and your declared hard minimum, snapshotting each under a size-suffixed name (`app_60x24`). A pure `fn compute_layout(area: Rect) -> ...` makes per-size assertions cheap, with no terminal at all.

**Restructuring an event loop so tests can drive it** can regress startup (gitui's first insta + TestBackend attempt was reverted when the refactor dropped the initial notify event and the app opened blank for one tick), so cover first draw in the same tests.

## Debugging

`println!` and `dbg!` are broken inside a running TUI: raw mode stops newline processing (crossterm's docs: "`println!` can't be used, use `write!` instead") and the next draw stomps anything printed, or the alt screen hides it. The working options:

- **Log to a file and tail it** (official recipe): `tracing` + `tracing-subscriber` (env-filter) writing to a plain file with ANSI disabled, then `tail -f app.log` in a second terminal.
- **In-app debug pane** (official recipe): keep `show_debug: bool` in app state, split off a column when toggled, and render `format!("{state:#?}")` into it.
- **tui-logger** (0.18.x, actively maintained) — the ready-made in-app log widget, built on `log`, with `slog` and `tracing` support behind feature flags; the official debug recipe points to it. Its `crossterm` / `termion` features gate only the crate's demo example, not the widget (it takes `ratatui` without default features, so the widget uses your app's backend); translate your own key events into `TuiWidgetEvent`s.
- **Debuggers:** attach from a *second* terminal (`lldb -p <pid>` / `gdb -p`) or use an IDE debugger so the debug console is separate from the app's terminal — stopping the process in its own terminal leaves you at a prompt that's still in raw mode + alt screen.

**Profiling:** use `cargo flamegraph` or `samply`. In raw mode Ctrl+C is a key event, not SIGINT, so it won't end a recording: quit through your app's own key, or attach with `flamegraph --pid <pid>`. In Tokio apps, `tokio-console` shows per-task poll and busy time. The usual slow path is O(n) work inside the render closure (collecting a large `Vec`, recomputing string widths every draw), not widget construction, which Ratatui expects every frame.

## Pitfalls

1. **Naive redraw loop.** Don't busy-loop on `draw`; use `event::poll(timeout)` (sync) or `tokio::select!` (async).
2. **On Windows, both Press and Release events fire.** Filter with `key.kind == KeyEventKind::Press`.
3. **Stateful widgets need state ownership.** `List`, `Table`, `Scrollbar` are `StatefulWidget`s — you pass `&mut ListState` / `TableState` / `ScrollbarState` at render time; the state lives in your App struct, not the widget.
4. **Mouse capture disables terminal text selection.** Most emulators bypass with Shift; document this.
5. **`String::len()` is bytes, not cells.** Use `Line::width()` / `Span::width()` for Ratatui text, but for cursor math or any width that must match what Ratatui draws use `ratatui::buffer::CellWidth` (`s.cell_width()`, 0.30.1+). `Line::width()` and `unicode_width` count halfwidth katakana marks (U+FF9E, U+FF9F) as zero cells; the renderer draws one.
6. **No accessibility layer.** Ratatui has no screen-reader support; [ratatui#2610](https://github.com/ratatui/ratatui/issues/2610) tracks it, and the experimental `tui-a11y` crate is Linux-only. Give screen-reader users a linear mode; see `visual-patterns.md` → *Accessibility*.

273-4. **Whitespace** — blank rows for separation; pads around important content.

275-6. **Borders** — a heavier border weight marks the focused panel.
276-

281-## Density: pack vs pad
282-
283-You have a fixed grid. Two strategies:
284-
285-**Pack (high density)** — htop, btop, k9s. For data scanned at a glance, updated in real time, and read horizontally across rows. Use tight one-line records, compact dim headers, abbreviations and units (`GiB`, `1.2k`, `99.9%`), and sparklines or mini-bars.
286-
287:**Pad (low density)** — gum/huh forms, glow, Posting. For prose, forms, and single decisions. Use generous vertical spacing, one field per line with labels above for narrow terminals, a single column, and lots of margin around modals.
288-
289:Use density to communicate hierarchy: dense data tables in the main panel, padded settings/forms in modals, dense status bars at the bottom.
290-
291:**Spacing defaults.** One blank row between groups, 1 cell of inner padding inside a bordered panel, a 2-cell gutter between table columns, and modals no wider than 60–80% of the terminal (fixed to content below that, never edge to edge).
292-
293:### The clutter audit — making "feels busy" countable
294-
295-"It feels noisy" is a real signal but useless until you convert it into specific offenders. When a layout feels cluttered, **count — don't squint** — and report the count, not a vibe:
296-
297-- **Border-nesting depth.** Trace any corner from the terminal edge inward. More than *one* border between the edge and the content is too many. A border wrapping content that's already inside a bordered panel separates nothing and shows no focus — delete it. Boxes-inside-boxes is the single most common cause of "busy," and an outer full-screen frame is almost always redundant (the terminal edge already frames the app).
298-- **Signals per piece of state.** Count how many things encode the same fact. `[PASS]` + green + `✅` + a `▸` row prefix is *four* signals for one status. **The budget is at most one color cue plus one non-color cue** (green plus a word, letter, or symbol); cut the rest. This is the one rule other sections point to.
299-- **Always-on markers.** A glyph that appears on 100% of rows (a `▸` on every line) marks nothing — it's texture, not information. Reserve markers for the exception: the selected row, the failed item.
300-- **Chrome-to-data ratio.** Add up the cells spent on borders, titles, padding, labels, and repeated boilerplate (a full ISO date on every log line when only the time changes) versus cells showing actual data. A high chrome ratio *is* the cluttered feeling.
301-- **The removal test.** For each decorative element ask: "if I delete this, do I lose information?" If no, delete it. Whitespace is not empty space — it's the cheapest separator you have, and a single blank row routinely out-reads a heavy border.
302-
303-Run this pass on any layout, yours or someone else's. "Three concentric borders, status encoded four ways, a marker on every row" tells the user exactly what to cut; "simplify it" tells them nothing.

330:## Responsive design — breakpoints and the floor
331-
332-A terminal layout is not designed for one size. The same app runs on a 220-column ultrawide, an 80×24 SSH session, a 60-column tmux split, and a 13-inch laptop. **A layout that only works at the author's window size is unfinished** — and the author rarely notices, because they only ever see their own terminal. Pressure-test every layout at the floor, and raise it in any review even when the user only asked about something else: it's the most-missed issue in TUI design.
333-
334-### The breakpoint ladder
335-
336-Decide behavior per width band, widest to narrowest. Exact thresholds depend on content, but the shape is universal:
337-
338-- **Wide (120+ cols)** — the full multi-panel layout; you can afford a side panel or preview alongside the primary view.
339-- **Standard (80–119)** — the baseline most users see. Often: one primary view full-width, with details/logs on drill-in (Enter / a key) rather than permanently side-by-side.
340-- **Narrow (60–79)** — collapse to a single column. Stack panels vertically or hide all but the primary. Multi-column layouts (Miller columns, 2×N grids) **must** fold to one pane here. (lazygit's `--screen-mode full` is a related single-panel mode — but it's a user-selectable escape hatch, not automatic responsive behavior.)
341-- **Below the application-specific minimum** — don't render garbage or panic. Show the too-small state (see *States*), naming the dimensions the app actually requires, until the user resizes. Do not claim an 80-column requirement if the single-pane layout intentionally supports 60 columns.
342-
343-### One app at three widths
344-
345-A sidebar, a list, and a detail pane, drawn at half scale. Defaults: the sidebar takes 20–30% of the width, clamped to 20–40 columns; the list never goes under 30 columns; the detail pane takes the rest and needs at least 30. A pane below its minimum folds away instead of shrinking: detail first, then the sidebar.
346-
347-```
348-120 columns: sidebar 30, list 40, detail 50
349-+---------------+--------------------+-------------------------+
350-| sidebar       | list               | detail                  |
351-+---------------+--------------------+-------------------------+
352-
353-80 columns: sidebar becomes a toggle; list 40, detail 40
354-+--------------------+--------------------+
355-| list               | detail             |
356-+--------------------+--------------------+
357-
358-60 columns: one pane; Enter opens the detail, Esc returns
359-+------------------------------+
360-| list                         |
--
407-
408-Three approaches:
409-
410-1. **Hide low-priority columns.** Define column priority; drop them as width shrinks.
411-2. **Horizontal scroll.** htop scrolls the process table left and right with the arrow keys when columns overflow.
412:3. **Detail-on-Enter.** Pressing Enter on a row opens a side panel or modal showing all fields. The highest-leverage option: show fewer columns, and the user is one keypress from full detail.
413-
414-### Virtualization
415-
416-**Always virtualize** lists that might exceed a few hundred items.
417-
418-- **k9s** (thousands of pods) and **Toolong** (multi-GB logs) virtualize.
419-- **Textual `DataTable`**, **Ratatui `List` + `ListState`**, and **Bubbles `list`** virtualize or offset efficiently.
420-- **Ink** needs an explicitly windowed slice or viewport for a changing collection. `<Static>` is only for finalized append-only history; it does not virtualize selectable, filtered, or otherwise mutable rows.
421-
422-The naive "render all rows, scroll viewport" approach degrades horribly at 10k+ items.
423-
424-### Emoji and aligned columns
425-
426-Emoji whose base character is East Asian Wide (`✅ ❌ ⭐`, plus most pictographs) take 2 cells everywhere. Emoji built from a narrow base plus a variation selector or joiner (`⚠️` is U+26A0 + U+FE0F, `✔️`, `❤️`, ZWJ families) take 1 or 2 depending on the terminal and the width library, so a column that contains them can misalign by a cell per row. For status columns use narrow text symbols (`✓ ✗ !`) or words; if you want emoji, choose Wide-base ones, measure with a grapheme-aware width library, and test on the terminals you support (see *Localization* for the width classes).
427-
428-### Diff views
429-
430-Choose by width: **unified** below about 120 columns, **side-by-side** at 120 or more, where each side keeps at least 55 columns plus a 2-cell gutter. Mark lines with a `+` or `-` in the first column (color only reinforces it), keep a line-number gutter, and highlight changed words inside a changed line. Navigate by hunk with `]`/`[` (or `n`/`N`). Don't wrap in side-by-side; truncate and scroll horizontally.

435-## Localization
436-
437-Terminal layouts assume a fixed number of cells per string, so translated text breaks them in ways a GUI would absorb.
438-
439-- **Budget for growth.** Translations run longer than English, and short strings grow most. IBM's globalization guidelines allow 100–200% extra space for strings up to 10 characters and 30% past 70 ([IBM](https://public.dhe.ibm.com/systems/power/docs/systemi/v5r2/en_US/rbagsmstp3.pdf), p. 16), and Microsoft's pseudo-localization lengthens text by 40% ([Microsoft](https://learn.microsoft.com/en-us/globalization/methodology/pseudolocalization)). Footer hints, column headers, and button labels are exactly those short strings. Size columns from the rendered text rather than the English labels, and let labels truncate before data does, with the full text in help.
440:- **Test with a pseudo-locale.** Before any translation exists, run the UI with every string lengthened by about half and wrapped in markers, as Windows' `qps-ploc`, Android's `en-XA`, and ICU's `en_XA` do, then pressure-test the floor from *Responsive design*. A 60-column split with long labels is where layouts fail. General catalog tools such as gettext's `en@boldquot` and Translate Toolkit's `podebug` produce the strings.
441-- **Right-to-left text.** Most terminals don't implement bidi. kitty, Alacritty, Ghostty, and Windows Terminal show Arabic and Hebrew in logical order, left to right; VTE (GNOME Terminal) and Konsole reorder lines by default, and WezTerm and iTerm2 only experimentally. The [terminal-wg recommendation](https://terminal-wg.pages.freedesktop.org/bidi/recommendation/basic-modes.html) has full-screen apps turn off the terminal's reordering (`CSI 8 l` on entry, `CSI 8 h` on exit), which leaves visual order to the app. Either way, keep right-to-left strings in their own field or line, never mix directions inside one cell, and don't promise correct shaping.
442-- **Ambiguous-width characters.** Unicode's East Asian Ambiguous class ([UAX #11](https://www.unicode.org/reports/tr11/tr11-46.html)) is narrow by default and wide only in East Asian legacy contexts, and terminals expose the choice as a setting: iTerm2, VTE, and Windows Terminal 1.25+. Nearly all box drawing, including the rounded corners, is ambiguous, and so are the block elements (`▀` through `▏`, plus `▒ ▓ ▔ ▕`, so every progress-bar block), the triangles `▲ ▶ ▼ ◀`, the shapes `● ○ ■ □ ◆ ★`, `…`, `·`, `•`, and the arrows `←↑→↓`. When the app and the terminal disagree, borders and markers misalign. go-runewidth switches to wide under any `ja`, `ko`, or `zh` locale, while most other width libraries default to narrow. Test with the terminal's ambiguous-wide setting on, prefer narrow-class markers where they fit (`▸ ▾ ▴ ◉ ◦ ⋅ ✓ ✗ ⋯` and the Braille spinner frames), and keep the ASCII border set from *ASCII fallback* and the ASCII bar from *Determinate progress bars* one switch away. Check a glyph against [EastAsianWidth.txt](https://www.unicode.org/Public/18.0.0/ucd/EastAsianWidth.txt); class `A` is ambiguous, `N` or `Na` is not.
443-- **Numbers, dates, and units.** Format human output with the user's locale, because separators, grouping, and even digits differ: 1234567.891 is `1 234 567,891` in French and `12,34,567.891` in Indian English. Use the platform's locale library (`Intl`, Babel, `golang.org/x/text/message`, ICU4X) rather than hand-built strings. Keep machine output (`--json`, `--plain`) locale-independent: under a comma-decimal locale, POSIX `printf` both prints and parses numbers with commas, so pin `LC_NUMERIC=C` for anything a script will read. Fixed-width ISO-8601 dates remain the right choice inside tables.
444-- **Locale detection.** Read `LC_ALL`, then the category variable (`LC_CTYPE` for encoding, `LC_NUMERIC` and `LC_TIME` for formats), then `LANG`, skipping empty values ([POSIX](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap08.html)). `C.UTF-8` is a glibc name rather than a POSIX one, and CI may run in either the C locale or a full one (GitHub's macOS runners set `LC_ALL=en_US.UTF-8`), so tests should pin the locale they expect.

448-## Status bars, headers, footers
449-
450-### A common full-screen four-section layout
451-
452-Header (persistent context: app, dataset, mode), then the main area (the panels), then a status/mode line (ephemeral feedback), then a footer hint bar (contextual shortcuts). Some apps merge status and footer into one line, and some skip the header. Complex full-screen apps benefit from persistent context around the work area; bounded inline tools often need neither a header nor a dedicated footer.
453-
454-### Header content
455-
456-- App name, plus the current dataset or context: branch name (lazygit), cluster + namespace (k9s), file path (bat/glow).
457-- Mode indicator (NORMAL / INSERT in editors).
458-- Right-aligned: time, host, version, sparingly and only if meaningful.
459-
460-### Status / mode line
461-
462-- Ephemeral feedback: "Saved", "3 files changed", "Connecting...".
463-- Success and info messages fade after 3–5 seconds or give way to the idle state. Keep errors and warnings until the user dismisses them, then move them to a message log the user can reopen (a `:messages` command or a key): a message that vanishes unread can't be acted on.
464-- **Toasts and the message log.** Show a transient message in the status line, or as a toast at the bottom-right just above the footer so it never covers the row being acted on, with at most two visible. Every message, errors included, is also written to a log the user can reopen (`:messages` or a key): newest last, with a timestamp and kind, capped around 200 entries for the session.
465:- The current mode, for modal apps (label and cursor shape: `interaction-patterns.md` → *Keybinding philosophies and modal vs modeless*).
466-- Lead each message with a symbol or label word (`✓ Saved`, `! Low disk space`, `✗ Save failed`) so the kind survives `NO_COLOR`, with green, yellow, or red as the one reinforcement. A message that already starts with a label (`Error:`) needs no symbol too; error wording follows `cli-basics.md` → *Error messages*.
467-
468-### Footer hint bar
469-
470-Lay hints out as `key action ⋅ key action ⋅ key action`, with `⋅` (U+22C5; the middle dot `·` is ambiguous-width) or `|` as the separator; htop's `F1Help F2Setup F3Search …` strip is the classic form. Put the most frequent action first and `?` last, and show one rendered line per width:
471-
472-```
473-80 columns:  q quit ⋅ / filter ⋅ enter open ⋅ space select ⋅ d delete ⋅ ? help
474-40 columns:  q quit ⋅ / filter ⋅ ? help
475-```
476-
477-Drop hints from the right of the least frequent until the line fits, keeping `?` so the full list stays one key away. Which shortcuts to show and how to generate them from your keymap: `interaction-patterns.md` → *Layer 1: Always-visible footer hints*.

481:## Modals and dialogs
482-
483-- **Width:** 60–80% of the terminal, at most about 80 columns for prose, at least 30. Center it horizontally and place it slightly above vertical center.
484:- **One modal at a time.** A second request replaces the first or queues behind it; `Esc` closes one modal per press (`interaction-patterns.md` → *Esc, q, and Ctrl+C*). The modal traps focus.
485-- **Clear the cells behind it** (draw a blank background) so underlying text doesn't bleed through, and give it its own border and a title.
486:- **Modality must not rest on dimming.** Dim the background with the faint attribute where supported, but dimming is an attribute, not a color, and some terminals ignore it. The border, the title, and the changed footer hints say "you are in a dialog" under `NO_COLOR` and without faint.

509-

575-## Theming systems
576-
577-Most production TUIs support themes: define semantic tokens (`status.error`, `text.muted`), map them to palette colors in one file per theme (TOML/YAML/CSS), and allow selection via config, env var, or runtime command.
578-
579-### Configuration formats
580-
581-No format is the TUI standard. Common ones: TOML (bottom, helix, starship, alacritty 0.13+), YAML (lazygit, lazydocker, k9s), TCSS (Textual, live-reloads), and flag files or git config (bat's config is a list of CLI flags; fzf reads `FZF_DEFAULT_OPTS` or `FZF_DEFAULT_OPTS_FILE`; delta lives under `[delta]` in `.gitconfig`). Matching the tool your users already configure, as when mirroring lazygit, is a good reason to use its format; otherwise choose the one that suits your own settings.
582-
583-### Community palettes for themeable, broadly distributed apps
584-
585-If theming is part of the product, ship popular palettes (Catppuccin, Dracula, Nord, Gruvbox, Tokyo Night, Rose Pine, Solarized) or document how to import them; the base16 spec underlies many. Users of highly themeable apps expect plug-and-play. Small single-purpose tools still need semantic colors and light/dark safety, but do not need to bundle every palette.
586-
587-### Icons and Nerd Fonts — there is no detection, only opt-in
588-
589-No terminal emulator exposes "a Nerd Font is installed and active" as a queryable signal (not kitty, WezTerm, iTerm2, Alacritty, Windows Terminal, or Ghostty): the protocol has no font capability query, and font-fallback chains can substitute per glyph anyway. Even `has-nerd-font`, which guesses from the terminal's configured font name, still needs a `NERD_FONT=1` override. **Don't invent a detection scheme — gate icons behind an explicit opt-in instead**, the way real tools do:
590-
591-- **eza** — `--icons=WHEN` (`always` / `automatic` / `never`); `automatic` gates on stdout being a TTY, not on font presence.
592-- **lazygit** — `gui.nerdFontsVersion: '2' | '3' | ""`; empty (the default) means no icons at all.
593-- **yazi** — icons are default-on in the shipped theme; users without a Nerd Font override the icon tables in `theme.toml`.
594-
595-**Pin the codepoint generation, not just "Nerd Font on/off."** Nerd Fonts v3 moved Material Design Icons' codepoints (`F500–FD46` → `F0001+`), a documented breaking change, which is why lazygit's config asks for `'2'` or `'3'` explicitly.
596-
597-The fallback ladder is Nerd Font glyphs → plain Unicode symbols → ASCII. starship ships all three rungs as named presets (`nerd-font-symbols` / `no-nerd-font` / `plain-text-symbols`), but most tools are binary (icons on or off), so don't imply every icon-capable tool implements all three.
598-
599-### Light/dark detection
600-
601-- OSC `]11;?` query — many terminals respond with their background color; others never answer, so bound the wait. Mode 2031 reports later theme switches where supported. The query, timeout, and sentinel details are in `terminal-protocols.md` → *Modes and sequences* and *Notes that change a decision*.

Render **the main view → `Clear` → the dialog**, in that order. A bordered `Paragraph` leaves some cells untouched, so underlying text survives unless you clear the popup rectangle first.

For **Ratatui 0.30.1+**, centering and a drop shadow are built in:

```rust
use ratatui::{
    layout::{Constraint, Offset},
    style::Stylize,
    widgets::{Block, Clear, Paragraph, Shadow},
    Frame,
};

fn draw_confirm(frame: &mut Frame) {
    // Draw your main view before calling this function.
    let area = frame.area().centered(
        Constraint::Percentage(60),
        Constraint::Length(5),
    );

    frame.render_widget(Clear, area);

    let shadow = Shadow::dark_shade()
        .black()
        .on_dark_gray()
        .offset(Offset::new(2, 1));

    let block = Block::bordered()
        .title("Confirm")
        .shadow(shadow);

    frame.render_widget(
        Paragraph::new("Delete this item?\n\n[y] Delete  [Esc] Cancel")
            .block(block),
        area,
    );
}
```

`Rect::centered` requires **0.30.0+**; `Shadow` and `Block::shadow` require **0.30.1+**. The shadow paints outside the cleared rectangle, offset two columns right and one row down. Choose its colors from your theme.

At 80 columns this dialog is 48 columns wide; in a 60-column split it is 36:

```text
80 columns                     60 columns
      + Confirm --------+          + Confirm --------+
      | Delete this item?|          | Delete this item?|
      |                  |          |                  |
      |[y] Delete [Esc]… |          |[y] Delete [Esc]… |
      +------------------+          +------------------+
```

Recompute the rectangle each frame so resizing recenters it. For longer messages, wrap and allocate enough height; below your minimum usable size, show a “terminal too small” message. Keep one dialog border, and route input exclusively to the dialog while it is open—`Clear` fixes rendering, but does not create modal focus.
